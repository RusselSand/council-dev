# Совет · бекенд — правила для агента

Ты пишешь новый API бекенда Spec Council («Совет») по контракту `docs/api-contract.md`. Новый API заменяет старый:
старые ручки уходят, новые встают на их место. Одна задача — один этап совета (все его ручки), одна ветка, один PR.

Фронтенд уже готов и работает по этому же контракту на моках. Твоя задача — чтобы он так же работал на настоящем
сервере.

Разделы «Вопросы» и «Замечания Codex» — в корневом `CLAUDE.md`, они действуют и здесь. Остальное в корневом файле —
про фронтенд.

## Что читать перед работой

1. Issue задачи: `gh issue view <номер>`. Это ТЗ: какой этап, какие ручки контракта, какие старые ручки уходят.
2. `docs/api-contract.md`: разделы «Решения», «Общее», «Объекты» и ручки своего этапа целиком.
3. `docs/old/arch.md` — как устроен совет: модели, нарезка, группы, исследование, потоки, задачи, хранение. Написан
   для старой версии: про бекенд он верен, про старый фронт — нет.
4. Код `backend/spec_council/` и тесты `backend/tests/`.
5. Старый фронт — копия только для чтения (путь назван в задании). Из него видно, как раньше фронт вёл совет:
   какие ручки звал и в каком порядке, какие правила считал сам (`api.ts`: `tasksStale`, `outcomeReady`,
   `groupsConfirmed` и другие).

## Что ты решаешь сам, а что — нет

**Контракт — закон.** Ручки, пути, тела, ответы, поля, коды ошибок и правила, которые в нём описаны («что меняется»,
когда действие доступно, что сервер не принимает), — решены. Раздел «Решения» — ответы владельца, они главнее
остального контракта.

Сам решаешь: внутреннее устройство — модули, имена, как хранить новые поля, как запускать работу моделей в фоне, как
устроены тесты.

Не решаешь сам:

- всё, чего нет в контракте: новые ручки, поля, состояния, правила;
- отступления от контракта. Если по контракту сделать нельзя (то, что он обещает, домен не умеет, или правило
  противоречит тому, как устроен совет) — вопрос владельцу, а не своя версия. Контракт молча не меняй;
- правила совета, которые сейчас живут в коде (`pipeline.py`, `work.py` и другие), не меняй, если контракт этого
  не требует.

Ответ владельца меняет контракт — в той же задаче поправь контракт, а если меняется то, что видит фронтенд, — и
фронтенд: типы, моки, http.

## Старый API и что переходит в бекенд

- Новые ручки — под `/api`, как в контракте. Старые ручки своего этапа и их тесты в той же задаче удаляешь.
- Логику домена переиспользуй: нарезку, группы, исследование, работу по вопросам, итоги, задачи, хранение. Не
  переписывай её без нужды.
- **Цепочка шагов теперь на сервере.** Раньше следующий шаг моделей запускал фронт: позвал одну ручку, дождался,
  позвал следующую. Теперь, как сказано в контракте, действие человека («утвердить», «подтвердить») само запускает
  следующую работу моделей на сервере. Порядок шагов бери из старого фронта и `docs/old/arch.md`.
- Работа моделей идёт в фоне: ручка действия отвечает сразу, а ход работы фронт видит, опрашивая ручки чтения.
- **Советы, сохранённые старой версией, должны открываться.** Они лежат в `.data/<id>.json` (или в `COUNCIL_DATA`).
  Новое поле в хранении — с умолчанием для старых файлов, а не миграция, которая их переписывает.

## Тесты

- Каждая ручка — тест через HTTP (`TestClient`): ответ по контракту, ошибки с кодами, «что меняется».
- Модели в тестах не запускаются: подделки, как в `tests/conftest.py`.
- Старые тесты ручек, которые ты удалил, удаляешь вместе с ними; тесты домена остаются и должны проходить.

## Проверки

Перед каждым коммитом:

- `uv --directory backend run ruff check .`
- `uv --directory backend run pytest`

Поправил фронтенд — ещё `npm --prefix frontend run typecheck` и `npm --prefix frontend run build`. Всё должно
пройти. После пуша то же прогонит CI на GitHub, и цикл не вольёт PR без зелёного CI.

## Git

- Работаешь в ветке, которую назвал цикл. В `main` не коммить, не вливай, `--force` не используй.
- Сообщения коммитов — по-русски, по делу.
- Первый раз: коммит, `git push -u origin <ветка>`, `gh pr create --base main` с описанием по-русски:
  - твой план задачи;
  - какие ручки контракта сделаны;
  - какие старые ручки и тесты удалены;
  - что из старого фронта перенесено в бекенд (цепочка шагов, правила);
  - что добавилось в хранении и как открываются старые советы;
  - где пришлось отступить от контракта и по какому решению владельца;
  - строка `Closes #<issue>`.
- В индекс добавляй только свои файлы, не `git add -A`. `.data/`, `.accounts/`, `.repos/`, `.env` в коммиты
  не попадают.
- `@codex review` не пиши — это делает цикл.
