# Совет · фронтенд — правила для агента

**Этот файл — про фронтенд (`frontend/`).** Задача про бекенд (заголовок issue начинается с «Бекенд ·») — правила
в `backend/CLAUDE.md`; из этого файла для неё действуют только разделы «Вопросы» и «Замечания Codex».

Фронтенд Spec Council («Совет») собран по макету, экран за экраном: одна задача — один экран или окно, одна ветка,
один PR. Экраны работают на моках или на настоящем сервере (`VITE_DATA_SOURCE`). Что умеет сервер — контракт
`docs/api-contract.md`; бекенд пишется по нему.

Старый фронтенд совета (репозиторий `council`) — не образец. Его кода в репозитории нет: не ищи его и не подгоняй
под него экраны и контракт.

## Что читать перед работой

1. Issue задачи: `gh issue view <номер>`. Это ТЗ: какой экран, его адрес в макете, что входит в задачу и что нет.
2. Макет — см. «Макет и сверка с ним».
3. `frontend/README.md` — как устроен фронтенд. Появляется с первой задачей; меняешь устройство — обнови его
   в том же PR.
4. `docs/api-contract.md` — контракт. Появляется с первой задачей. Раздел **«Решения»** — закон: всё, что там
   написано, решено владельцем.

## Что ты решаешь сам, а что — нет

**Макет — источник правды.** Что на нём есть — решено: экраны, блоки, тексты, действия, этапы совета и шаги потока,
состояния советов, этапов и шагов. Правила, которые видны в коде макета (когда кнопка доступна, что проверяется
перед действием, что меняется после него), — тоже часть макета: перенеси их и запиши в контракт.

Сам решаешь: из каких компонентов собрать экран, имена, форму данных и ручек в контракте, коды ошибок, как выглядят
загрузка и ошибка там, где макет их не показывает (одинаково на всех экранах).

Не решаешь сам: всё, чего в макете нет, — новые сущности, состояния, статусы, правила, настройки, кнопки. Даже если
это кажется очевидным, даже если об этом просит ревью Codex. Такое — вопрос владельцу (см. «Вопросы»), а не код.

Заглушки макета — не правила: застывшие дата и время, «как будто модели поработали» по таймеру, ответы «как будто
сработало». У нас такие значения приходят из данных.

## Макет и сверка с ним

- Макет один: `design/Совет - прототип.html`, только под компьютер. Телефонную раскладку не делаем. Файл макета
  не меняй.
- Код макета читай в `design/.src/Совет - прототип/`: `prototype.js` — данные, состояния и действия всех экранов,
  `markup.html` — разметка и стили, `data-1.json` — данные настоящего совета `g1`. Папки нет —
  `npm --prefix frontend run proto` (скрипт появляется с первой задачей).
- У каждого экрана макета свой адрес после `#`. Адреса настоящего совета `g1`:
  - `#/home` — Сводка
  - `#/projects` — Проекты
  - `#/c/g1/brief` — Ввод
  - `#/c/g1/slices` — Нарезка
  - `#/c/g1/structure` — Группы
  - `#/c/g1/research` — Исследование
  - `#/c/g1/streams/A/project` — поток A, шаг «Решения проекта»
  - `#/c/g1/streams/A/questions` — Вопросы
  - `#/c/g1/streams/A/options` — Варианты
  - `#/c/g1/streams/A/decisions` — Решения
  - `#/c/g1/streams/A/outcomes` — Итоги
  - `#/c/g1/streams/A/notes` — Документация
  - `#/c/g1/tasks` — Задачи

  Общий вид: `#/c/<совет>/<этап>`, у потоков — `#/c/<совет>/streams/<поток>/<шаг>`. У нас адреса те же, без `#`.
- **Варианты макета.** В макете есть переключатели вида. Делаем так:
  - Сводка — и канбан, и список; человек переключает их на экране, как в макете;
  - прогоны шагов потока — только вид «grouped»; виды «grid» и «summary» не делаем;
  - список советов в меню слева и панель прогонов — показываются, как по умолчанию в макете.

  Сами настройки макета (его панель переключателей для дизайнера) в приложение не переносятся.
- **Не копируй код макета.** Это одноразовый код с другим устройством. Экран собирается из наших `ui/`
  и `components/`; цвета, шрифты и отступы — из токенов. В макете встретилось новое значение — добавь токен, а не
  пиши значение в компонент.
- В моки бери примеры из макета: настоящий совет `g1` — из `data-1.json`, остальные советы и проекты —
  из `prototype.js`. Так экраны проще сверять.
- Скриншоты: `npm --prefix frontend run shot -- --name <id> --proto "#/c/g1/slices" --app "/c/g1/slices"` →
  `design/.shots/<id>-proto.png` и `<id>-app.png`; открывай их через Read. Сравнивай раскладку, иерархию, состав
  блоков, тексты и поведение, а не пиксели. Скрипт тоже появляется с первой задачей.

## Как устроен фронтенд

- Код — в `frontend/`: React 18, TypeScript, Vite. Рядом потом встанет бекенд, поэтому в корне репозитория кода
  фронтенда нет. Команды npm запускай из корня репозитория: `npm --prefix frontend run <скрипт>`.
- `frontend/src/`:
  - `ui/` — то, что не знает про совет: кнопка, поле, переключатель;
  - `components/` — знает про советы, проекты, этапы и потоки, но не привязано к одному экрану;
  - `features/<экран>/` — экран: `useX.ts` (данные и действия, без JSX), `X.tsx`, `parts/`, стили, `index.tsx`;
  - `data/` — слой данных: интерфейс источника, моки, http, хуки запросов;
  - `domain/` — типы и расчёты без React;
  - `i18n/` — тексты интерфейса: словари языков, `t()`, даты и числа по правилам языка;
  - `styles/tokens.css` — цвета, шрифты, отступы.
- Экран не ходит в `fetch` сам — только через хуки слоя данных.
- Новая зависимость — только если без неё нельзя; назови её в описании PR.

### Переиспользование и компоненты

Компоненты никто не выделяет заранее: они появляются по ходу экранов. Поэтому порядок на каждом экране такой.

- **Сначала ищи, что уже есть.** Прежде чем писать новое, просмотри `ui/`, `components/` и `parts/` других экранов.
  Похожее уже есть — используй его или добавь ему вариант (`variant`, `size`, проп), а не копируй с правками.
- **Новый компонент — только если готового действительно нет.** В описании PR назови каждый новый компонент
  и объясни, почему готовое не подошло.
- **Куда класть:** без знания домена — `ui/`; со знанием домена, но не привязанное к одному экрану — `components/`;
  то, что имеет смысл только на этом экране, — `features/<экран>/parts`. Кусок из `parts` понадобился второму
  экрану — перенеси его в `components/` или `ui/`, а не копируй.
- **Собирай экран из небольших компонентов** с одной задачей каждый. Большой файл экрана — признак того, что его
  надо разрезать.
- Данные и действия — в хуке, вёрстка — в компоненте, расчёты — в `domain/`.
- Новое поведение общего компонента — через пропы и варианты, а не через `if` под конкретный экран внутри него.
- Компонент получает данные пропами и не знает, откуда они. Передавай то, что ему нужно, а не весь объект.
- Зависимости сверху вниз: `ui/` не импортирует `components/` и `features/`, `components/` не импортирует `features/`.

## Тексты интерфейса

Интерфейс переводится. Как добавить текст или язык и список терминов — в `frontend/README.md`, раздел «Тексты
интерфейса».

- **Все тексты интерфейса — в словаре** `frontend/src/i18n/locales/`: подписи, кнопки, подсказки, заголовки,
  названия этапов, шагов и состояний, сообщения об ошибках. Компонент берёт текст по ключу — `t('screen.home')`;
  строки интерфейса прямо в компоненте нет. `ui/` получает тексты пропами, `components/` и `features/` берут их
  через `useI18n()`.
- **Языки сейчас — русский и английский.** Язык добавляется одним файлом словаря и строкой в списке языков, без
  правки компонентов.
- **Русские тексты — дословно из макета.** Английские пишешь сам. Один термин переводится одинаково везде: список
  терминов — в `frontend/README.md`; встретился новый термин — допиши его туда.
- **Формы числа, даты и время — через словарь и правила языка**, а не склейкой строк: «1 фрагмент», «2 фрагмента»,
  «5 фрагментов» / «1 fragment», «2 fragments» — один ключ с формами числа; даты — `formatDate`. Фразу не собирай
  из кусков: в другом языке порядок слов другой. Целая фраза — один ключ с подстановками `{имя}`.
- **Набор ключей во всех языках одинаковый.** Нехватка ключа, лишний ключ или не та подстановка ломают `typecheck`,
  а не всплывают на экране.
- **Вёрстка не рассчитывает на длину русского текста:** в других языках подписи длиннее. Не задавай ширину под
  русскую подпись; длинное переносится или обрезается многоточием.
- **Не переводится то, что приходит из данных:** названия советов, проектов и групп, текст ввода, фрагменты,
  вопросы, варианты, решения, итоги, задачи — всё, что написали человек и модели; имена моделей.
- **Ошибки сервера** интерфейс показывает по `code` текстом из словаря (`errorKey`), а не `message` из ответа.

## Контракт

`docs/api-contract.md` пишется от макета: что экран показывает и что на нём делают — то бекенд и должен уметь.

- Раздел «Решения» — ответы владельца на вопросы, дословно, с номером вопроса.
- Для каждой ручки: метод, путь, тело, ответ с примером JSON, ошибки с кодом, какие экраны её зовут.
- **Сначала ищи, что уже есть в контракте.** Нужные данные уже отдаёт существующая ручка — используй её или добавь
  в её ответ поле, а не заводи вторую ручку про то же самое. Коды ошибок тоже переиспользуй.
- Ручка — про один ресурс или одно действие; путь называет сущность, а не экран. Чтение и действие — разные ручки;
  действие отвечает изменённым объектом. Один и тот же объект везде приходит в одном формате.
- И сразу то же в коде: типы, интерфейс источника, моки, http, хуки запросов.

## Вопросы

Если без решения владельца дальше нельзя — не придумывай. Допиши вопрос в файл вопросов (путь назван в задании)
и закончи работу: всё, что уже сделано, закоммить и запушь, PR не открывай.

```json
{ "id": "q-001", "task": "i1", "question": "…", "context": "…",
  "options": ["…", "…"], "recommended": 1, "answer": null, "answered_at": null }
```

- `id` — следующий свободный номер в файле; `task` — id задачи, он назван в задании.
- Вопрос читают с телефона в Telegram: коротко, простыми словами, без ссылок на код, который надо открыть.
- `context` — 1–2 предложения: зачем это нужно экрану.
- 2–4 варианта; `recommended` — номер рекомендованного (с 1) или `null`.

Когда ответ пришёл (`answer` заполнен), перенеси его в «Решения» контракта дословно, с номером вопроса.

## Проверки

Перед каждым коммитом: `npm --prefix frontend run typecheck` и `npm --prefix frontend run build`. Оба должны пройти.
После пуша их же прогонит CI на GitHub, и цикл не вольёт PR без зелёного CI.

## Git

- Работаешь в ветке, которую назвал цикл. В `main` не коммить, не вливай, `--force` не используй.
- Сообщения коммитов — по-русски, по делу.
- Первый раз: коммит, `git push -u origin <ветка>`, `gh pr create --base main` с описанием по-русски:
  - твой план задачи;
  - что сделано;
  - **Компоненты:** что взято готовым, чему добавлен вариант, что добавлено новым и почему готовое не подошло;
  - что добавлено в контракт;
  - чем экран отличается от макета и почему;
  - строка `Closes #<issue>`.
- В индекс добавляй только свои файлы, не `git add -A`. `design/.src/` и `design/.shots/` в коммиты не попадают.
- `@codex review` не пиши — это делает цикл.

## Замечания Codex

Сначала оцени каждое замечание, потом действуй. Codex тоже ошибается: не применяй замечание только потому, что оно
пришло.

1. Прочитай замечание и код, о котором оно. Реально ли там проблема? Не ломает ли правка правила этого файла,
   макет или «Решения»?
2. Реши одно из трёх:
   - **применить** — проблема есть, правка в рамках твоих решений;
   - **вопрос владельцу** — правка требует того, чего нет в макете: новой сущности, состояния, правила;
   - **не применять** — проблемы нет или правка сделает хуже.
3. **Ответь в ветке каждого замечания**, одним-двумя предложениями: что сделано или почему не применено.
4. **Закрой ветки обработанных замечаний** (применённых и отклонённых; ушедшие в вопрос — нет). Id веток:

   ```
   gh api graphql -f query='query { repository(owner: "RusselSand", name: "council-dev") { pullRequest(number: <PR>) {
     reviewThreads(first: 100) { nodes { id isResolved comments(first: 1) { nodes { databaseId } } } } } } }'
   ```

   закрыть: `gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "<id>"}) { thread { isResolved } } }'`
