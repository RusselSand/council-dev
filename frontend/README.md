# Фронтенд Совета

React 18, TypeScript, Vite. Экраны собираются по макету `design/Совет - прототип.html`, данные — с настоящего сервера
(`backend/`) или из моков. Что сервер умеет — `docs/api-contract.md`. Правила работы — `CLAUDE.md` в корне; как
поставить и запустить всё приложение — `README.md` в корне.

## Запуск

Нужен Node.js 20.19 или новее. Команды — из корня репозитория:

```
npm --prefix frontend install
npm --prefix frontend run dev          # http://localhost:5420, запросы /api — на бекенд, localhost:8420
npm --prefix frontend run dev:mock     # то же на моках, без бекенда
npm --prefix frontend run typecheck    # проверка типов, в том числе словарей
npm --prefix frontend run build        # typecheck + сборка в frontend/dist
npm --prefix frontend run proto        # распаковать код макета в design/.src/
npm --prefix frontend run shot -- …    # снимки макета и нашего экрана, см. «Сверка с макетом»
```

### Настройки

Настройки — переменные окружения или файл `frontend/.env` (образец — `frontend/.env.example`, сам `.env` в git не
попадает).

| Переменная         | Что                                                                       | По умолчанию            |
| ------------------ | ------------------------------------------------------------------------- | ----------------------- |
| `VITE_DATA_SOURCE` | откуда брать данные: `http` — настоящий сервер, `mock` — моки из макета    | `http`                  |
| `VITE_API_URL`     | адрес API для `http`                                                      | `/api`                  |
| `VITE_API_PROXY`   | куда `dev` передаёт запросы `/api`: бекенд                                | `http://localhost:8420` |
| `VITE_USE_POLLING` | `1` — `dev` опрашивает файлы, а не ждёт событий (докер на Windows)        | —                       |

Собранный фронт (`build`) ходит в настоящий сервер: его отдаёт сам бекенд, и `/api` — на том же адресе. Моки — для
разработки экранов (`dev:mock` — режим `mock`, `frontend/.env.mock`) и снимков (`shot` всегда на моках).

## Устройство

```
src/
  main.tsx          вход: шрифты, токены, общие стили, <App />
  app/              приложение целиком: язык интерфейса, экран по адресу
  ui/               то, что не знает про совет: кнопка, поле, переключатель; тексты получает пропами
  components/       знает про советы, проекты, этапы и потоки, но не привязано к одному экрану
  features/<экран>/ экран: useX.ts (данные и действия, без JSX), X.tsx, parts/, стили, index.tsx
  router/           адреса: разбор пути, переходы, ссылка
  data/             слой данных: интерфейс источника, моки, http, хуки запросов
  domain/           типы и расчёты без React
  i18n/             тексты интерфейса: словари, t(), даты и числа
  styles/           токены, шрифты, общие стили страницы
```

Зависимости — сверху вниз: `app` → `features` → `components` → `ui`. `ui/` не импортирует `components/` и `features/`,
`components/` не импортирует `features/`. `router/`, `data/`, `domain/`, `i18n/` может брать кто угодно, кроме `ui/`
(ему нужны только `styles/`).

Стили компонента — CSS-модуль рядом с ним (`X.module.css`), значения — только из токенов (см. «Токены»).

Каждый экран стоит в рамке `features/frame`: меню слева (разделы, советы по проектам, «Модели совета» с меткой
«судья» у судьи открытого совета) и шапка страницы (путь, заголовок, у совета — строка «проект · судья · модели ·
когда менялся», кнопки справа). Рамку ставит `app/App.tsx`, экран под шапкой выбирает `app/Screen.tsx`.
Свои переключатели в шапке (у Сводки — «Канбан / Список») экран ставит через `<PageTools>` из `ui/PageTools`: рамка
держит для них место между заголовком и кнопками.

Экраны: `features/home` — Сводка, `features/projects` — Проекты, `features/council` — совет, `features/brief` — его
этап «Ввод», `features/slices` — этап «Нарезка», `features/structure` — этап «Группы», `features/research` — этап
«Исследование», `features/stream` — шаг потока (общее для всех шагов), `features/projectDecisions` — шаг «Решения
проекта», `features/questions` — шаг «Вопросы», `features/options` — шаг «Варианты», `features/decisions` — шаг
«Решения», `features/outcomes` — шаг «Итоги», `features/notes` — шаг «Документация», `features/tasks` — этап
«Задачи».

Экран совета (`features/council`, `<Council route>`) — общий для всех этапов и шагов потока: под шапкой рамки вкладки
шести этапов, под ними — этап, который `app/Screen.tsx` выбирает по адресу и получает совет из списка
(`{(council) => …}`). Совета с таким id нет — Сводка.

«Ввод» (`features/brief`) сохраняет всё сам, кнопки «Сохранить» нет: текст и название — после паузы в наборе
(`useAutosave()` из `data/`), проект, модели и судья — сразу по щелчку (`useCouncilEdit()` рядом с экраном, по хуку
на поле: запросы по одному, с последним выбором, у каждого поля своя ошибка; `settle()` — дождаться ответа).
«Нарезать →» сначала сохраняет всё несохранённое (`flush()`, `settle()`) и, пока нарезка запускается, не даёт править
«Ввод»; ушли с «Ввода» за это время — «Нарезка» не открывается. Поля и действия — `useBriefForm()`; экран ставится
с `key={council.id}`, чтобы другой совет начинал «Ввод» заново. Закрытый «Ввод» передаёт свои запросы, которые ещё
идут (сохранения, запуск нарезки), в `holdBrief()` из `data/`: открытый снова «Ввод» того же совета запросит текст
после ответа на них. Текст и название, которые так и не сохранились, закрытый «Ввод» запоминает
(`features/brief/drafts.ts`), а открытый снова — показывает и сохраняет снова.

«Нарезка» (`features/slices`) — два вида по `stages.slices` совета, как в макете: модели режут текст — «ИИ работает»
и «Ход работы» (`components/RunningStage`, `components/RunProgress`); нет — фрагменты с типами и «Дальше»
(`parts/FragmentList`, `parts/FragmentCard`). Нарезку даёт `useCouncilSlicing(id, running)` из `data/`: пока нарезка
идёт, она и список советов перезапрашиваются через 5 с после ответа на нарезку (`poll()`); нарезка началась или
кончилась — до ответа на новый запрос нарезки нет (`data` — `undefined`). Тип фрагмента сохраняется сразу по щелчку —
`useFragmentLabels(id, running)`: у каждого фрагмента своя очередь запросов и своя ошибка, `settle()` — дождаться
ответа; нарезка началась или кончилась — смены и ошибки прежних фрагментов забываются.
«Предложить группы →» сначала дожидается смен типа, потом запускает раскладку (`useStartStructure()`) и открывает
«Группы»; пока она запускается, типы не меняются. Строки «Хода работы» из частей работы моделей — `progressRows()`
в `domain/run.ts`.

«Группы» (`features/structure`) — так же по `stages.structure`: модели раскладывают фрагменты — «ИИ работает» и «Ход
работы» (те же `RunningStage` и `RunProgress`); нет — «ИИ предлагает N групп», карточки групп
(`parts/GroupGrid`, `parts/GroupCard`: `GroupTitle`, `GroupIdea`, `GroupFragments`, `GroupActions`, `MergePanel`,
`SplitPanel`) и тёмная плашка «Подтвердить группы»; раскладка остановилась — над ними `components/FailedBanner` с
«Запустить снова». Раскладку даёт `useCouncilStructure(id, running)` — с тем же опросом, что у нарезки (`useStageQuery()`).
Правки групп — `useGroupEdits(id, running)`: все запросы групп по одному, в порядке действий человека; название и идея
видны сразу (`pending`), объединение и разделение — после ответа (`reshaping` — ждут ответа), ошибка — у группы
(`errors`), `settle()` — дождаться ответа на все правки, которые идут. Что открыто на карточке (поле названия,
«Объединить с», «Разделить»), отметки фрагментов и идеи, которые ещё набирают (уходят после паузы 0,6 с и при закрытии
экрана), — в `useStructure()` рядом с экраном. «Подтвердить →» сначала отправляет набранное и дожидается правок, потом
подтверждает группы (`useConfirmStructure()`) и открывает «Исследование»; «Запустить снова» так же сначала дожидается
правок, потом запускает раскладку (`useRetryStructure()`). Пока группы подтверждаются или раскладка запускается снова,
правки групп и обе кнопки не действуют.

«Исследование» (`features/research`) ведёт себя по исследованию совета, а не по `stages.research`; по нему — только
«уже утверждено» и опрос, а по `stages.structure` — подтверждены ли группы: до этого «К потокам →» недоступна
(решение q-002). Недоступна она и пока у группы нет идеи (`withoutIdea()` из `domain/structure.ts`, решение q-002
бекенда): тогда раскладка опрашивается — `useCouncilStructure(id, running, awaitsIdeas)`, — и ИИ найдёт идею —
кнопка станет доступна. Опрос: пока этап в списке советов `running`, исследование и список опрашиваются, даже если
исследование уже кончилось, — так список догоняет его (`useCouncilResearch(id, running)`). Два блока рядом —
код (`parts/CodeBlock`) и макет (`parts/DesignBlock`) — на общем `parts/ResearchBlock`, который по состоянию блока
показывает настройку, работу моделей (`parts/RunList`), результат (`parts/ResultLine`) или «пропущено»
(`parts/SkippedNote`) и свои кнопки. Исследование остановилось (`stopReason` не `null`) — над настройкой красная
`ui/Callout` «Остановилось» и под ней причина: сервер шлёт код, текст — из словаря (`research.stopReason.*`).
Отметки репозиториев и ссылка на Figma живут в `useResearch()` рядом с экраном и
уходят на сервер с «Начать исследование»; блок сменил состояние — снова как на сервере. Действия с блоком —
`useResearchAction()`, по экземпляру на блок: у каждого своё «ждёт ответа» и своя ошибка. Есть находки — «Что пойдёт
в потоки» (`parts/Findings`, `parts/FindingCard`, `parts/ConflictSides`): фильтр — на экране, группы — из раскладки
(`useCouncilStructure()`), решение по находке сохраняется сразу (`useFindingDecisions()`). Код исследован — сценарии
(`parts/CodeFlows`) и покрытие (`parts/CoverageList`). «К потокам →» дожидается решений, потом утверждает исследование
(`useApproveResearch()`) и открывает первый поток; уже утверждено — просто открывает его. Расчёты — что будет
с находкой, какие у неё кнопки, можно ли начать и утвердить — `domain/research.ts`.

Шаг потока (`features/stream`, `<Stream council route>`) — общий для всех шагов, как совет для этапов: под вкладками
этапов — вкладки потоков (`parts/StreamTabs`), слева цепочка шагов (`parts/StepChain`), плашка состояния открытого шага
с «Запустить снова» (`parts/StepBanner`) и «Ход работы» (`parts/RunPanel`) вида «grouped» (`parts/RunGroups`: у шага с
ошибкой, у шага, где работают модели, и у «Вариантов» — всегда, как в макете), справа — карточка шага (`ui/TitledCard`:
подпись капсом, название, пояснение). Пока у «Решений» идут пересчёты решений (`rechecks` у шага), «Ход работы» —
«пересчёт»: по строке на вопрос «Q5 · судья · 0:42», щелчок раскрывает под строкой его ход (`parts/RecheckRuns` на
`parts/RunGroups`), сначала раскрыт пересчёт решения, открытого на «Решениях»; плашка «Решений», которые ждут вас, —
«ИИ работает» и какие вопросы пересчитывают, а не «Ход за вами». Внутри карточки —
шаг, который `app/Screen.tsx` выбирает по адресу и получает поток, все потоки совета и шаг (`{({ stream, streams, step,
retrying, onBusy, onFocus }) => …}`); шаг не начат — «Шаг откроется, когда пройдены предыдущие.» вместо него. «Запустить снова»
называет открытый шаг (`useRetryStream()` — совет, поток и шаг): шагов с ошибкой у потока бывает два. «Запустить снова»
и переход или правки шага не уходят вместе: пока запуск ждёт ответа (`retrying`), переход и правки шага не действуют;
пока переход или правка ждёт ответа, шаг сообщает об этом (`onBusy(true)`), и «Запустить снова» не действует. Какое
решение открыто, «Решения» сообщают `onFocus(id)`. Потоки даёт `useCouncilStreams(id, running)` из `data/`: пока на шаге
работают модели или идут пересчёты решений, потоки и список советов опрашиваются (`useModelsPoll()`). Потока из адреса
нет — открывается первый поток на его текущем шаге. Расчёты — текущий шаг и состояние потока, когда показывать «Ход
работы», состояние части шага, какая часть идёт и кто в ней работает, «думает 0:12» — `domain/stream.ts`.
Переходы шага — внизу карточки (`ui/CardFooter`), у каждого шага свои.

«Решения проекта» (`features/projectDecisions`) — идея потока на жёлтой плашке (`ui/Highlight`); шаг готов — что учтено
(`taken`) и «Изменить отбор» (`parts/SelectionSummary`); ждёт вас или отбор открыт — невыгруженные потоки, строка
каталога с поиском прошлых решений (`parts/CatalogLine`: «Искать прошлые решения» / «Искать заново» —
`useSearchProjectDecisions()`, и «Каталог изменился: …», если каталог изменился после поиска), прошлые решения с
галочками (`parts/DecisionCard` на `CheckTile variant="card"`) и два перехода к вопросам. Галочки живут
в `useProjectDecisionsStep()` рядом с экраном до перехода, поиск заново их не сбрасывает; переход —
`useApproveProjectDecisions()`, потом открываются «Вопросы» потока. Экран ставится с `key` по совету и потоку.

«Вопросы» (`features/questions`) — вопросы строками (`parts/QuestionRow`: id, текст, откуда и «почему», справа «Убрать» /
«Вернуть»), на строке — «Пересматривает решение проекта» (`parts/RevisitNote`) и «В тексте уже есть ответ»
(`parts/AnswerNote`), обе на `ui/Callout`; под вопросами — «Свой вопрос…» и «Добавить» (`parts/OwnQuestion`); шаг ждёт
вас или остановился — внизу «Утвердить вопросы → к вариантам». Пока на шаге работают модели — серые строки
(`ui/Skeleton`). Вопросы даёт `useStreamQuestions(id, streamId, state)`: шаг сменил состояние — вопросы
перезапрашиваются, а до ответа их нет. «Убрать» / «Вернуть» уходят сразу (`useQuestionRemovals()` на `useQueuedSaves()`),
свой вопрос — по «Добавить» (`useAddQuestion()`: повтор с тем же текстом, без пробелов по краям, — с прежним
Idempotency-Key, текст поправили — с новым), «Утвердить» сначала дожидается «Убрать» / «Вернуть», потом
утверждает (`useApproveQuestions()`) и открывает «Варианты». Поле и действия — `useQuestionsStep()` рядом с экраном;
когда вопросы правят и утверждают — `domain/questions.ts` (на общих `stepEditable()` и `stepApprovable()` из
`domain/stream.ts`). Экран ставится с `key` по совету и потоку.

«Варианты» (`features/options`) — вопросы по одному: чипы вопросов, «готово 2 из 4», «←» / «→»
(`components/QuestionNav`), вопрос (`components/QuestionHead`), у вопроса в круге зависимостей — жёлтая строка «Круг
зависимостей: Q1 и Q2 зависят друг от друга.» (`components/DependencyLoop` по `cycle`), у вопроса, чей выбор не тот,
что проверили на «Решениях», — жёлтая строка «Новый выбор ещё не проверен — пересчитайте его на «Решениях».»
(`ui/NoteLine` по `unchecked` с сервера), серая плашка «Выбор за вами ·
судья …» с отброшенными (`parts/JudgeNote`), варианты
карточками с кружком выбора (`parts/OptionCard` на `ui/RadioCard`: «почему», «цена», «зависит от Q2 · решён»,
«Поправить» → `parts/OptionEditor`, «Удалить»), «Свой вариант» (`parts/OwnOption`) и «Пока не решаю» (`RadioCard
variant="dashed"`); шаг ждёт вас или остановился — внизу «Выбрано 2 из 4» и «Утвердить выбор → к решениям». Пока на шаге
работают модели — серые строки. Вопросы идут так, как их прислал сервер, — по «зависит от» вариантов (порядок и круги
считает сервер, экран их не пересчитывает); по этому же порядку ходят «←» / «→». Открывается первый вопрос без выбора,
а когда сюда пришли по «Поправить в «Вариантах»»
с «Решений», — тот вопрос (`navigationFocus()` из `router/`; в другом наборе вариантов — снова первый без выбора).
Варианты даёт `useStreamOptions(id, streamId, state)`, как вопросы — по состоянию шага;
в ответе — `run`, номер запуска шага. Набор вариантов (`round` у выбора, поля и правки) — состояние шага и `run`: шаг
запустили снова в другой вкладке, и он успел кончиться, пока экран этого не видел, — состояние то же, а варианты другие.
Чтобы экран это увидел, варианты опрашиваются вместе с потоками (`useCouncilStreams()` передаёт `useModelsPoll()` тему
`options`). Набор другой — открывается его первый вопрос без выбора. Выбор, свой вариант, правка и «Утвердить» уходят
с `run` вариантов на экране (у поля и правки — с тем, что был, когда их открыли): шаг с тех пор запустили снова — сервер
их не примет (`options_not_ready`), и выбор из прежних вариантов не встанет в новые с теми же id.
Выбор уходит сразу по щелчку (`useOptionChoices()` на `useQueuedSaves()`); выборы одного вопроса уходят по одному и
между экранами (`writeChoice()`): ушли с экрана, пока выбор уходил, вернулись и выбрали другое — новый не обгонит прежний.
Очереди выбора — у каждого запуска шага свои (`lane` у `useQueuedSaves()`, `run` в ключе `writeChoice()`): выбор в
новом запуске не ждёт ответа на тот, что ещё идёт в прежнем, — его сервер всё равно не примет. Так же и с остальным:
очередь сохранений поля «Свой вариант», правка, которая уходит (`saving`), и «Утвердить», который ждёт ответа
(`approving`), — у каждого набора вариантов свои; то, что ещё идёт в прежнем, новый набор не запирает и не держит
«Утвердить» и «Запустить снова», а его ответ не отпускает то, что ушло в новом. Поле «Свой вариант» — `useOwnOption()` рядом
с экраном: набранное уходит после паузы, сначала создаёт свой вариант (`useAddOption()`), дальше правит его
(`useUpdateOption()`), и экран выбирает его; пока поле открыто, созданный вариант — в нём, а не карточкой (и тот, что
нашёлся по ключу поля, когда поправить его не вышло). Кружок поля выбран, только когда в поле набрано то, чего на
сервере ещё нет (`unsaved`), или его вариант уже выбран: пустое поле выбор не меняет, а сохранился вариант, но выбрать
его не вышло, — выбран прежний выбор, и щелчок по кружку выбирает вариант снова. Стёрли поле, из которого вариант уже
создан, — у поля ошибка `text_required`, сохранение не вышло. Набор вариантов другой — у `useOwnOption()` и
`useOptionEditor()` свой `round` (`useRound()`), как у выбора: поля и правка прежних вариантов забываются, а ответ на
то, что из них ещё уходило, в варианты не встаёт (`fresh` у `useAddOption()` и `useUpdateOption()`, как у
`useQueuedSaves()`), и найденный по ключу вариант прежних вариантов не правится. Ответ на выбор, свой вариант и правку
встаёт в варианты, только если у них тот же `run`, с которым ушёл запрос (`putSet()`, `putOption()`): и с экрана,
который уже закрыли, ответ про прежний запуск не встанет в варианты нового. Вопроса больше нет в вариантах (убрали
на «Вопросах», а шаг тот же) — его поле и правка забываются так же (`sets` у обоих хуков). Поля
хранятся по вопросу: ушли от вопроса, а набранное не сохранилось, — поле ждёт у своего вопроса с ошибкой. Закрыли
экран, а набранное не сохранилось, — поле ждёт «Варианты» потока, открытые снова (`leftFields` в `useOwnOption.ts` на
`leftovers()` из `features/options/leftovers.ts`, общее для всех экранов, как номера выбора): там оно у своего вопроса
с набранным и ошибкой, если набор вариантов тот же и вопрос не убрали; номера полей общие для всех экранов, и поле
пробует с прежним ключом. Правка —
`useOptionEditor()`: у варианта совета создаёт свой вариант на его основе, у своего — правит его, и выбирает
сохранённое; вариант, который правка нашла по своему ключу, а поправить не вышло (`created`), — в правке, а не
карточкой, пока её не сохранят или не закроют. Стёрли текст правки — «Сохранить» не шлёт запрос, у правки ошибка
`text_required`, и `settle()` — не всё сохранилось. Правка, которую не вышло сохранить, когда экран закрыли (и та, что
уходила, когда закрыли, и не сохранилась), ждёт «Варианты» потока, открытые снова (`leftEdits`, тоже на
`leftovers()`): там она ждёт своего вопроса (`current`) и открывается, когда он на экране и другой правки нет, с
набранным, ошибкой и прежним полем (`field` — ключ создания тот же); пока ждёт — `settle()` не всё сохранилось. Выбрали у вопроса другое (вариант, «Пока не решаю», «Свой вариант», ушедшая правка), пока поле или правка
сохранялись, — сохранённое не выбирается, выбор за последним щелчком: каждый выбор берёт у вопроса номер
(`claimChoice()` из `features/options/choiceClaims.ts`), и поле или правка выбирают сохранённое, только если их номер
ещё последний (`holdsChoice()`). Поле «Свой вариант» берёт номер, когда в нём начали писать (или сразу, если в нём уже
есть текст или созданный вариант), а не когда его открыли: пустое поле выбор не меняет, и правка, которая ещё уходит,
остаётся выбором. Номер у поля один: открыли снова поле, за которым выбор и так, — номер прежний; выбор с тех пор
забрали — прежний номер отпускается, и поле берёт новый. Всё стёрли, а из поля ничего не создано и не уходит, — номер отпускается (`releaseChoice()`), и
выбор снова за тем, кто выбирал до поля: поле и правка выбирают сохранённое через `applyChoice()`, и то, что уже
сохранилось, пока в поле писали, становится выбором, как только номер поля отпустили. Так же — правка, которую не
вышло сохранить: её номер (`claim`) — у неё, пока её не сохранят снова (номер прежний, если выбор всё ещё за ней) или
не закроют без сохранения («Отмена», уход к другому вопросу, другая правка) — тогда он отпускается. Номера общие для всех экранов «Варианты»: ушли с экрана, пока поле или правка
сохранялись, вернулись и выбрали другое — сохранённое тоже не выбирается. Правки одного варианта
не обгоняют друг друга: пока правка уходит — и с экрана, который закрыли, пока она уходила, — «Поправить» не действует
(`locked`, `start()` её не открывает), а вариант, который ещё
сохраняется из поля «Свой вариант» (`saves()`: и когда поле уже закрыто, а вариант стоит карточкой), не правится, пока
не сохранится, — и на экране, открытом снова: сохранения из полей общие для всех экранов (`writes` в `useOwnOption.ts`).
Выбор, поле и правка, которые ещё уходят, — в `features/options/pendingWrites.ts`, общем для всех экранов, по совету,
потоку и запуску шага: `trackWrite()` ставит запись, как только её начали (выбор — по щелчку, а не когда до него дошла
очередь), `settleWrites()` ждёт, пока в запуске шага не останется ни одной, — и тех, что ушли по ответу на прежние
(сохранённое стало выбором); у выборов вопроса ответ — по последнему из них (`question` у `trackWrite()`): прежний не
сохранился, а выбранный после него сохранился — сохранено; `useWriting()` — уходит ли правка. Выбор ставит
`trackChoice()`: не сохранился, а после него у вопроса не выбирали, — он там же держится, пока у вопроса не выберут
снова (`failedChoicesOf()`, `useFailedChoices()`; ошибку берёт `errorOf()` у `useQueuedSaves()` — и с закрытого экрана):
его ошибка — у вопроса и на экране, открытом снова, а «Утвердить» не утверждает (`not_saved`). Пока выбор утверждается или шаг запускают снова, к другому вопросу не уйти (`navLocked`): уход отправил
бы набранное в поле «Свой вариант» вместе с ними; пока правка уходит — тоже: уход закрыл бы её, и ошибку было бы не
видно, а «Утвердить» утвердил бы без неё. Открытый вопрос, плашка,
правка и «Утвердить» — `useOptionsStep()`: открывается первый вопрос без выбора; «Утвердить» сначала дожидается того,
что уходит в этом запуске шага и с экранов, которые закрыли (`settleWrites()`: поле и правка оттуда, которые не
сохранились, встают здесь у своих вопросов), потом сохраняет поля
(и те, где не вышло) и дожидается правки и выбора, потом утверждает (`useApproveOptions()`) и открывает «Решения»;
что-то не сохранилось (и правка открыта с ошибкой или с набранным, которое не сохраняли, пока её не сохранят или не
закроют) — под кнопкой ошибка
`not_saved`. Ошибка у каждого поля «Свой вариант» и у правки своя (`attempt()`), а не последняя ошибка хука.
«Удалить» у варианта — `useOptionDeletion()`, как удаление проекта на «Проектах»: первое нажатие — «Да, удалить»
(`Button variant="link" tone="danger"`), второе удаляет (`useDeleteOption()`: ответ `204`, вариант сразу уходит из
вариантов вопроса, если набор тот же, — `dropOption()`; `not_found` — тоже удалён); ушли к другому вопросу или набор
вариантов другой — вопрос снят. Выбранный вариант (и тот, выбор которого уходит) не удаляют — «Удалить» недоступна с
пояснением; пока выбор вопроса уходит, правка уходит или вариант сохраняется из поля, — тоже недоступна; пока вариант
удаляется, «Удалить» у всех вариантов, «Утвердить» и «Запустить снова» не действуют, а сам вариант не выбрать и не
поправить. Расчёты — сколько выбрано, состояние зависимости, какой
вопрос открыть — `domain/options.ts`. Экран ставится с `key` по совету и потоку.

«Решения» (`features/decisions`) — решения по одному, как «Варианты»: чипы вопросов (точка: зафиксировано — зелёная,
противоречие — красная, иначе жёлтая; выбор поменяли на «Вариантах» — жёлтая и при противоречии), «готово 1 из 4», «←» /
«→» (`components/QuestionNav`) — в порядке, как прислал
сервер (по «зависит от» проверки); вопрос с меткой решения справа (`components/QuestionHead`), «Ваш выбор» и, у решения
в круге зависимостей, «Круг зависимостей: …» (`components/DependencyLoop`); красная плашка проблемы с «Поправить в «Вариантах»» (`parts/ProblemNote`:
открывает «Варианты» на этом вопросе — `navigate(path, { focus })`); «Судья: …» (`parts/JudgeLine`); решение (ADR) на
`ui/Panel` — контекст, решение, «почему» (`TextArea variant="outlined"`) и кто его написал, в контексте, последствия
(`parts/AdrCard` на `ui/Facts size="md"`); ряд «Решение: P12 · Оставить открытым · Зафиксировать →»
(`parts/DecisionActions` на `Chip shape="box"`); шаг ждёт вас или остановился — внизу «Зафиксировать решения → к
итогам». Пока на шаге работают модели — серые строки. Решения даёт `useStreamDecisions(id, streamId, state)`, как
варианты — по состоянию шага, с `run` и опросом вместе с потоками (тема `decisions`). Правки — `useDecisionEdits(id,
streamId, run)`: правка решения шлёт «почему», где решение и отметки замен целиком (`DecisionEdit`); у каждого вопроса своя очередь, и
уходит последнее, что сделал человек. Очереди, набранное «почему», правки, которые уходят, и ошибки — общие для всех
экранов «Решения» и у каждого запуска шага свои (`lanes` в `data/hooks/useDecisions.ts`): ушли с экрана, пока правка
уходила, — новая не обгонит её; набранное, которое не сохранилось, ждёт на экране, открытом снова, с ошибкой. «почему»
уходит после паузы в наборе (0,6 с), при уходе к другому решению и с экрана; зафиксированное без «почему» не
сохраняется — набранное ждёт. «Зафиксировать →» дожидается ответа и открывает следующее незафиксированное решение;
«Оставить открытым» и щелчок по варианту у открытого — сразу. «Зафиксировать решения» отправляет набранное, дожидается
правок (`settle()`, и с экранов, которые закрыли), что-то не сохранилось — `not_saved` и открывается решение, где не
сохранилось; иначе фиксирует (`useApproveDecisions()`) и открывает «Итоги». У противоречия с решением проекта (`kind` —
`decision`), пока шаг ждёт вас или остановился, в последствиях — отметка «Это решение заменяет ADR-0003» (`Button
tone="danger"` с `aria-pressed` в строке `parts/AdrCard`: отмечена — `variant="primary"`, нет — `outline`): она уходит
правкой решения (`replaces` в `DecisionEdit`), моделей не зовёт; отмеченные замены — серыми строками «Заменяет ADR-0003:
…». «Пересчитать» — на красной плашке рядом с «Поправить в «Вариантах»» (`parts/ProblemNote`, `Button variant="outline"`;
в макете на её месте «Перепроверить»), доступна, когда `recheck` решения — `ready` или `failed`: сначала отправляет
набранное и дожидается правок (`flush()` в `useDecisionsStep()`), потом уходит (`useRecheckDecision()`) — решение из
ответа встаёт на место прежнего. Пока решение пересчитывают (`recheck` — `running`), оно занято, под кнопками — «ИИ
пересчитывает это решение…», решения опрашиваются (`useModelsPoll()` в `useStreamDecisions()`), ход пересчёта — в «Ходе
работы» экрана потока, а «Зафиксировать
решения» недоступна — слева от неё пояснение (`lead` у `CardFooter`); остальные решения правят. Пересчитать есть что не
только из-за отметок: выбор вопроса поменяли на готовых «Вариантах» (`unchecked` у решения — его не фиксируют:
«Зафиксировать →» и «Зафиксировать решения» недоступны, слева от последней — «Выбор поменяли на «Вариантах» —
пересчитайте Q5…»; почему — строкой под кнопками на красной плашке) или проверка опиралась на прежний выбор других
вопросов (`stale`): над «Проблемой» — по строке на вопрос «Проверка шла с Q5: P7, а сейчас у Q5 выбран P58 —
пересчитайте, проблема может уйти.». У решения без проблемы всё это — на жёлтой плашке с «Пересчитать»
(`parts/RecheckNote`; в макете её нет). Поле и
действия — `useDecisionsStep()` рядом с экраном; расчёты — точка решения, первое и следующее незафиксированное, есть
ли «почему», доступна ли «Пересчитать» и почему (`recheckReason()`) — `domain/decisions.ts`. Экран ставится с `key` по
совету и потоку.

«Итоги» (`features/outcomes`) — итоги по одному, как «Решения»: чипы итогов с номером моноширинным (`components/QuestionNav`
с `labels` про итоги и `mono`; точка: утверждён — зелёная, заблокирован — красная, иначе жёлтая), «утверждено 2 из 3»,
«←» / «→»; итог — серый блок (`parts/OutcomeCard` на `Panel variant="muted"`): номер (в каталоге, а не выгружен — в
потоке), название и метка «готов к разработке» / «есть пробелы» / «заблокирован Q4» (`components/QuestionHead
size="md"`), что меняется, белый блок «Готово, когда · 4» с пустыми квадратиками (`parts/DoneWhen`), решения, которые итог
реализует, — «ADR-0046 — что меняет» (`Facts size="xs"`), внизу мелко «опирается на … · ограничения: F3» (у решений нет
пояснений — «решения: ADR-0007, ADR-0008») и кнопка итога: «Утвердить → дальше», «Утверждён · дальше →» или серая
«Пропустить · дальше →» у заблокированного (`Button tone="muted"`). Шаг ждёт вас или остановился — внизу «Утвердить итоги
→ к документации». Пока на шаге работают модели — серые строки. Итоги даёт `useStreamOutcomes(id, streamId, state)`, как
решения — по состоянию шага, с `run` и опросом вместе с потоками (тема `outcomes`). «Утвердить → дальше» уходит сразу
(`useOutcomeApprovals()`; утверждения и их ошибки общие для «Итогов» одного запуска шага, как правки решений),
дожидается ответа и открывает следующий итог; заблокированный не утверждают. «Утвердить итоги» снова отправляет
утверждения, которые не вышли, и дожидается тех, что ещё уходят, — и с экрана, который закрыли раньше ответа; не
утвердилось — `not_saved` и открывается этот итог; иначе утверждает (`useApproveOutcomes()`) и открывает «Документацию».
Открытый итог и действия — `useOutcomesStep()` рядом с экраном; расчёты — метка и точка итога, первый и следующий итог,
можно ли утвердить — `domain/outcomes.ts`. Экран ставится с `key` по совету и потоку.

## Адреса

Адреса — как в макете, только без `#`. Разбор и сборка пути — `router/routes.ts`.

| Адрес                              | Экран                                  |
| ---------------------------------- | -------------------------------------- |
| `/home`                            | Сводка                                 |
| `/projects`                        | Проекты                                |
| `/c/<совет>/<этап>`                | этап совета: `brief`, `slices`, `structure`, `research`, `tasks` |
| `/c/<совет>/streams/<поток>/<шаг>` | шаг потока: `project`, `questions`, `options`, `decisions`, `outcomes`, `notes` |

`/` и незнакомый адрес ведут на `/home` — как в макете. Текущий адрес — `useRoute()`, путь для адреса —
`routePath({ screen: 'step', council: 'g1', stream: 'A', step: 'options' })`, переход — `navigate(path)` или
`<Link to={path}>`. Что открыть на экране, куда ведёт переход («Поправить в «Вариантах»» — вопрос), —
`navigate(path, { focus: 'Q4' })`: адрес тот же, а `focus` лежит в записи истории, его читает `navigationFocus()`. Куда ведёт совет из списка (этап, где он сейчас; на «Потоках» — первый поток на его текущем
шаге) — `councilRoute(council)`.

## Слой данных

Экран не ходит в `fetch` сам — только через хуки из `data/`.

- `data/source.ts` — интерфейс источника `DataSource`: по методу на ручку контракта.
- `data/mock/` — моки. Совет `g1`, его нарезка, группы, исследование, поток, вопросы, варианты, решения, итоги и
  заметки — из `data-1.json` макета, остальные советы, их фрагменты, группы, находки, потоки, прошлые решения, вопросы,
  варианты, решения, итоги, заметки и проекты — из `prototype.js`. «Записать в каталог» в моках проставляет решениям и
  итогам потока id в каталоге и меняет статусы прошлых решений того же каталога.
  «К потокам →» в моках создаёт потоки из групп; их «Решения проекта» ждут вас, а поиск прошлых решений, как и другая
  работа моделей в моках, не кончается. У потока A совета c7 каталог пополнили после поиска — видно «Каталог
  изменился». План задач в моках — на весь совет, когда готовы все потоки (решение
  q-009 бекенда): у g1 — из `data-1.json`, у c1, c4, c7 — `ISSUES` макета (у c1 потоки ещё не готовы — задач нет);
  каталог задач — папка задач проекта совета (`Кромка` — `kromka-api/docs/tasks`, `Сайт` — `site/docs/tasks`,
  `gen_sdk_tooling` — `/repos/tasks`, у looper её нет — «Без папки»). Все потоки стали готовы у совета без плана в моках
  — «Задачи» — ИИ работает, и модели в моках работу не заканчивают; «Записать в каталог» на «Задачах» делает «Задачи»
  готовыми, «Запустить снова» запускает остановившийся план. Порядок вопросов на «Вариантах» и «Решениях» и круги
  зависимостей (`cycle`) моки считают, как сервер (`data/mock/order.ts`): по `dependsOn` вариантов совета и решений.
  Моки отдают копию данных: экран не может их испортить.
- `data/http/` — настоящий сервер: `request()` разбирает ответ и ошибку по контракту.
- `data/config.ts` — какой источник взять, по `VITE_DATA_SOURCE`: без неё — настоящий сервер.
- `data/hooks/` — хуки запросов: `useCouncils()`, `useCouncilBrief(id)`, `useCouncilSlicing(id, running)`,
  `useCouncilStructure(id, running)`, `useCouncilResearch(id, running)`, `useCouncilStreams(id, running)`,
  `useProjectDecisions(id, streamId)`, `useStreamQuestions(id, streamId, state)`, `useStreamOptions(id, streamId,
  state)`, `useStreamDecisions(id, streamId, state)`, `useStreamOutcomes(id, streamId, state)`, `useStreamNotes(id,
  streamId, state)`, `useCouncilTasks(id, running)`, `useModels()`, `useProjects()`, `useRepos()` → `{ data, error, loading,
  reload }`; хуки действий:
  `useCreateCouncil()`, `useUpdateCouncil()`, `useSaveBrief()`, `useStartSlicing()`, `useStartStructure()`,
  `useConfirmStructure()`, `useRetryStructure()`, `useResearchAction()` (`run(id, { action: 'start' | 'skip' | 'stop' |
  'reset', kind, … })`), `useApproveResearch()`, `useRetryStream()`, `useSearchProjectDecisions()`,
  `useApproveProjectDecisions()`, `useAddQuestion()`,
  `useApproveQuestions()`, `useAddOption()`, `useUpdateOption()`, `useApproveOptions()`, `useApproveDecisions()`,
  `useApproveOutcomes()`, `useApproveNotes()`, `useApproveTasks()`, `useRetryTasks()`, `useCreateProject()`,
  `useUpdateProject()`, `useDeleteProject()` →
  `{ run, pending, error }`.
  `run()` отвечает изменённым объектом (удаление — id удалённого) или `undefined`, если не вышло (причина — в `error`).
  `attempt()` — то же, но отвечает `{ value }` или `{ error }` этого запуска: когда действие запускают для разных
  объектов (поля «Свой вариант» разных вопросов), `error` хука — только про последний.
  `useFragmentLabels(id, running)` — смена типа фрагмента по щелчку, `useFindingDecisions(id, round)` — решение по
  находке по щелчку, `useQuestionRemovals(id, streamId, round)` — «Убрать» / «Вернуть» вопрос,
  `useOptionChoices(id, streamId, run, round)` — выбор по вопросу на «Вариантах»: все — на `useQueuedSaves()` (у
  каждого ключа своя очередь, на сервере — последний выбор; `pending` и `errors` по ключу, `change()` — отвечает, когда
  очередь дошла до выбора, `settle()`; сменился набор `round` — выборы прежних забываются; сменилась `lane` — очереди
  новые, и прежние их не держат: у выбора вариантов `lane` — `run`).
  `useRound(round, reset)` — номер набора: `round` стал другим — номер растёт и зовётся `reset()`; запрос, ушедший в
  прежнем наборе, по номеру узнаёт, что его ответ уже не про экран. Номер растёт в `useLayoutEffect`, в том же такте,
  что новый набор встал на экран: ответ, пришедший между ними, не примут за ответ про новый набор.
  `useGroupEdits(id, running)` — правки групп: `change()` (название, идея), `merge()`, `split()`, `pending` и `errors`
  по id группы, `reshaping`, `settle()`.
  `useDecisionEdits(id, streamId, run)` — правки решений: `type()` — набранное «почему» (`drafts`), `save()` — «почему»
  и где решение целиком, `pending` и `errors` по id вопроса, `settle()`, `latest()` — то же, но сейчас. Всё это общее
  для всех экранов «Решения» одного запуска шага: экран, открытый снова, видит набранное, уходящее и ошибки.
  `useOutcomeApprovals(id, streamId, run)` — «Утвердить → дальше» на «Итогах»: `approve()` — утвердить итог (отвечает,
  утвердился ли; итог уже утверждается — ответ на то утверждение), `pending` и `errors` по id итога, `errorOf()` — то
  же, но сейчас, `settle()` — дождаться всех утверждений запуска. Тоже общее для всех экранов «Итоги» одного запуска шага.
  Общее хранилище по совету, потоку и запуску шага у обоих — `runLanes()`, `updateLane()`, `useLaneState()` из
  `data/hooks/runLanes.ts`.
- `useAutosave(value, save, { delay, equal, stored })` — автосохранение того, что набирают: правка уходит после паузы,
  запросы — по одному с последним значением, закрыли экран — несохранённое уходит сразу; `saved` — всё сохранено,
  `flush()` — сохранить сейчас. `equal` — одинаковы ли значения для сервера (у названия — без пробелов по краям);
  `stored` — что сохранено, если на экране в начале другое (набранное в прошлый раз, которое не сохранилось).
- После действия данные, которые оно меняет, перезапрашиваются сами: действие после успеха помечает их устаревшими
  (`useMutation(action, (result, ...args) => markStale('councils', patch))`), запрос на них подписан
  (`useQuery(…, deps, 'councils')`). Правка `patch` вносит ответ действия в данные сразу, до перезапроса, и остаётся,
  если перезапрос не вышел: созданный совет виден в шапке и меню без нового списка. Данные и их вид — `Topics`
  в `data/hooks/stale.ts`.
- Опрос — когда данные могут поменяться без наших действий (модели работают): `poll('councils')` перезапрашивает
  запросы по ним, кроме тех, что ещё ждут ответа, — на медленной связи ответ не отбрасывается следующим опросом.
  Следующий опрос — через паузу после ответа на прошлый, а не по часам (`useModelsPoll(running, query)`): этап, где
  работают модели (нарезка, раскладка, план задач), запрашивает `useStageQuery()`; исследование опрашивается, пока по нему самому
  видно, что хоть одно исследование идёт.
- Действие, которое создаёт объект, шлёт `Idempotency-Key` (`data/hooks/idempotency.ts`): пока объект не создан, все
  попытки идут с одним ключом, и повтор после оборванного ответа не создаёт второй (`useCreateCouncil()`,
  `useCreateProject()`, `useAddQuestion()`, `useAddOption()`). Ключ живёт столько же, сколько хук: у проекта — пока
  открыто окно «Новый проект»; у вопроса — пока он не создан; у своего варианта — пока он не создан из этого поля
  (`field` — поле «Свой вариант» или правка варианта), даже если текст между попытками поправили; ключ у каждого поля
  свой и не теряется, пока сохраняют другие поля, — и между экранами «Варианты» (`fieldKeys` — по совету, потоку,
  запуску шага и полю): поле, которое не сохранилось, когда экран закрыли, на открытом снова пробует с тем же ключом.
- `data/errors.ts` — `ApiError` с `code`; текст ошибки — `t(errorKey(error.code))`, а не `message`.

Новая ручка: описать в `docs/api-contract.md` → тип в `domain/` → метод в `DataSource` → мок → http → хук.
Моки действий меняют данные моков, пока открыта вкладка: созданный совет виден в списке до перезагрузки страницы.

Загрузка и ошибка там, где макет их не показывает, выглядят одинаково на всех экранах — `components/LoadState`:
строка «Загружаем…» или текст ошибки по коду и «Повторить» (`reload` запроса). Данных ещё нет — на их месте
`<LoadState loading={q.loading} error={q.error} onRetry={q.reload} />`.

## Тексты интерфейса

Все тексты интерфейса — в словарях `src/i18n/locales/`: подписи, кнопки, подсказки, заголовки, названия этапов, шагов
и состояний, ошибки. В компоненте строк интерфейса нет: `components/` и `features/` берут их через `useI18n()`,
`ui/` получает пропами. Не переводится то, что приходит из данных: названия советов, проектов и групп, тексты,
написанные человеком и моделями, имена моделей.

Язык интерфейса — первый из языков браузера, который у нас есть; если ни одного — русский. Переключателя в макете
нет.

### Как добавить текст

1. Ключ и русский текст — в `locales/ru.ts`. Ключ — `раздел.имя`: `screen.home`, `stage.slices`. Русский текст —
   дословно из макета.
2. Тот же ключ — во всех остальных словарях (`locales/en.ts`). Термины — по списку ниже.
3. В компоненте: `const { t } = useI18n(); t('screen.home')`.

`typecheck` не пропустит словарь, в котором не хватает ключа, есть лишний ключ или не те подстановки.

**Подстановки.** Фразу не собирают из кусков: в другом языке другой порядок слов. Целая фраза — один ключ с
подстановками `{имя}`: `'date.today': 'сегодня, {time}'` → `t('date.today', { time })`. Числа в подстановках
форматируются по правилам языка.

**Формы числа.** Ключ с формами — объект с категориями `Intl.PluralRules` языка, число — `{count}`. Например:

```ts
// ru.ts — у русского one, few, many, other
'fragments.count': { one: '{count} фрагмент', few: '{count} фрагмента', many: '{count} фрагментов', other: '{count} фрагмента' },
// en.ts — у английского one, other
'fragments.count': { one: '{count} fragment', other: '{count} fragments' },
```

`t('fragments.count', { count: 5 })` → «5 фрагментов» / «5 fragments». Нужной формы нет — берётся `other`.

**Даты и числа** — из `useI18n()`, а не склейкой строк:

- `formatDate(value, 'relative')` — «сегодня, 14:20», «вчера, 19:40», «8 окт»; год — если он не текущий;
- `formatDate(value, 'day')` — «8 окт»; `formatDate(value, 'time')` — «14:20»;
- `formatNumber(1234)` — «1 234» / «1,234»;
- `formatList(['B', 'C'])` — «B и C» / «B and C»: перечисление через «и», а не склейка через запятую.

**Вёрстка** не рассчитывает на длину русского текста: в других языках подписи длиннее. Ширину под подпись не задаём;
длинное переносится или обрезается многоточием.

### Как добавить язык

Файл словаря `locales/<код>.ts` по образцу `en.ts` (через `translation()`) и строка в `LOCALES` в `locales/index.ts`.
Компоненты не меняются.

## Токены

`src/styles/tokens.css` — все цвета, шрифты, размеры текста, отступы, радиусы, тени и фон страницы из макета.
Компонент пишет `var(--…)`, а не значение. В макете встретилось новое значение — добавь токен.

- цвета — по роли: `--color-ink`, `--color-surface`, `--color-text-muted`, `--color-line`;
- состояния — `--state-<состояние>` (точка), `--state-<состояние>-bg` (фон метки), `--state-<состояние>-ink` (текст
  на нём): `done`, `running`, `waiting`, `failed`, `idle`;
- текст — `--font-sans` (Manrope), `--font-mono` (JetBrains Mono), `--text-xs`…`--text-title`, `--weight-*`,
  `--leading-*`, `--tracking-*`;
- отступы и радиусы — числом пикселей: `--space-14`, `--radius-18`; плюс `--radius-pill`, `--radius-round`;
- размеры — по назначению: `--sidebar-width`, `--logo-size`, `--dot-sm`, `--dot-md`, `--icon-sm`, `--card-min`
  и `--card-min-lg` (самая узкая карточка в сетке), `--intro-width` (абзац-пояснение под шапкой), `--dialog-width`
  и `--dialog-max-height` (окно), `--icon-button` (круглая кнопка «×»), `--checkbox-size` (галочка),
  `--check-tile-min` (самая узкая плитка с галочкой в сетке), `--stage-num-sm` и `--stage-num-md` (кружок с номером
  этапа: канбан, вкладки совета), `--stage-main-min` и `--stage-side-min` (колонки этапа совета), `--textarea-tall`
  (поле текста ввода), `--switch-width`, `--switch-height`, `--switch-knob` (переключатель), `--skeleton-line`,
  `--skeleton-width-second`, `--skeleton-width-third` (серые строки «ещё готовится»), `--fragment-id-width` (колонка
  с id фрагмента), `--badge-md` (кружок с буквой группы), `--alert-icon` (знак «!» на красной плашке),
  `--checkbox-size-sm` (галочка в строке фрагмента группы), `--card-min-xl` (широкие блоки рядом: исследования кода
  и макета), `--ref-min` («где найдено» на находке), `--conflict-side-min` (сторона противоречия), `--flow-step-num`
  (кружок с номером шага сценария в коде), `--stage-side-max` (боковая колонка слева: цепочка шагов потока),
  `--badge-sm` (буква потока на вкладке), `--step-num`, `--chain-line`, `--chain-line-min` (кружок шага и черта в
  цепочке), `--hint-width` (пояснение шага потока), `--pulse-spread` (кольцо вокруг точки модели, которая думает),
  `--question-id-width` (колонка с id вопроса потока), `--icon-button-sm` (круглая кнопка «←» / «→» на карточке),
  `--radio-size` и `--radio-dot` (кружок выбора варианта и точка в нём), `--option-label-min` (колонка «почему» /
  «цена» на карточке варианта), `--decision-label-min` (колонка подписей решения: «контекст», «последствия»),
  `--fix-num` (белый кружок с номером в «Что поправить»), `--adr-ref-min` (колонка номеров решений на итоге),
  `--criterion-box` (пустой квадратик перед критерием в «Готово, когда»), `--note-id-min` (колонка с id заметки на
  «Документации»), `--task-title-min` (название задачи на «Задачах» не уже этого);
- прозрачность — `--opacity-count` (число на чипе), `--opacity-disabled` (недоступный переключатель), `--opacity-idle`
  (не начатый шаг в цепочке), `--opacity-removed` (убранный вопрос потока);
- тени — `--shadow-card`, `--shadow-modal`, `--shadow-knob`; фон страницы — `--page-background`; затемнение под
  окном — `--overlay-bg`, `--overlay-blur`.

Шрифты Manrope и JetBrains Mono подключены пакетами `@fontsource` (`styles/fonts.css`), без запросов к Google Fonts.
В их наборах нет стрелки «→»: на кнопках и в моноширинном тексте («ADR-1 → ADR-0041») она берётся из системного
шрифта (`system-ui` в `--font-sans` и `--font-mono`).

## Сверка с макетом

`npm --prefix frontend run proto` распаковывает макет в `design/.src/Совет - прототип/`: `prototype.js` — данные,
состояния и действия экранов, `markup.html` — разметка и стили, `data-1.json` — данные настоящего совета `g1`.

`npm --prefix frontend run shot` снимает экран макета и наш экран на моках, ширина 1440:

```
npm --prefix frontend run shot -- --name home --proto "#/home" --app "/home"
npm --prefix frontend run shot -- --name slices --proto "#/c/g1/slices" --app "/c/g1/slices"
```

Снимки — `design/.shots/<name>-proto.png` и `<name>-app.png`. Макет снимается после того, как загрузит данные `g1`.
Флаги: `--click` / `--app-click` — клик по тексту, `css:<селектор>`, `fill:<селектор>=<текст>`, `key:<клавиша>`;
`--full` — страница целиком; `--height` — высота окна; `--locale en-US` — наш экран на английском. Остальное — в
начале `scripts/shot.mjs`. В селекторе `fill:` не должно быть `=` — по нему отделяется текст: вместо
`input[type=text] >> nth=1` пишите `:nth-match(dialog input[placeholder], 2)`. Окно проекта:

```
npm --prefix frontend run shot -- --name projedit --proto "#/projects" --click "Править" --app "/projects" --app-click "Править"
```

Шаги потока: `g1` — все шаги готовы; у `c1` поток A ждёт вас на «Документации», B — на «Вариантах», C остановился на
«Вопросах»; отбор прошлых решений — «Изменить отбор»:

```
npm --prefix frontend run shot -- --name project --proto "#/c/c1/streams/A/project" --click "Изменить отбор" --app "/c/c1/streams/A/project" --app-click "Изменить отбор"
npm --prefix frontend run shot -- --name failed --proto "#/c/c1/streams/C/questions" --app "/c/c1/streams/C/questions"
```

«Вопросы»: у `g1` шаг готов; у `c1` поток A — с «Пересматривает решение проекта» и «В тексте уже есть ответ», C —
остановился, внизу «Утвердить вопросы → к вариантам». Убрать вопрос и добавить свой:

```
npm --prefix frontend run shot -- --name questions --proto "#/c/c1/streams/C/questions" --click "Убрать" --click "fill:input[placeholder]=Свой" --click "Добавить" --app "/c/c1/streams/C/questions" --app-click "Убрать" --app-click "fill:input[placeholder]=Свой" --app-click "Добавить"
```

«Варианты»: у `g1` шаг готов (у Q2, Q7, Q8 — своя правка, у Q10 — свой вариант, Q12 — unresolved); у `c1` поток B
ждёт вас — выбран только Q1, открыт Q3. Отброшенные и правка у Q1, свой вариант у Q3 (пауза в наборе — `key:Shift`):

```
npm --prefix frontend run shot -- --name options --proto "#/c/c1/streams/B/options" --click "←" --click "Отброшено вариантов: 2 — почему" --click "Поправить" --app "/c/c1/streams/B/options" --app-click "←" --app-click "Отброшено вариантов: 2 — почему" --app-click "Поправить" --full
npm --prefix frontend run shot -- --name own --proto "#/c/c1/streams/B/options" --click "Свой вариант" --click "fill:textarea[placeholder]=Свой" --app "/c/c1/streams/B/options" --app-click "Свой вариант" --app-click "fill:textarea[placeholder]=Свой" --app-click "key:Shift" --full
```

«Решения»: у `g1` все решения зафиксированы, у Q12 — заметка судьи; у `c1` поток A — как в макете: «Решения» готовы,
решения — черновики, у Q4 — противоречие и «Что поправить». Q4, «Оставить открытым» и «Поправить в «Вариантах»»:

```
npm --prefix frontend run shot -- --name decisions --proto "#/c/c1/streams/A/decisions" --click "Q4" --click "Оставить открытым" --app "/c/c1/streams/A/decisions" --app-click "Q4" --app-click "Оставить открытым" --full
npm --prefix frontend run shot -- --name tooptions --proto "#/c/c1/streams/A/decisions" --click "Q4" --click "Поправить в «Вариантах»" --app "/c/c1/streams/A/decisions" --app-click "Q4" --app-click "Поправить в «Вариантах»"
```

«Итоги»: у `g1` все итоги утверждены, у итогов — решения с пояснениями; у `c1` поток A — как в макете: «Итоги» готовы,
итоги не утверждены, OUT-3 заблокирован Q4. Заблокированный итог и «Утвердить → дальше»:

