# Контракт API Совета

Что бекенд должен уметь, чтобы работали экраны фронтенда. Контракт пишется от макета (`design/Совет - прототип.html`):
что экран показывает и что на нём делают — то бекенд и отдаёт. Бекенда пока нет: экраны работают на моках, которые
ведут себя так, как написано здесь.

Каждая ручка повторена в коде фронтенда: типы — `frontend/src/domain/`, интерфейс источника — `frontend/src/data/source.ts`,
моки — `frontend/src/data/mock/`, настоящий сервер — `frontend/src/data/http/`, хуки запросов — `frontend/src/data/hooks/`.

## Решения

Ответы владельца на вопросы — дословно, с номером вопроса. Контракт и экраны им не противоречат.

- **q-001.** В меню слева, в блоке «Модели совета», у одной модели стоит метка «судья». Чей это судья?
  — «У каждого совета свой судья; в меню метка у судьи открытого совета, на Сводке и в Проектах метки «судья» нет».
- **q-002.** Можно ли нажать «К потокам →» на «Исследовании», пока группы ещё не подтверждены? И что с потоками, если
  группы потом поменяли? — «„К потокам →“ недоступна, пока группы не подтверждены; правки групп после появления
  потоков их не меняют».

## Общее

- Адрес API — `/api` на том же сервере, что и фронтенд. Пути ниже — полные: `GET /api/councils`.
- Тело запроса и ответа — JSON в UTF-8. Имена полей — camelCase.
- id — строки. Фронтенд их не разбирает и не собирает сам.
- Время — строка ISO 8601 в UTC: `"2026-10-15T13:41:50Z"`. Как его показать («сегодня, 14:20», «15 окт»), решает
  фронтенд.
- Тексты из данных — названия советов и проектов, текст ввода, фрагменты, вопросы, варианты, решения, итоги,
  задачи — приходят такими, как их написали человек или модели; фронтенд их не переводит. Подписи интерфейса —
  названия этапов, шагов, состояний — бекенд не присылает: он отдаёт значение (`"stage": "slices"`), а подпись
  («Нарезка» / «Slicing») фронтенд берёт из своего словаря.
- Чтение и действие — разные ручки. Действие отвечает изменённым объектом в том же виде, в каком его отдаёт чтение.
  Удаление отвечает `204` без тела: объекта больше нет.
- Один и тот же объект во всех ручках приходит в одном виде — см. «Объекты».

### Ошибки

Ответ с кодом 4xx или 5xx — всегда такого вида:

```json
{ "error": { "code": "not_found", "message": "Совет c9 не найден" } }
```

- `code` — что случилось, одним словом. Интерфейс показывает по нему текст из своего словаря.
- `message` — подробности для разработчика и логов. Интерфейс его не показывает.

Общие коды — их может вернуть любая ручка:

| code        | HTTP | Когда                              |
| ----------- | ---- | ---------------------------------- |
| `not_found` | 404  | нет такого объекта или такой ручки |
| `internal`  | 500  | сбой на сервере                    |

Свои коды ручки описаны у ручки. Прежде чем заводить новый код, проверь, не подходит ли уже описанный.

Ещё три кода фронтенд ставит сам, сервер их не присылает: `network` — сервер не ответил; `unknown` — ответ не
разобрать или код незнакомый; `not_saved` — действие не отправлено, потому что не сохранились правки перед ним
(«Утвердить выбор» на [«Вариантах»](#варианты-потока)).

### Общие значения

**Этап совета** (`stage`) — по порядку:

| Значение    | Этап         |
| ----------- | ------------ |
| `brief`     | Ввод         |
| `slices`    | Нарезка      |
| `structure` | Группы       |
| `research`  | Исследование |
| `streams`   | Потоки       |
| `tasks`     | Задачи       |

**Шаг потока** (`step`) — по порядку:

| Значение    | Шаг             |
| ----------- | --------------- |
| `project`   | Решения проекта |
| `questions` | Вопросы         |
| `options`   | Варианты        |
| `decisions` | Решения         |
| `outcomes`  | Итоги           |
| `notes`     | Документация    |

**Состояние** (`state`) совета, этапа или шага:

| Значение  | Подпись     | Что значит                                    |
| --------- | ----------- | --------------------------------------------- |
| `done`    | готово      | готово                                        |
| `running` | ИИ работает | модели сейчас работают                        |
| `waiting` | ждёт вас    | ИИ закончил, ход за человеком                 |
| `failed`  | ошибка      | ИИ не справился, нужно запустить снова         |
| `idle`    | черновик    | у совета — черновик; у этапа и шага — не начат |

**Тип фрагмента** (`label`) — по порядку, как в макете:

| Значение     | Подпись     |
| ------------ | ----------- |
| `idea`       | идея        |
| `question`   | вопрос      |
| `proposal`   | предложение |
| `constraint` | ограничение |
| `risk`       | риск        |

**Часть нарезки** (`phase`) — по порядку; так их называет `slicing.steps` у настоящего совета g1 (`data-1.json`):

| Значение      | Подпись        | Кто работает   |
| ------------- | -------------- | -------------- |
| `slice`       | Нарезка        | модели совета  |
| `slice_judge` | Судья нарезки  | судья          |
| `label`       | Разметка       | модели совета  |
| `label_judge` | Судья разметки | судья          |

**Работа модели** (`state` у [Run](#run--работа-модели)):

| Значение  | Подпись        | Что значит                                         |
| --------- | -------------- | -------------------------------------------------- |
| `waiting` | ждёт           | очередь модели ещё не пришла                       |
| `running` | работает…      | модель работает                                    |
| `done`    | готово         | модель закончила                                   |
| `failed`  | не справилась  | модель не справилась                               |
| `skipped` | не понадобился | судья не понадобился: модели не разошлись          |

**Часть раскладки** (`phase` у [StructureStep](#structurestep--часть-раскладки)) — по порядку; так их называет
`structure.steps` у настоящего совета g1 (`data-1.json`):

| Значение          | Подпись         | Кто работает  |
| ----------------- | --------------- | ------------- |
| `structure`       | Раскладка       | модели совета |
| `structure_judge` | Судья раскладки | судья         |

**Откуда идея группы** (`ideaBy` у [Group](#group--группа)) — как в макете:

| Значение | Подпись   | Что значит                                                                         |
| -------- | --------- | ---------------------------------------------------------------------------------- |
| `text`   | из текста | идея взята из текста ввода                                                         |
| `ai`     | ИИ        | идею восстановил ИИ по фрагментам; идея пустая — ИИ её ещё восстановит              |
| `user`   | вы        | идею вписал человек                                                                |

**Связь группы** (`kind` у [GroupLink](#grouplink--связь-группы)) — строка под фрагментами группы в макете:

| Значение      | Подпись                 | Что значит                                                                  |
| ------------- | ----------------------- | --------------------------------------------------------------------------- |
| `depends_on`  | зависит от A            | эта группа зависит от группы `group`                                         |
| `required_by` | от неё зависит B        | группа `group` зависит от этой                                               |
| `related`     | связана с A             | группы связаны, но не зависят одна от другой                                 |
| `shared`      | F5 — копия, общий с C   | фрагмент `fragment` есть и здесь, и в группе `group`; здесь — его копия      |
| `merged`      | объединена с группой A  | с этой группой объединили группу `group` («Объединить с…»)                   |
| `split`       | выделена из группы A    | эту группу выделили из группы `group` («Разделить»)                          |

**Исследование** (`kind`) — два блока этапа «Исследование», как в макете:

| Значение | Подпись              | Что исследует                                            |
| -------- | -------------------- | -------------------------------------------------------- |
| `code`   | Исследование кода    | репозитории проекта: карта реализации под все группы      |
| `design` | Исследование макета  | макет Figma по ссылке: экраны, данные, действия, состояния |

**Состояние исследования** (`state` у [CodeResearch](#coderesearch--исследование-кода) и
[DesignResearch](#designresearch--исследование-макета)) — метка блока в макете:

| Значение  | Подпись    | Что значит                                                        |
| --------- | ---------- | ----------------------------------------------------------------- |
| `setup`   | не начато  | человек выбирает, что исследовать (репозитории, ссылку), и начинает или пропускает |
| `running` | идёт       | модели исследуют                                                  |
| `done`    | готово     | модели закончили: находки — в `findings`                          |
| `skipped` | пропущено  | человек пропустил исследование: потоки пойдут без него            |

**Вид находки** (`kind` у [Finding](#finding--находка)) — как в макете:

| Значение    | Подпись      | Что значит                                                     |
| ----------- | ------------ | -------------------------------------------------------------- |
| `fact`      | факт         | подтверждено кодом или макетом — уходит в потоки как есть       |
| `inference` | вывод ИИ     | ИИ так заключил — человек подтверждает или отклоняет           |
| `conflict`  | противоречие | текст ввода (или документация) говорит одно, код или макет — другое |
| `gap`       | пробел       | не установлено — по умолчанию станет вопросом потока           |

**Решение по находке** (`decision` у [Finding](#finding--находка)) — кнопки находки в макете; у каждого вида свои:

| Вид         | Значение   | Кнопка                 | Подпись справа на находке   |
| ----------- | ---------- | ---------------------- | --------------------------- |
| `fact`      | `null`     | —                      | → в потоки                  |
| `inference` | `null`     | —                      | ждёт вас                    |
| `inference` | `accept`   | Верно                  | → в потоки как факт         |
| `inference` | `reject`   | Неверно                | не пойдёт в потоки          |
| `conflict`  | `null`     | —                      | ждёт вас                    |
| `conflict`  | `text`     | Прав текст             | → прав текст                |
| `conflict`  | `source`   | Прав код / Прав макет  | → прав код / → прав макет   |
| `conflict`  | `question` | В вопрос               | → вопрос в поток            |
| `gap`       | `question` | Вернуть вопрос         | → вопрос в поток            |
| `gap`       | `drop`     | Не важно               | не пойдёт в потоки          |

Находка ждёт решения человека — вывод ИИ или противоречие с `decision` `null`. У пробела `null` не бывает: по
умолчанию он `question` — «Пробелы по умолчанию станут вопросами потока», как в макете.

**Покрытие** (`status` у [Coverage](#coverage--покрытие)) — как в макете:

| Значение         | Подпись    |
| ---------------- | ---------- |
| `covered`        | проверено  |
| `partial`        | частично   |
| `not_applicable` | вне задачи |

**Часть шага потока** (`phase` у [StepProgress](#stepprogress--часть-шага-потока)) — по порядку; так их называют шаги
потока у настоящего совета g1 (`data-1.json`: `questions.steps`, `proposals.steps`, `analysis.steps`,
`outcomes.steps`). У «Решений проекта» и «Документации» частей нет: там модели не работают.

| Значение             | Подпись           | Шаг       | Кто работает  |
| -------------------- | ----------------- | --------- | ------------- |
| `question_discovery` | Сбор вопросов     | Вопросы   | модели совета |
| `question_judge`     | Судья вопросов    | Вопросы   | судья         |
| `proposal_discovery` | Поиск вариантов   | Варианты  | модели совета |
| `proposal_judge`     | Судья вариантов   | Варианты  | судья         |
| `decision_analysis`  | Проверка решений  | Решения   | модели совета |
| `decision_judge`     | Судья решений     | Решения   | судья         |
| `outcome_discovery`  | Сбор итогов       | Итоги     | модели совета |
| `outcome_judge`      | Судья итогов      | Итоги     | судья         |

Подписи «Сбор вопросов», «Поиск вариантов», «Судья вариантов» — из макета; у судьи вопросов в макете «Судья
репозитория», остальных в макете нет — они названы так же.

**Как прошлое решение относится к идее потока** (`relation` у [PastDecision](#pastdecision--прошлое-решение)) — метка
решения в макете:

| Значение             | Подпись             | Цвет    |
| -------------------- | ------------------- | ------- |
| `applicable`         | относится           | зелёный |
| `potential_conflict` | может противоречить | красный |
| `uncertain`          | неясно              | серый   |

**Статус прошлого решения** (`status` у [PastDecision](#pastdecision--прошлое-решение)) — серая метка рядом, как в
макете:

| Значение       | Метка                                                         |
| -------------- | ------------------------------------------------------------- |
| `active`       | — (решение действует, метки нет)                              |
| `under_review` | под вопросом: его пересматривают                              |
| `superseded`   | superseded · заменено ADR-0008 — отметьте его вместо этого     |

**Откуда вопрос** (`source` у [Question](#question--вопрос-потока)) — серая метка вопроса в макете:

| Значение | Подпись   | Что значит                                                   |
| -------- | --------- | ------------------------------------------------------------ |
| `text`   | из текста | вопрос записан в тексте ввода или прямо из него следует        |
| `ai`     | ИИ        | вопрос нашли модели                                            |
| `user`   | вы        | вопрос добавил человек: «Свой вопрос…» и «Добавить»            |

В `data-1.json` у g1 это `source` вопроса: `user` и `inferred` — `text`, `discovered` — `ai`, `added` — `user`; так их
подписывает макет.

**Откуда вариант** (`source` у [Option](#option--вариант)) — метка варианта в макете:

| Значение | Подпись   | Цвет    | Что значит                                                                           |
| -------- | --------- | ------- | ------------------------------------------------------------------------------------ |
| `group`  | из группы | зелёный | вариант из фрагмента-предложения группы — того, что на «Вопросах» было «В тексте уже есть ответ» |
| `ai`     | ИИ        | тёмный  | вариант нашли модели                                                                 |
| `user`   | вы        | тёмный  | вариант человека: «Свой вариант» или правка варианта («Поправить»)                    |

В `data-1.json` у g1 варианты моделей — `source: "council"`, это `ai`; свои варианты лежат в `choices` с текстом
(`text`, `based_on`) — это `user`.

## Объекты

### CouncilSummary — совет в списке

```json
{
  "id": "g1",
  "name": "Получение списка сервисов Generation",
  "project": { "id": "p4", "name": "gen_sdk_tooling" },
  "stage": "tasks",
  "state": "done",
  "stages": {
    "brief": "done",
    "slices": "done",
    "structure": "done",
    "research": "done",
    "streams": "done",
    "tasks": "done"
  },
  "streams": [{ "id": "A", "step": "notes" }],
  "participants": ["sol", "opus"],
  "judge": "opus",
  "updatedAt": "2026-10-15T13:41:50Z",
  "activity": [],
  "summary": "7 задач и 57 заметок записаны"
}
```

| Поле        | Тип                   | Что                                                                        |
| ----------- | --------------------- | -------------------------------------------------------------------------- |
| `id`        | string                | id совета; он же в адресах экранов: `/c/<id>/<этап>`                        |
| `name`      | string                | название; пустая строка — совет без названия. Меняют на «Вводе»             |
| `project`   | ProjectRef \| null    | проект совета; `null` — без проекта. Меняют на «Вводе»                      |
| `stage`     | этап                  | на каком этапе совет сейчас                                                |
| `state`     | состояние             | состояние совета: точка у совета в меню, метка и порядок карточек на Сводке |
| `stages`    | этап → состояние      | состояние каждого из шести этапов: дорожка этапов на Сводке, номера на вкладках этапов совета |
| `streams`   | StreamSummary[]       | потоки совета по порядку; до этапа «Потоки» — пустой массив. Если `stage` — `streams`, поток есть хотя бы один |
| `participants` | string[]           | модели, которые работают в совете, — `id` моделей из [GET /api/models](#get-apimodels--модели-совета), по порядку. Меняют на «Вводе» |
| `judge`     | string                | судья совета — `id` модели из [GET /api/models](#get-apimodels--модели-совета); у каждого совета свой (решение q-001). Меняют на «Вводе» |
| `updatedAt` | время                 | когда совет менялся последний раз                                          |
| `activity`  | Activity[]            | где в совете сейчас ошибка, где ждут человека, где работает ИИ — строки карточки совета на Сводке; см. [Activity](#activity--что-происходит-в-совете). Готовый совет — пустой массив |
| `summary`   | string                | итог совета одной строкой: «7 задач и 57 заметок записаны». Текст пишет сервер; Сводка показывает его у совета без `activity` — в строке «Готово» |

Под заголовком совета в шапке — строка из этих полей, как в макете: «gen_sdk_tooling · судья opus · модели sol, opus ·
15 окт» — проект (`project`, нет — «Без проекта»), судья (`judge`), модели (`participants`), когда менялся
(`updatedAt`).

Куда ведёт совет из меню — как в макете: на этап `stage`; если это `streams` — на первый поток из `streams`, на его
шаг `step` (`/c/<id>/streams/<поток>/<шаг>`).

Под шапкой совета на всех его экранах — вкладки шести этапов, как в макете: номер и название этапа, цвет номера —
состояние этапа из `stages` (готово и ИИ работает — зелёный, ждёт вас — жёлтый, ошибка — красный, не начат — серый);
открытая вкладка — тёмная. Вкладка ведёт на этап: `/c/<id>/<этап>`. «Потоки» — на поток и шаг, которые человек
последним открывал в этом совете, пока открыта вкладка браузера (так в макете); иначе — туда же, куда совет на
«Потоках» из меню: первый поток на его шаге; потоков ещё нет — «Исследование». Своей ручки у вкладок нет: всё
приходит в списке советов.

### StreamSummary — поток в списке советов

```json
{ "id": "A", "step": "notes" }
```

| Поле   | Тип    | Что                                                                                  |
| ------ | ------ | ------------------------------------------------------------------------------------ |
| `id`   | string | id потока; он же в адресе шага: `/c/<совет>/streams/<id>/<шаг>`                       |
| `step` | шаг    | на каком шаге поток сейчас: первый неготовый шаг; все шаги готовы — последний, `notes` |

Поток целиком — с названием, идеей и шагами — [Stream](#stream--поток), его отдают
[потоки совета](#get-apicouncilsidstreams--потоки-совета).

### Activity — что происходит в совете

Одно место совета, где сейчас что-то происходит: там ошибка, ждут человека или работают модели. На Сводке это строка
на карточке совета: «Поток B · Варианты — Выберите вариант на 2 вопроса из 3».

```json
{ "stage": "streams", "stream": "B", "step": "options", "state": "waiting", "text": "Выберите вариант на 2 вопроса из 3" }
```

```json
{ "stage": "structure", "stream": null, "step": null, "state": "failed", "text": "Раскладка по группам остановилась" }
```

| Поле     | Тип            | Что                                                                                  |
| -------- | -------------- | ------------------------------------------------------------------------------------ |
| `stage`  | этап           | этап, где это происходит                                                             |
| `stream` | string \| null | поток — `id` из `streams` совета; только на этапе `streams`, на других этапах — `null` |
| `step`   | шаг \| null    | шаг потока; только на этапе `streams`, на других этапах — `null`                       |
| `state`  | состояние      | только `failed` — ошибка, `waiting` — ждёт вас, `running` — ИИ работает              |
| `text`   | string         | что нужно от человека или что делает ИИ — одной строкой, текст пишет сервер (см. ниже) |

Что попадает в `activity` — как в макете:

- каждый этап, кроме «Потоков», и каждый шаг потока в состоянии `failed`, `waiting` или `running` — по пункту;
- черновик (совет в состоянии `idle`) — один пункт: «Ввод», `waiting`, «Допишите текст и нарежьте»;
- готовый совет — ничего.

Порядок задаёт сервер, фронтенд его сохраняет. В макете: сначала ошибки, потом «ждёт вас», потом «ИИ работает»;
внутри — сначала то, что изменилось позже.

`text` — короткая строка о том, что в этом месте: «Сбор вопросов остановился», «Подтвердите карту кода», «Запишите
6 задач в каталог», «sol и fable режут текст», «Черновик заметок ждёт вас: ADR-0005 станет superseded». В ней числа,
имена моделей и номера решений этого совета, поэтому её пишет сервер, а интерфейс показывает как есть и не переводит —
как тексты моделей. Подпись места («Поток B · Варианты», «Группы») и цвет строки фронтенд берёт из `stage`, `stream`,
`step` и `state`.

Куда ведёт пункт: на этап `/c/<совет>/<этап>`; на «Потоках» — на шаг потока `/c/<совет>/streams/<stream>/<step>`.

### CouncilFields — поля совета

То, что человек меняет на [«Вводе»](#ввод-совета): название, проект, модели и судья. Тело
[правки совета](#patch-apicouncilsid--правка-совета). Полей, которых нет в теле, правка не меняет; «Ввод» шлёт одно
поле за раз (модели — весь список).

```json
{ "name": "Офлайн-режим заявок", "projectId": "p1", "participants": ["sol", "fable"], "judge": "fable" }
```

| Поле           | Тип            | Что                                                                                   |
| -------------- | -------------- | ------------------------------------------------------------------------------------- |
| `name`         | string         | название; пробелы по краям сервер убирает; пустая строка — совет без названия          |
| `projectId`    | string \| null | проект — `id` из [GET /api/projects](#get-apiprojects--проекты); `null` — без проекта  |
| `participants` | string[]       | модели совета — `id` из [GET /api/models](#get-apimodels--модели-совета), по порядку; может быть пустым. Повтор `id` сервер считает одной моделью |
| `judge`        | string         | судья — `id` модели из [GET /api/models](#get-apimodels--модели-совета)                |

Как в макете, не подключённую модель (`online: false`) не добавить в совет и не сделать судьёй. Модель, которая уже
в совете или уже судит его, остаётся, даже если её отключили (так у совета g1: модели sol и opus, судья opus, а opus
не подключена). Других проверок нет — в макете их тоже нет: судья может не входить в модели совета, моделей может не
быть совсем.

Ошибки полей:

| code              | HTTP | Когда                                                                                |
| ----------------- | ---- | ------------------------------------------------------------------------------------ |
| `unknown_project` | 422  | проекта нет в [GET /api/projects](#get-apiprojects--проекты)                          |
| `unknown_model`   | 422  | модели из `participants` или `judge` нет в [GET /api/models](#get-apimodels--модели-совета) |
| `model_offline`   | 422  | в `participants` добавлена не подключённая модель или она поставлена судьёй           |

«Ввод» не даёт выбрать ни то, ни другое, поэтому эти ошибки — на случай, когда список на экране устарел: проект
удалили, модель отключили, пока «Ввод» был открыт. Интерфейс показывает текст ошибки по коду в блоке, где меняли, без
«Повторить», возвращает поле к тому, что в списке советов, и заново запрашивает список проектов (`unknown_project`)
или моделей (`unknown_model`, `model_offline`).

### Brief — текст ввода

Мысли человека в свободной форме: из них совет нарезает фрагменты (этап «Нарезка»). Пишут его на «Вводе».

```json
{ "text": "Обеспечить получение списка сервисов Generation из существующих данных Scan и вывести его в /generation. …" }
```

| Поле   | Тип    | Что                                                                                   |
| ------ | ------ | ------------------------------------------------------------------------------------- |
| `text` | string | текст как есть — с переносами строк и пробелами, как его написал человек; пустая строка — текста нет |

### Slicing — нарезка совета

Что сделали модели на этапе «Нарезка»: ход работы последней нарезки и фрагменты текста ввода с типами. Показывает
её [«Нарезка»](#нарезка-совета).

```json
{
  "progress": [
    { "phase": "slice", "runs": [{ "model": "sol", "state": "running" }, { "model": "fable", "state": "done" }] },
    { "phase": "slice_judge", "runs": [{ "model": "fable", "state": "waiting" }] },
    { "phase": "label", "runs": [{ "model": "sol", "state": "waiting" }, { "model": "fable", "state": "waiting" }] },
    { "phase": "label_judge", "runs": [{ "model": "fable", "state": "waiting" }] }
  ],
  "fragments": []
}
```

| Поле        | Тип           | Что                                                                                     |
| ----------- | ------------- | --------------------------------------------------------------------------------------- |
| `progress`  | SlicingStep[] | ход работы последней нарезки — четыре [части](#общие-значения) по порядку; нарезки не было — пустой массив |
| `fragments` | Fragment[]    | фрагменты в порядке текста; пока нарезка идёт (`stages.slices` — `running`) или её не было — пустой массив |

### SlicingStep — часть нарезки

```json
{ "phase": "slice", "runs": [{ "model": "sol", "state": "running" }, { "model": "fable", "state": "done" }] }
```

| Поле    | Тип    | Что                                                                                         |
| ------- | ------ | ------------------------------------------------------------------------------------------- |
| `phase` | часть нарезки | `slice`, `slice_judge`, `label`, `label_judge`                                       |
| `runs`  | Run[]  | модели этой части по порядку: у `slice` и `label` — модели совета (`participants`), у судей — судья совета (`judge`). Судья, который не понадобился, тоже здесь — с `skipped` |

### Run — работа модели

```json
{ "model": "sol", "state": "running" }
```

| Поле    | Тип    | Что                                                                  |
| ------- | ------ | -------------------------------------------------------------------- |
| `model` | string | `id` модели из [GET /api/models](#get-apimodels--модели-совета)      |
| `state` | работа модели | `waiting`, `running`, `done`, `failed`, `skipped`             |

### Fragment — фрагмент

Кусок текста ввода — как его написал человек, без изменений, — и его тип.

```json
{
  "id": "F2",
  "text": "В список входят сервисы read-in-full = 100%, partial или scanned, у которых в активном снимке есть хотя бы один эндпоинт.",
  "label": "proposal",
  "councilLabel": "proposal",
  "decidedBy": "judge"
}
```

| Поле           | Тип    | Что                                                                                  |
| -------------- | ------ | ------------------------------------------------------------------------------------ |
| `id`           | string | id фрагмента; интерфейс показывает его как есть: «F2». Он же в пути [смены типа](#patch-apicouncilsidfragmentsfragmentid--сменить-тип-фрагмента) |
| `text`         | string | кусок текста ввода как есть                                                          |
| `label`        | тип фрагмента | тип сейчас: выбранный человеком; не выбирал — тот, что дал совет               |
| `councilLabel` | тип фрагмента | тип, который дал совет                                                         |
| `decidedBy`    | string | кто дал тип: `agreed` — модели сошлись; `judge` — модели разошлись, решил судья      |

В `data-1.json` у g1 это `slicing.fragments`: `id` — «F» и номер, `label`, `council_label`, `decided_by`.

### Structure — раскладка совета по группам

Что сделали модели на этапе «Группы»: ход работы последней раскладки, группы фрагментов и почему раскладка
остановилась. Показывает её [«Группы»](#группы-совета).

```json
{
  "progress": [
    { "phase": "structure", "runs": [{ "model": "sol", "state": "done" }, { "model": "opus", "state": "done" }] },
    { "phase": "structure_judge", "runs": [{ "model": "opus", "state": "skipped" }] }
  ],
  "groups": [
    {
      "id": "A",
      "title": "Список сервисов Generation",
      "idea": "Обеспечить получение списка сервисов Generation из существующих данных Scan и вывести его в /generation.",
      "ideaBy": "text",
      "fragments": [
        {
          "id": "F1",
          "text": "Обеспечить получение списка сервисов Generation из существующих данных Scan и вывести его в /generation.",
          "label": "idea",
          "councilLabel": "idea",
          "decidedBy": "agreed"
        }
      ],
      "links": []
    }
  ],
  "error": null
}
```

| Поле       | Тип             | Что                                                                                     |
| ---------- | --------------- | --------------------------------------------------------------------------------------- |
| `progress` | StructureStep[] | ход работы последней раскладки — две [части](#общие-значения) по порядку; раскладки не было — пустой массив |
| `groups`   | Group[]         | группы по порядку; пока раскладка идёт (`stages.structure` — `running`) или её не было — пустой массив |
| `error`    | string \| null  | почему раскладка остановилась — одной строкой, текст пишет сервер: «fable не справилась: прерван, сервер остановился.»; раскладка не остановилась (`stages.structure` — не `failed`) — `null`. В ней имена моделей и причина сбоя, поэтому интерфейс показывает её как есть и не переводит — как `text` у [Activity](#activity--что-происходит-в-совете) |

В `data-1.json` у g1 это `structure`: `steps`, `groups`, `error`; идея группы — `streams[].idea` (`text`, `by`).

### StructureStep — часть раскладки

```json
{ "phase": "structure", "runs": [{ "model": "sol", "state": "running" }, { "model": "fable", "state": "done" }] }
```

| Поле    | Тип             | Что                                                                                      |
| ------- | --------------- | ---------------------------------------------------------------------------------------- |
| `phase` | часть раскладки | `structure`, `structure_judge`                                                            |
| `runs`  | Run[]           | модели этой части по порядку: у `structure` — модели совета, у судьи — судья совета; судья, который не понадобился, — с `skipped`. [Run](#run--работа-модели) — тот же, что у нарезки |

### Group — группа

Фрагменты вокруг одной идеи. После «Подтвердить группы» каждая группа станет потоком.

```json
{
  "id": "B",
  "title": "Конфликты при синхронизации",
  "idea": "При отправке очереди сервер сверяет версии заявки и не затирает правки диспетчера молча.",
  "ideaBy": "ai",
  "fragments": [
    {
      "id": "F4",
      "text": "Что делать, если диспетчер успел поменять ту же заявку на сервере?",
      "label": "question",
      "councilLabel": "question",
      "decidedBy": "judge"
    }
  ],
  "links": [
    { "kind": "depends_on", "group": "A", "fragment": null },
    { "kind": "shared", "group": "C", "fragment": "F5" }
  ]
}
```

| Поле        | Тип             | Что                                                                                   |
| ----------- | --------------- | ------------------------------------------------------------------------------------- |
| `id`        | string          | id группы; интерфейс показывает его как есть, в кружке: «B». Он же в пути [правки группы](#patch-apicouncilsidgroupsgroupid--правка-группы) |
| `title`     | string          | название; пустая строка — без названия                                                 |
| `idea`      | string          | идея группы; пустая строка — идеи нет, ИИ восстановит её по фрагментам                  |
| `ideaBy`    | откуда идея     | `text`, `ai`, `user` — см. [общие значения](#общие-значения)                          |
| `fragments` | Fragment[]      | фрагменты группы по порядку; один фрагмент может быть в нескольких группах. [Fragment](#fragment--фрагмент) — тот же, что у нарезки: `label` — тип, с которым фрагмент идёт дальше (выбранный человеком на «Нарезке») |
| `links`     | GroupLink[]     | связи с другими группами в порядке сервера; нет — пустой массив                         |

### GroupLink — связь группы

```json
{ "kind": "shared", "group": "C", "fragment": "F5" }
```

| Поле       | Тип            | Что                                                                     |
| ---------- | -------------- | ----------------------------------------------------------------------- |
| `kind`     | связь группы   | `depends_on`, `required_by`, `related`, `shared`, `merged`, `split` — см. [общие значения](#общие-значения) |
| `group`    | string         | `id` другой группы этой раскладки                                        |
| `fragment` | string \| null | `id` общего фрагмента — только у `shared`; у других связей `null`         |

Связь ссылается только на группу, которая есть в `groups`: группа пропала (её объединили с другой) — сервер правит
связи, см. [объединение](#post-apicouncilsidgroupsgroupidmerge--объединить-группы).

### GroupFields — поля группы

То, что человек меняет на карточке группы: название и идея. Тело
[правки группы](#patch-apicouncilsidgroupsgroupid--правка-группы). Полей, которых нет в теле, правка не меняет.

```json
{ "title": "Офлайн-очередь заявок", "idea": "Заявка копится на телефоне и уходит сама, когда сеть вернётся." }
```

| Поле    | Тип    | Что                                                                                         |
| ------- | ------ | ------------------------------------------------------------------------------------------- |
| `title` | string | название; пробелы по краям сервер убирает; пустая строка — можно (в макете название стирается) |
| `idea`  | string | идея как есть; пустая строка — можно. Идея, которую поправил человек, — его: `ideaBy` становится `user` |

### Research — исследование совета

Что совет узнал о коде и макете под все группы сразу: два исследования — кода и макета, — находки, сценарии в коде и
покрытие. Показывает его [«Исследование»](#исследование-совета).

```json
{
  "code": {
    "state": "done",
    "repos": [
      { "name": "gen_sdk_tooling", "selected": true },
      { "name": "python-t-cloud", "selected": true }
    ],
    "runs": [],
    "minutes": 0,
    "scanned": [
      { "name": "gen_sdk_tooling", "commit": "7440e1a59acf61eafe9d13c2441b39a8ee72e73b", "files": 304 },
      { "name": "python-t-cloud", "commit": "ba74a37679b790a8a6f9c6e1e397de945bac549c", "files": 74 }
    ],
    "rounds": 1
  },
  "design": { "state": "skipped", "link": "", "runs": [], "minutes": 0, "frames": 0 },
  "findings": [
    {
      "id": "R15",
      "group": "A",
      "source": "code",
      "kind": "inference",
      "text": "Если у снимка есть ключ `analytics.read_in_full` и хотя бы один документ со статусом, то из `scanned` следует read-in-full = 100%.",
      "conflict": null,
      "ref": "core/service_state.py:149-164, 218-224 +1",
      "decision": "accept"
    }
  ],
  "flows": [
    {
      "name": "Смена активного снимка",
      "entry": "gen_sdk_tooling/src/tools/panel/api/routes/scans.py",
      "steps": [{ "text": "Worker активирует сохранённый снимок, latest не меняется.", "findings": ["R19"] }]
    }
  ],
  "coverage": [
    { "area": "Тесты", "status": "partial", "reason": "Исходники тестов проверены выборочно, сами тесты не запускались." }
  ]
}
```

| Поле       | Тип            | Что                                                                                      |
| ---------- | -------------- | ---------------------------------------------------------------------------------------- |
| `code`     | CodeResearch   | [исследование кода](#coderesearch--исследование-кода)                                     |
| `design`   | DesignResearch | [исследование макета](#designresearch--исследование-макета)                               |
| `findings` | Finding[]      | [находки](#finding--находка) готовых исследований: сначала кода, потом макета, в порядке сервера; исследование не готово — его находок нет |
| `flows`    | Flow[]         | [сценарии в коде](#flow--сценарий-в-коде) — «Потоки в коде» в макете; код не исследован (`code.state` — не `done`) — пустой массив |
| `coverage` | Coverage[]     | [какие части кода совет проверил](#coverage--покрытие); код не исследован — пустой массив |

В `data-1.json` у g1 это `research`: `scan.repositories`, `scan.rounds`, `scan.result` (`findings`, `unknowns`,
`documentation_conflicts`, `flows`, `coverage`), `design` (`by: "skipped"`).

### CodeResearch — исследование кода

| Поле      | Тип                | Что                                                                                   |
| --------- | ------------------ | ------------------------------------------------------------------------------------- |
| `state`   | состояние исследования | `setup`, `running`, `done`, `skipped` — см. [общие значения](#общие-значения)      |
| `repos`   | RepoChoice[]       | репозитории проекта совета по порядку — `repos` [проекта](#project--проект); без проекта — пустой массив. См. ниже |
| `runs`    | ResearchRun[]      | [что делают модели](#researchrun--работа-модели-в-исследовании), пока исследование идёт; иначе — пустой массив |
| `minutes` | number             | сколько примерно минут займёт исследование — «~2 мин»; пока идёт; иначе `0`           |
| `scanned` | ScannedRepo[]      | [какие репозитории исследованы](#scannedrepo--исследованный-репозиторий), по порядку; готово — не пустой; иначе — пустой массив |
| `rounds`  | number             | сколько проходов по коду сделали модели — «проходов: 2»; готово; иначе `0`              |

**RepoChoice** — репозиторий проекта на «Исследовании»:

```json
{ "name": "kromka-android", "selected": false }
```

| Поле       | Тип     | Что                                                                                         |
| ---------- | ------- | ------------------------------------------------------------------------------------------- |
| `name`     | string  | имя рабочей копии — как в `repos` проекта                                                    |
| `selected` | boolean | исследование возьмёт репозиторий: галочка стоит, когда открывается настройка. Исследование уже было — стоит у тех, что взяли тогда; не было — у тех, что, по мнению совета, нужны идее. `false` — совет считает, что идее он не нужен: на экране «не нужен этой идее?»; `true` — «репозиторий проекта» |

### DesignResearch — исследование макета

| Поле      | Тип                | Что                                                                                   |
| --------- | ------------------ | ------------------------------------------------------------------------------------- |
| `state`   | состояние исследования | `setup`, `running`, `done`, `skipped`                                              |
| `link`    | string             | ссылка на Figma: пока идёт и готово — та, что исследуется; в настройке — та, что была в прошлый раз (её можно поправить); не было — пустая строка |
| `runs`    | ResearchRun[]      | что делают модели, пока исследование идёт; иначе — пустой массив                       |
| `minutes` | number             | сколько примерно минут займёт исследование — «~1 мин»; пока идёт; иначе `0`           |
| `frames`  | number             | сколько фреймов по ссылке — «4 фрейма»; пока идёт и готово; иначе `0`                  |

### ResearchRun — работа модели в исследовании

```json
{ "model": "sol", "state": "running", "text": "проход 1 · читает kromka-api" }
```

| Поле    | Тип           | Что                                                                                      |
| ------- | ------------- | ---------------------------------------------------------------------------------------- |
| `model` | string        | `id` модели из [GET /api/models](#get-apimodels--модели-совета)                          |
| `state` | работа модели | `waiting`, `running`, `done`, `failed` — как у [Run](#run--работа-модели)                 |
| `text`  | string        | что модель делает — одной строкой, текст пишет сервер: «проход 1 · читает kromka-api», «сверяет с группами». В нём номера проходов и имена репозиториев, поэтому интерфейс показывает его как есть, как `text` у [Activity](#activity--что-происходит-в-совете) |

### ScannedRepo — исследованный репозиторий

```json
{ "name": "gen_sdk_tooling", "commit": "7440e1a59acf61eafe9d13c2441b39a8ee72e73b", "files": 304 }
```

| Поле     | Тип    | Что                                                                       |
| -------- | ------ | ------------------------------------------------------------------------- |
| `name`   | string | имя рабочей копии                                                         |
| `commit` | string | коммит, который исследован, — SHA целиком; интерфейс показывает 7 знаков   |
| `files`  | number | сколько файлов прочитано                                                  |

Под исследованием кода, как в макете, — первый репозиторий: «gen_sdk_tooling · коммит 7440e1a · файлов: 304 ·
проходов: 1».

### Finding — находка

```json
{
  "id": "R6",
  "group": "B",
  "source": "code",
  "kind": "conflict",
  "text": "Кто может править заявку, пока мастер офлайн.",
  "conflict": {
    "by": "text",
    "claim": "Диспетчер правит заявку, пока мастер без сети (F4).",
    "found": "API разрешает править заявку только её автору."
  },
  "ref": "kromka-api/requests/permissions.py:18",
  "decision": null
}
```

| Поле       | Тип            | Что                                                                                    |
| ---------- | -------------- | -------------------------------------------------------------------------------------- |
| `id`       | string         | id находки, один на всё исследование; интерфейс его не показывает. Он же в пути [решения](#patch-apicouncilsidresearchfindingsfindingid--решение-по-находке) и в `findings` у шагов сценария |
| `group`    | string         | `id` [группы](#group--группа), к которой находка, — под ней она на экране               |
| `source`   | исследование   | откуда находка: `code` — «код», `design` — «макет»                                      |
| `kind`     | вид находки    | `fact`, `inference`, `conflict`, `gap` — см. [общие значения](#общие-значения)          |
| `text`     | string         | что найдено — как написали модели                                                       |
| `conflict` | ConflictSides \| null | у противоречия — что говорит каждая сторона; у других видов — `null`              |
| `ref`      | string \| null | где найдено, одной строкой — файл и строки («kromka-api/requests/permissions.py:18») или фрейм макета («Figma · Заявки / список»); текст пишет сервер, интерфейс показывает как есть. Не установлено — `null`: «не установлено» |
| `decision` | решение \| null | решение человека — см. [общие значения](#общие-значения)                               |

**ConflictSides** — две стороны противоречия, слева и справа на находке:

| Поле    | Тип    | Что                                                                                         |
| ------- | ------ | ------------------------------------------------------------------------------------------- |
| `by`    | string | чья левая сторона: `text` — «Ваш текст» (текст ввода), `docs` — «Документация» проекта        |
| `claim` | string | что говорит текст или документация                                                          |
| `found` | string | что на деле в коде или макете — правая сторона, «Код» или «Макет» по `source`                |

В `data-1.json` у g1: `scan.result.findings` — `statement`, `status` (`verified` — факт, `inferred` — вывод ИИ),
`evidence`; `unknowns` — пробелы; `documentation_conflicts` — противоречия документации и кода.

### Stream — поток

Группа, ставшая потоком на [«К потокам →»](#post-apicouncilsidresearchapprove--утвердить-исследование), и шесть её
шагов. Показывает его [шаг потока](#потоки-совета).

```json
{
  "id": "C",
  "title": "Индикатор сети",
  "idea": "Понятный индикатор: есть сеть или нет, сколько заявок ждёт отправки.",
  "steps": [
    { "step": "project", "state": "done", "note": "без прошлых решений", "text": null, "progress": [] },
    {
      "step": "questions",
      "state": "failed",
      "note": "сбор вопросов остановился",
      "text": "sol не справилась: превышено время молчания CLI (15 мин).",
      "progress": [
        {
          "phase": "question_discovery",
          "runs": [
            { "model": "sol", "state": "failed", "startedAt": null },
            { "model": "fable", "state": "done", "startedAt": null }
          ]
        },
        { "phase": "question_judge", "runs": [{ "model": "fable", "state": "waiting", "startedAt": null }] }
      ]
    },
    { "step": "options", "state": "idle", "note": "", "text": null, "progress": [] },
    { "step": "decisions", "state": "idle", "note": "", "text": null, "progress": [] },
    { "step": "outcomes", "state": "idle", "note": "", "text": null, "progress": [] },
    { "step": "notes", "state": "idle", "note": "", "text": null, "progress": [] }
  ]
}
```

| Поле    | Тип          | Что                                                                                         |
| ------- | ------------ | ------------------------------------------------------------------------------------------- |
| `id`    | string       | id потока — `id` группы, из которой он сделан: «C». Интерфейс показывает его в кружке на вкладке потока. Он же в адресе шага `/c/<совет>/streams/<id>/<шаг>` и в `streams` [совета](#streamsummary--поток-в-списке-советов) |
| `title` | string       | название — название группы, когда она стала потоком; правки групп после этого его не меняют (решение q-002) |
| `idea`  | string       | идея потока — идея группы, утверждённая на «Группах»: «Идея потока · утверждена в группах» на «Решениях проекта» |
| `steps` | StreamStep[] | все шесть [шагов](#streamstep--шаг-потока) по порядку: `project`, `questions`, `options`, `decisions`, `outcomes`, `notes` |

Шаги идут по порядку: пока шаг не готов, следующие за ним не начаты (`idle`). Текущий шаг потока — первый неготовый;
все готовы — `notes`. Он же `step` у потока в [списке советов](#streamsummary--поток-в-списке-советов).

В `data-1.json` у g1 это `streams[0]`: `group`, `idea` (`text`), шаги — `questions`, `proposals`, `choices`,
`analysis`, `outcomes`, `notes`, у каждого — `state` и `steps`.

### StreamStep — шаг потока

| Поле       | Тип            | Что                                                                                   |
| ---------- | -------------- | ------------------------------------------------------------------------------------- |
| `step`     | шаг            | `project`, `questions`, `options`, `decisions`, `outcomes`, `notes` — см. [общие значения](#общие-значения) |
| `state`    | состояние      | `done`, `running`, `waiting`, `failed`, `idle` — у шага `idle` значит «не начат»       |
| `note`     | string         | строка под шагом в цепочке: что на шаге — «учтены ADR-0003, ADR-0005», «отобрано 4 вопроса», «выбрано 1 из 4», «итоги утверждены · 6», «черновик ждёт вас», «сбор вопросов остановился». В ней числа и номера решений этого потока, поэтому её пишет сервер, а интерфейс показывает как есть — как `text` у [Activity](#activity--что-происходит-в-совете). У не начатого шага — пустая строка: интерфейс пишет «не начато» |
| `text`     | string \| null | строка на плашке под цепочкой, текст пишет сервер: у шага с ошибкой (`failed`) — почему он остановился («sol не справилась: превышено время молчания CLI (15 мин).»), у шага, где работают модели (`running`), — что они делают («sol собирает вопросы заново, ответ fable сохранён и не оплачивается второй раз.»); у остальных — `null` |
| `progress` | StepProgress[] | ход последнего запуска шага — [части](#stepprogress--часть-шага-потока) по порядку; модели на шаге не работали (не начат, «Решения проекта», «Документация») — пустой массив |

### StepProgress — часть шага потока

```json
{ "phase": "question_discovery", "runs": [{ "model": "sol", "state": "running", "startedAt": "2026-10-21T10:12:00Z" }] }
```

| Поле    | Тип                | Что                                                                                   |
| ------- | ------------------ | ------------------------------------------------------------------------------------- |
| `phase` | часть шага потока  | `question_discovery`, `question_judge` и другие — см. [общие значения](#общие-значения) |
| `runs`  | StepRun[]          | модели этой части по порядку: у `…_discovery` и `decision_analysis` — модели совета, у судей — судья совета. Судья, который не понадобился, — с `skipped`; судья, до которого не дошла очередь, — с `waiting` |

**StepRun** — работа модели на шаге потока: как [Run](#run--работа-модели), и ещё когда модель начала работать.

| Поле        | Тип            | Что                                                                                   |
| ----------- | -------------- | ------------------------------------------------------------------------------------- |
| `model`     | string         | `id` модели из [GET /api/models](#get-apimodels--модели-совета)                       |
| `state`     | работа модели  | `waiting`, `running`, `done`, `failed`, `skipped` — как у [Run](#run--работа-модели)    |
| `startedAt` | время \| null  | когда модель начала работать — только у `running`: «sol · думает 0:12» в «Ходе работы» считается от него; у остальных — `null` |

Показывает его [«Решения проекта»](#решения-проекта-потока).

```json
  "decisions": [
    {

      "decision": "Минимальная версия Android — 8.0 (API 26).",
      "question": "Какую минимальную версию Android поддерживаем?",
      "relation": "applicable",
      "status": "active",
      "supersededBy": null,
      "reason": "Фоновая отправка очереди через WorkManager опирается на API 26+.",
      "trail": [{ "issue": "ISS-0004", "path": "app/build.gradle", "commit": "a91c3e2" }],
      "selected": true
    },
    {
      "id": "ADR-0004",
      "decision": "Заявку закрывает только диспетчер.",
      "question": "Кто закрывает заявку?",
      "relation": "applicable",
      "status": "superseded",
      "supersededBy": "ADR-0008",

      "trail": [],

  ]

```

| Поле        | Тип                     | Что                                                                                    |
| ----------- | ----------------------- | -------------------------------------------------------------------------------------- |
| `catalog`   | DecisionCatalog \| null | каталог решений проекта — см. ниже; у совета нет проекта или у проекта нет папки документации (`docs` [проекта](#project--проект) пустой) — `null`, и прошлых решений нет |
| `decisions` | PastDecision[]          | [прошлые решения](#pastdecision--прошлое-решение), относящиеся к идее, в порядке сервера; нет — пустой массив |

**DecisionCatalog** — каталог решений проекта: папка документации, откуда «Решения проекта» берут прошлые решения.

| Поле     | Тип    | Что                                                            |
| -------- | ------ | -------------------------------------------------------------- |
| `path`   | string | путь к каталогу — папка документации проекта (`docs`)          |
| `total`  | number | сколько решений в каталоге всего                               |
| `traced` | number | сколько из них со следом в коде                                |

В `data-1.json` у g1: каталог — `questions.notes` («/repos/claude_notes»), прошлых решений нет
(`project_decisions` — `null`, в макете «решений в каталоге нет»).

### PastDecision — прошлое решение

| Поле           | Тип            | Что                                                                                 |
| -------------- | -------------- | ----------------------------------------------------------------------------------- |
| `id`           | string         | id решения в каталоге — «ADR-0003»; интерфейс показывает его как есть. Им же решение отмечают в [отборе](#post-apicouncilsidstreamsstreamidproject-decisionsapprove--отбор-прошлых-решений) |
| `decision`     | string         | что решено — как записано в каталоге                                                 |
| `question`     | string         | на какой вопрос решение отвечает: «вопрос: …»                                       |
| `relation`     | отношение      | `applicable`, `potential_conflict`, `uncertain` — см. [общие значения](#общие-значения) |
| `status`       | статус решения | `active`, `under_review`, `superseded` — см. [общие значения](#общие-значения)       |
| `supersededBy` | string \| null | каким решением заменено — у `superseded`: «заменено ADR-0008»; у остальных — `null`  |
| `reason`       | string         | почему совет счёл решение относящимся к идее — как написали модели                    |
| `trail`        | TrailEntry[]   | след решения в коде: задача, файл, коммит — «след в коде: ISS-0004 · app/build.gradle · a91c3e2»; следа нет — пустой массив, «следа в коде нет» |
| `selected`     | boolean        | галочка стоит, когда открывается отбор: шаг готов — решение учитывается; шаг ещё ждёт человека — совет предлагает его учесть |

**TrailEntry** — `{ "issue": "ISS-0004", "path": "app/build.gradle", "commit": "a91c3e2" }`: задача, файл и коммит —
как их пишет каталог; интерфейс показывает их как есть.

### Question — вопрос потока

Вопрос, который поток должен решить. Показывает его шаг [«Вопросы»](#вопросы-потока).

```json
{
  "id": "Q5",
  "text": "Может ли правка мастера, сделанная офлайн, менять статус заявки, если сервер уже выставил другой?",
  "source": "ai",
  "reason": "F4 требует, чтобы правки мастера не терялись, а ADR-0005 делает сервер единственным источником статуса",
  "proposals": [],
  "revisits": { "id": "ADR-0005", "decision": "Сервер — источник истины для статуса заявки." },
  "removed": false
}
```

| Поле        | Тип                 | Что                                                                                 |
| ----------- | ------------------- | ----------------------------------------------------------------------------------- |
| `id`        | string              | id вопроса в потоке; интерфейс показывает его как есть: «Q5». Он же в пути [правки вопроса](#patch-apicouncilsidstreamsstreamidquestionsquestionid--убрать-или-вернуть-вопрос) |
| `text`      | string              | вопрос — как его написали модели или человек                                         |
| `source`    | откуда вопрос       | `text`, `ai`, `user` — см. [общие значения](#общие-значения)                         |
| `reason`    | string \| null      | почему вопрос нужен — как написали модели: «почему: …»; у своего вопроса — `null`     |
| `proposals` | Fragment[]          | фрагменты-предложения из текста ввода, которые уже отвечают на вопрос: «В тексте уже есть ответ · предложение». На «Вариантах» они станут вариантами «из группы». [Fragment](#fragment--фрагмент) — тот же, что у нарезки; нет — пустой массив |
| `revisits`  | DecisionRef \| null | решение проекта, которое вопрос пересматривает: «Пересматривает решение проекта»; не пересматривает — `null` |
| `removed`   | boolean             | человек убрал вопрос: он остаётся в списке, а на следующие шаги не идёт               |

**DecisionRef** — решение проекта внутри другого объекта: `id` и `decision` — те же, что у
[PastDecision](#pastdecision--прошлое-решение).

```json
{ "id": "ADR-0005", "decision": "Сервер — источник истины для статуса заявки." }
```

В `data-1.json` у g1 это `streams[0].scope`: `id`, `text`, `source`, `reason`, `proposal_ids` (номера фрагментов:
`2` — F2), `revisits`. Убранных вопросов у g1 нет.

| ------------ | ----------------- | ---------------------------------------------------------------------------- |
| `option`     | `option` — `id` варианта из `options` | выбран этот вариант — совета или свой                         |
| `unresolved` | —                 | «Пока не решаю — передать как unresolved»: вопрос разберёт следующий шаг      |


```json
{ "kind": "unresolved" }
```

В `data-1.json` у g1 это `streams[0].proposals.options` (по вопросу: `proposals`, `verdict`, `reason`) и
`streams[0].choices`. У g1 судья не отбрасывал вариантов; `reason` по вопросу есть, только когда судья оставил
несколько вариантов (`verdict` — `alternatives`), а когда один (`recommended`) — макет пишет «Судья оставил один
вариант и рекомендует его: остальные противоречат тексту или находкам.». Выбор с текстом (`text`, `based_on`) — свой
вариант; без варианта (`proposal` — `null`) — `unresolved`.

### Option — вариант

| Поле          | Тип            | Что                                                                                   |
| ------------- | -------------- | ------------------------------------------------------------------------------------- |
| `id`          | string         | id варианта в потоке; интерфейс показывает его как есть: «P12». Он же в `choice`, в `basedOn` и в пути [правки своего варианта](#patch-apicouncilsidstreamsstreamidoptionsquestionidoptionid--правка-своего-варианта) |
| `text`        | string         | вариант — как его написали модели или человек                                          |
| `source`      | откуда вариант | `group`, `ai`, `user` — см. [общие значения](#общие-значения)                          |
| `recommended` | boolean        | судья рекомендует этот вариант: «рекомендация судьи»; у своего варианта — `false`       |
| `reason`      | string \| null | «почему» — как написали модели. У своего варианта — `null`, пока совет его не дописал: интерфейс пишет «Ваш вариант.» или «Ваша правка варианта P2.», как макет у g1 |
| `cost`        | string \| null | «цена» — чем вариант плох; нет — `null`, и строки «цена» нет                            |
| `dependsOn`   | string[]       | `id` вопросов потока, от решения которых вариант зависит: «зависит от Q2 · решён»; нет — пустой массив |
| `basedOn`     | string \| null | у своего варианта, сделанного правкой («Поправить»), — `id` варианта, который правили; у своего варианта с нуля и у вариантов совета — `null` |

«Почему», «цену» и зависимости своего варианта совет допишет сам — так обещает макет («Совет допишет «почему»,
«цену» и зависимости», «совет пересмотрит «почему» и «цену» под новую формулировку»); пока не дописал — `reason` и
`cost` — `null`, `dependsOn` — пустой.

### Project — проект

Репозитории и папка документации, которые совет берёт по проекту, а не вводит в каждом потоке. Проект выбирают на
«Вводе» совета.

```json
{
  "id": "p1",
  "name": "Кромка",
  "repos": ["kromka-api", "kromka-frontend", "kromka-android"],
  "docs": "kromka-api/docs/reasoning",
  "councilCount": 3
}
```

| Поле           | Тип      | Что                                                                                    |
| -------------- | -------- | -------------------------------------------------------------------------------------- |
| `id`           | string   | id проекта                                                                             |
| `name`         | string   | название проекта                                                                       |
| `repos`        | string[] | репозитории проекта — имена рабочих копий git из [GET /api/repos](#get-apirepos--рабочие-копии-git), по порядку, без повторов, не больше 10; может быть пустым |
| `docs`         | string   | папка документации — путь, куда этап «Задачи» выгружает заметки и откуда «Решения проекта» берут прошлые решения; пустая строка — папки нет |
| `councilCount` | number   | в скольких советах выбран проект — сколько советов с этим проектом в [списке советов](#get-apicouncils--список-советов); `0` — не используется |

### ProjectFields — поля проекта

То, что человек задаёт в окне проекта: тело [нового проекта](#post-apiprojects--новый-проект) и
[правки](#patch-apiprojectsid--сохранить-проект). Поля — те же, что у [Project](#project--проект).

```json
{
  "name": "Кромка",
  "repos": ["kromka-api", "kromka-frontend", "kromka-android"],
  "docs": "kromka-api/docs/reasoning"
}
```

| Поле    | Тип      | Что                                                                                         |
| ------- | -------- | ------------------------------------------------------------------------------------------- |
| `name`  | string   | название; не пустое. Пробелы по краям сервер убирает                                         |
| `repos` | string[] | репозитории — имена из [GET /api/repos](#get-apirepos--рабочие-копии-git), по порядку, не больше 10; может быть пустым. Повтор имени сервер считает одним репозиторием |
| `docs`  | string   | папка документации — путь от COUNCIL_REPOS; пустая строка — папки нет. Пробелы по краям сервер убирает |

Ошибки полей — общие для создания и правки:

| code             | HTTP | Когда                                                                           |
| ---------------- | ---- | ------------------------------------------------------------------------------- |
| `name_required`  | 422  | название пустое (или из одних пробелов)                                          |
| `too_many_repos` | 422  | репозиториев больше 10                                                          |
| `unknown_repo`   | 422  | репозитория нет в [GET /api/repos](#get-apirepos--рабочие-копии-git); при правке те, что уже были в проекте, оставить можно |

Окно проекта не даёт сохранить без названия и отметить больше 10, поэтому `name_required` и `too_many_repos` — на
случай чужого клиента. `unknown_repo` — рабочую копию убрали из COUNCIL_REPOS, пока окно было открыто: интерфейс
показывает текст ошибки по коду над кнопками окна и заново запрашивает список рабочих копий.

| `provider` | string  | через что модель работает: `codex`, `claude`                              |

| `online`   | boolean | подключена ли модель; `false` — в меню серая точка и метка «офлайн»       |

Меню группирует советы по проекту: проекты — в порядке их первого совета в списке, советы внутри проекта — в порядке

  списка. На карточке — метка состояния (`state`) и дорожка этапов (`stages`, жирная подпись — у `stage`);
- на карточке в обоих видах — проект, название, строки из `activity` (нет их — строка «Готово» с `summary`) и когда
  совет менялся (`updatedAt`). Проект и название ведут туда же, куда совет из меню; строка — на своё место в совете.

### POST /api/councils — новый совет

Создаёт черновик совета. Кто зовёт: «+ Новый совет» в шапке, «Новый совет» в меню слева, «+ Новый совет» в колонке
«Ввод» на Сводке — одно действие (`components/NewCouncil`). В коде — хук `useCreateCouncil()`. После ответа фронтенд
ставит совет из ответа первым в списке советов у себя, открывает «Ввод» нового совета — `/c/<id>/brief`, как в
макете, и заново запрашивает список советов и [список проектов](#get-apiprojects--проекты): у проекта нового совета
стало на совет больше (`councilCount`).

Тело — пустой объект:

```json
{}
```

Заголовок `Idempotency-Key` — ключ нового совета: строка, которую придумывает фронтенд. Если ответ не дошёл (оборвалась
связь, сбой), совет мог уже создаться, поэтому, пока совет не создан, каждая попытка — «Повторить» и новое нажатие
«Новый совет» — идёт с тем же ключом. Сервер, получив ключ, по которому уже создал совет, второй не создаёт и отвечает
этим советом, как в первый раз (`201`). Ключ сервер помнит не меньше суток. Фронтенд шлёт ключ всегда; без него каждый
запрос создаёт новый совет.

```http
POST /api/councils
Idempotency-Key: 6f1c2a9e0b7d4c3f8a5e2d1b0c9f7e6a
```

Новый совет — как в макете:

- без названия (`name` — пустая строка), на этапе `brief`, состояние `idle`, все шесть этапов — `idle`, потоков нет;
- проект — как у первого совета в [списке советов](#get-apicouncils--список-советов); советов нет — без проекта;
- модели и судья — те, что сервер ставит новому совету по умолчанию (в макете — sol и fable, судья fable); их меняют
  на «Вводе»;
- `activity` — как у любого черновика: «Ввод», `waiting`, «Допишите текст и нарежьте»; `summary` — «Черновик — текст
  не нарезан»;
- `updatedAt` — время создания;
- в списке советов встаёт первым.

Ответ `201` — созданный совет, [CouncilSummary](#councilsummary--совет-в-списке):

```json
{
  "council": {
    "id": "c8",
    "name": "",
    "project": { "id": "p4", "name": "gen_sdk_tooling" },
    "stage": "brief",
    "state": "idle",
    "stages": { "brief": "idle", "slices": "idle", "structure": "idle", "research": "idle", "streams": "idle", "tasks": "idle" },
    "streams": [],
    "participants": ["sol", "fable"],
    "judge": "fable",
    "updatedAt": "2026-10-20T16:42:00Z",
    "activity": [{ "stage": "brief", "stream": null, "step": null, "state": "waiting", "text": "Допишите текст и нарежьте" }],

```

Ошибки: только общие. Не вышло — интерфейс показывает текст ошибки по коду под шапкой страницы и «Повторить».

### «Ввод» совета

Этап «Ввод» — `/c/<id>/brief` (`features/brief`), как в макете. Слева — текст, справа — название, проект, модели и
судья совета.

- «Мысли в свободной форме» — текст ввода из [GET /api/councils/{id}/brief](#get-apicouncilsidbrief--текст-ввода).
  Под ним — сколько в тексте слов (считает фронтенд: куски текста между пробелами и переносами строк, как в макете) и
  «· сохранено».
- «Название» — `name` совета; пустое — в поле подсказка «Без названия».
- «Проект» — чипы проектов из [GET /api/projects](#get-apiprojects--проекты) в порядке списка и «Без проекта»;
  выбран проект совета. Под чипами — что даёт выбранный проект, как в макете: без проекта — «Без проекта: нет скана
  кода и выгрузки заметок.»; у проекта есть папка документации — «Репозитории (`repos.length`) подставятся в шаг
  «Репозиторий», заметки уйдут в `docs`.»; папки нет — «У проекта нет папки документации: потоки не выгрузить в
  заметки.» «Проекты →» ведёт на Проекты.
- «Совет» — модели из [GET /api/models](#get-apimodels--модели-совета) в порядке списка: имя, под ним провайдер и
  модель у него («codex/gpt-5.6-sol»), переключатель «в совете» — включён у моделей из `participants`. Не подключённая
  модель — «не подключена» красным, переключатель бледный и не переключается. Включённая модель встаёт в
  `participants` на своё место в списке моделей.
- «Судья» — подключённые модели; выбрана `judge`. Судья совета не подключён — не выбрана ни одна.
- «Нарезать →» — [нарезать текст](#post-apicouncilsidslicing--нарезать). Кнопка доступна всегда, как в макете, — и у
  черновика, и у совета, который ушёл дальше; недоступна, только пока нарезка запускается. Пока она запускается,
  «Ввод» не правится: текст и название — только для чтения, щелчки по проектам, моделям и судье не действуют.

Сохраняется всё само — кнопки «Сохранить» в макете нет, есть «· сохранено»:

- текст — [PUT /api/councils/{id}/brief](#put-apicouncilsidbrief--сохранить-текст-ввода), название —
  [PATCH /api/councils/{id}](#patch-apicouncilsid--правка-совета), когда человек перестал набирать (пауза 0,6 с);
  ушёл с экрана раньше — сразу;
- название, которое отличается от сохранённого только пробелами по краям, не отправляется: сервер их всё равно
  убирает. В поле название остаётся, как его набрали, — без пробелов по краям оно придёт, когда «Ввод» откроют снова;
- проект, модели и судья — [PATCH /api/councils/{id}](#patch-apicouncilsid--правка-совета) сразу по щелчку;
- запросы одного поля идут по одному: следующий — после ответа на предыдущий, с последним значением;
- «· сохранено» — когда текст на экране сохранён; пока он ждёт отправки или отправляется, подписи нет;
- не сохранилось — текст ошибки по коду в блоке, где меняли; у текста и названия — «Повторить», у проекта, моделей и
  судьи — без него (см. [ошибки полей](#councilfields--поля-совета)). Человек вернул в текст или название то, что уже
  сохранено, — ошибки больше нет: на экране то, что на сервере. Ошибка поля держится, пока это поле не поменяют снова:
  правка судьи не стирает ошибку моделей, и наоборот;
- ушли с «Ввода», а текст или название так и не сохранились, — «Ввод» того же совета, открытый снова, пока открыта
  вкладка браузера, показывает набранное и после паузы сохраняет его снова.

Текст и название «Ввод» запоминает, когда открылся совет: новый список советов их не меняет. Проект, модели и судья
берутся из списка советов, а пока правка идёт — как их выбрал человек.

### PATCH /api/councils/{id} — правка совета

Меняет название, проект, модели или судью совета. Кто зовёт: [«Ввод»](#ввод-совета) (`features/brief`). В коде — хук
`useUpdateCouncil()`.

Тело — [CouncilFields](#councilfields--поля-совета): только поля, которые меняют.

```http
PATCH /api/councils/c1
```

```json
{ "participants": ["sol"] }
```

У совета меняется и `updatedAt` — время правки. Название и проект совета видны везде, где он есть: в меню, шапке, на
Сводке; у проектов меняется `councilCount`.

Ответ `200` — совет после правки, [CouncilSummary](#councilsummary--совет-в-списке):

```json

    "id": "c1",
    "name": "Офлайн-режим заявок",
    "project": { "id": "p1", "name": "Кромка" },

    "state": "waiting",
    "stages": { "brief": "done", "slices": "done", "structure": "done", "research": "done", "streams": "waiting", "tasks": "idle" },

    "participants": ["sol"],
    "judge": "fable",
    "updatedAt": "2026-10-20T16:50:00Z",
    "activity": [
      { "stage": "streams", "stream": "C", "step": "questions", "state": "failed", "text": "Сбор вопросов остановился" },
```

и список проектов. Остальные поля из ответа он не берёт: правки разных полей идут одновременно, и ответ на раннюю,
пришедший позже, вернул бы старое значение поля, которое уже поменяла другая.

ошибки по коду в блоке, где меняли.

### GET /api/councils/{id}/brief — текст ввода

Кто зовёт: [«Ввод»](#ввод-совета) (`features/brief`) — каждый раз, когда открывается. В коде — хук `useCouncilBrief()`.
Пока текст грузится или не загрузился — на месте «Ввода» «Загружаем…» или текст ошибки и «Повторить».

С «Ввода» ушли, а его запросы ещё идут — сохранение текста
([PUT](#put-apicouncilsidbrief--сохранить-текст-ввода)), правки названия, проекта, моделей и судьи
([PATCH](#patch-apicouncilsid--правка-совета)), запуск нарезки ([POST](#post-apicouncilsidslicing--нарезать)), — и «Ввод»
того же совета открыли снова: фронтенд запрашивает текст, когда пришли ответы на все них (до тех пор — «Загружаем…»).
Иначе «Ввод» показал бы текст и название до правки и счёл бы их сохранёнными, а пока нарезка запускается — дал бы его
править.

Ответ `200` — [Brief](#brief--текст-ввода):

```json
{
  "brief": {
    "text": "Обеспечить получение списка сервисов Generation из существующих данных Scan и вывести его в /generation. В список входят сервисы read-in-full = 100%, partial или scanned, у которых в активном снимке есть хотя бы один эндпоинт. Генерация, раскладка ресурсов и отслеживание PR в эту задачу не входят."
  }
}
```

У нового совета текста нет — `text` пустой, как в макете.

Ошибки: `not_found` — совета нет; остальные общие.

### PUT /api/councils/{id}/brief — сохранить текст ввода

Заменяет текст ввода. Кто зовёт: автосохранение текста на [«Вводе»](#ввод-совета) и «Нарезать →» перед нарезкой.
В коде — хук `useSaveBrief()`.

Тело:

```json
{ "text": "Мастера на объектах часто без связи — подвал, промзона." }
```

`text` сервер хранит как есть, пустая строка — можно. У совета меняется `updatedAt`.

Ответ `200` — сохранённый текст, [Brief](#brief--текст-ввода):

```json
{ "brief": { "text": "Мастера на объектах часто без связи — подвал, промзона." } }
```

После ответа фронтенд заново запрашивает список советов: у совета новое время изменения.

Ошибки: `not_found` — совета нет; остальные общие. Интерфейс показывает текст ошибки по коду под текстом и
«Повторить».

### POST /api/councils/{id}/slicing — нарезать

Запускает нарезку текста ввода: модели совета режут текст на фрагменты. Кто зовёт: «Нарезать →» на
[«Вводе»](#ввод-совета). В коде — хук `useStartSlicing()`.

Перед запросом фронтенд сохраняет всё, что на «Вводе»: несохранённые текст
([PUT /api/councils/{id}/brief](#put-apicouncilsidbrief--сохранить-текст-ввода)) и название
([PATCH /api/councils/{id}](#patch-apicouncilsid--правка-совета)) уходят сразу, на правки проекта, моделей и судьи,
которые ещё идут, он дожидается ответа. Нарезается то, что на экране, и теми моделями, что на экране. Что-то не
сохранилось — нарезку не запускает: ошибка — в блоке, где меняли. Больше ничего не проверяется — как в макете: текст
может быть пустым, модели — любыми.

Тело — пустой объект:

```json
{}
```

Что меняется в совете — как в макете:

- `stages.brief` — `done`, `stages.slices` — `running`; остальные этапы не меняются;
- `stage` — `slices`, `state` — `running`;
- `activity` — пункт «Нарезки» в состоянии `running` с текстом, что делают модели («sol и fable режут текст»);
  остальные — по [общим правилам](#activity--что-происходит-в-совете);
- `summary` — «Нарезка — модели режут текст»;
- `updatedAt` — время запуска.

Нарезка уже идёт (`stages.slices` — `running`) — сервер её не перезапускает и отвечает советом как есть.

Ответ `200` — совет после запуска, [CouncilSummary](#councilsummary--совет-в-списке):

```json
{
  "council": {
    "id": "c5",
    "name": "",
    "project": { "id": "p3", "name": "Сайт" },
    "stage": "slices",
    "state": "running",
    "stages": { "brief": "done", "slices": "running", "structure": "idle", "research": "idle", "streams": "idle", "tasks": "idle" },
    "streams": [],
    "participants": ["sol", "fable"],
    "judge": "fable",
    "updatedAt": "2026-10-20T16:55:00Z",
    "activity": [{ "stage": "slices", "stream": null, "step": null, "state": "running", "text": "sol и fable режут текст" }],
    "summary": "Нарезка — модели режут текст"
  }
}
```

После ответа фронтенд сразу ставит совет из ответа на место старого в списке советов у себя, заново запрашивает
список и открывает [«Нарезку»](#нарезка-совета) — `/c/<id>/slices`, как в макете: там «ИИ работает» и ход работы
новой нарезки, фрагментов прошлой больше нет. Если человек, пока нарезка запускалась, ушёл
с «Ввода» на другой экран, «Нарезка» не открывается: он остаётся там, куда ушёл. Вернулся на «Ввод» того же совета,
пока нарезка ещё запускается, — до ответа на запуск там «Загружаем…» (см.
[GET /api/councils/{id}/brief](#get-apicouncilsidbrief--текст-ввода)): «Ввод» не правится, пока нарезка запускается.

Ошибки: `not_found` — совета нет; остальные общие. Интерфейс показывает текст ошибки по коду под «Нарезать →» и
«Повторить».

### «Нарезка» совета

Этап «Нарезка» — `/c/<id>/slices` (`features/slices`), как в макете. Что на нём — по `stages.slices` совета из
[списка советов](#get-apicouncils--список-советов) и [нарезке](#get-apicouncilsidslicing--нарезка) совета.

Модели режут текст (`stages.slices` — `running`):

- слева — метка «ИИ работает», «Совет режет текст на фрагменты», пояснение и серые строки на месте фрагментов;
- справа — «Ход работы» из `progress`: по строке на часть нарезки и состояние модели — точка, часть, модели через
  запятую, состояние («Нарезка · sol · работает…», «Разметка · sol, fable · ждёт»). Модели одной части в одном
  состоянии — одна строка, в разных — разные, как в макете. Точка: работает и готово — зелёная, ждёт и не понадобился —
  серая, не справилась — красная. Под строками — «Участники работают по отдельности, судья решает там, где они
  разошлись.»;
- пока нарезка идёт, фронтенд через 5 с после ответа на прошлый запрос нарезки заново запрашивает нарезку
  и [список советов](#get-apicouncils--список-советов) (список, который ещё не ответил, — не перезапрашивает): экран
  видит, как работают модели, и, когда `stages.slices` перестал быть `running`, показывает фрагменты.

Нарезка не идёт (`stages.slices` — любое, кроме `running`, как в макете: и готовая, и не начатая, и с ошибкой):

- «Фрагменты · 3» — сколько фрагментов, пояснение и карточки фрагментов из `fragments` по порядку: `id`, `text`, пять
  типов — выбран `label`;
- пометка справа от типов, как в макете: `label` не тот, что `councilLabel`, — «вы выбрали другой тип, у совета —
  «ограничение»»; иначе, если `decidedBy` — `judge`, — «модели разошлись — решил судья»;
- щелчок по другому типу — [сменить тип](#patch-apicouncilsidfragmentsfragmentid--сменить-тип-фрагмента) сразу, без
  кнопки «Сохранить» (её в макете нет). Пока ответа нет, на экране выбранный тип; запросы одного фрагмента идут по
  одному: следующий — после ответа на предыдущий, с последним выбором. Не сохранилось — текст ошибки по коду на
  карточке фрагмента, без «Повторить» (выбрать тип снова), тип — снова с сервера. Нарезка началась заново — ошибки
  и несохранённые смены прежних фрагментов забываются: у новых фрагментов те же `id`, но это другие фрагменты;
- справа — «Дальше · Разложить по группам», пояснение и «Предложить группы →» —
  [предложить группы](#post-apicouncilsidstructure--предложить-группы). Кнопка доступна всегда, как в макете,
  недоступна, только пока раскладка запускается.

### GET /api/councils/{id}/slicing — нарезка

Кто зовёт: [«Нарезка»](#нарезка-совета) (`features/slices`) — когда открывается, когда нарезка началась или кончилась
(`stages.slices` в списке советов стал или перестал быть `running`), после смены типа и, пока нарезка идёт, через 5 с
после ответа на прошлый запрос. В коде — хук `useCouncilSlicing()`. Пока нарезка грузится или не загрузилась — на месте
«Нарезки» «Загружаем…» или текст ошибки и «Повторить». Нарезка началась или кончилась — до ответа на новый запрос тоже
«Загружаем…»: нарезка, запрошенная раньше, — от другой нарезки (у новых фрагментов те же `id`, а «Предложить группы →»
не должна стать доступной, пока новые фрагменты не на экране).

Ответ `200` — [Slicing](#slicing--нарезка-совета):

```json
{
  "slicing": {
    "progress": [
      { "phase": "slice", "runs": [{ "model": "sol", "state": "done" }, { "model": "opus", "state": "done" }] },
      { "phase": "slice_judge", "runs": [{ "model": "opus", "state": "done" }] },
      { "phase": "label", "runs": [{ "model": "sol", "state": "done" }, { "model": "opus", "state": "done" }] },
      { "phase": "label_judge", "runs": [{ "model": "opus", "state": "done" }] }
    ],
    "fragments": [
      {
        "id": "F1",
        "text": "Обеспечить получение списка сервисов Generation из существующих данных Scan и вывести его в /generation.",
        "label": "idea",
        "councilLabel": "idea",
        "decidedBy": "agreed"
      },
      {
        "id": "F2",
        "text": "В список входят сервисы read-in-full = 100%, partial или scanned, у которых в активном снимке есть хотя бы один эндпоинт.",
        "label": "proposal",
        "councilLabel": "proposal",
        "decidedBy": "judge"
      }
    ]
  }
}
```

Модели закончили нарезку — `stages.slices` становится `waiting`: ИИ закончил, ход за человеком (см.
[состояние](#общие-значения)); в `fragments` — новые фрагменты, `label` у них — тот, что дал совет. Новая нарезка
([POST /api/councils/{id}/slicing](#post-apicouncilsidslicing--нарезать)) начинает ход работы заново, а фрагменты
прошлой нарезки пропадают: пока она идёт, `fragments` — пустой массив.

Ошибки: `not_found` — совета нет; остальные общие.

### PATCH /api/councils/{id}/fragments/{fragmentId} — сменить тип фрагмента

Кто зовёт: щелчок по типу фрагмента на [«Нарезке»](#нарезка-совета). В коде — хук `useFragmentLabels()`.

Тело:

```http
PATCH /api/councils/g1/fragments/F2
```

```json
{ "label": "constraint" }
```

`label` — [тип фрагмента](#общие-значения). У фрагмента меняется `label`, `councilLabel` остаётся; у совета —
`updatedAt`. Тип, выбранный человеком, — тот, с которым фрагмент идёт дальше: в группы и на следующие этапы; у этого
фрагмента в группах [раскладки](#structure--раскладка-совета-по-группам) `label` тоже новый.

Ответ `200` — фрагмент после правки, [Fragment](#fragment--фрагмент):

```json
{
  "fragment": {
    "id": "F2",
    "text": "В список входят сервисы read-in-full = 100%, partial или scanned, у которых в активном снимке есть хотя бы один эндпоинт.",
    "label": "constraint",
    "councilLabel": "proposal",
    "decidedBy": "judge"
  }
}
```

После ответа фронтенд сразу ставит фрагмент из ответа в нарезку у себя, заново запрашивает нарезку и список советов
(у совета новое время изменения).

Ошибки:

| code              | HTTP | Когда                                                                   |
| ----------------- | ---- | ----------------------------------------------------------------------- |
| `slicing_running` | 409  | нарезка идёт (`stages.slices` — `running`): фрагментов ещё нет           |
| `unknown_label`   | 422  | такого типа нет                                                         |
| `not_found`       | 404  | нет совета или у него нет такого фрагмента                              |

«Нарезка» показывает фрагменты, только когда нарезка не идёт, и даёт выбрать только пять типов, поэтому
`slicing_running` — на случай, когда нарезку запустили снова в другой вкладке, а `unknown_label` — чужого клиента.
Интерфейс показывает текст ошибки по коду на карточке фрагмента; на `slicing_running` заново запрашивает список
советов — и показывает «ИИ работает».

### POST /api/councils/{id}/structure — предложить группы

Раскладывает фрагменты по группам: совет группирует их вокруг идей, каждая группа станет потоком. Кто зовёт:
«Предложить группы →» на [«Нарезке»](#нарезка-совета). В коде — хук `useStartStructure()`.

Перед запросом фронтенд дожидается ответа на смены типа, которые ещё идут: группы раскладывают по типам, что на
экране. Что-то не сохранилось — раскладку не запускает: ошибка — на карточке фрагмента. Пока раскладка запускается,
щелчки по типам не действуют.

Тело — пустой объект:

```json
{}
```

Что меняется в совете — как в макете:

- `stages.slices` — `done`;
- раскладки ещё не было (`stages.structure` — `idle`) — она запускается: `stages.structure` — `running`, модели
  раскладывают фрагменты. В макете «Группы» сразу ждут вас, будто модели уже поработали; у нас группы приходят, когда
  модели закончат. Раскладка уже была или идёт — сервер её не перезапускает, `stages.structure` не меняется (так
  в макете);
- `stage` — первый этап после «Нарезки», который ещё не готов (все готовы — `tasks`), `state` — состояние этого этапа:
  после запуска раскладки — `structure` и `running`;
- `activity` — без пунктов «Ввода» и «Нарезки»; раскладка запустилась — пункт «Групп» в состоянии `running` с текстом,
  что делают модели («sol и fable раскладывают фрагменты по группам»); остальные — по
  [общим правилам](#activity--что-происходит-в-совете);
- `summary` — пишет сервер по новому состоянию; после запуска раскладки — «Группы — модели раскладывают фрагменты»;
- `updatedAt` — время запроса. «Нарезка» уже готова и раскладка не запускается — ничего не меняется, сервер отвечает
  советом как есть.

Ответ `200` — совет после запроса, [CouncilSummary](#councilsummary--совет-в-списке):

```json
{
  "council": {
    "id": "c2",
    "name": "Уведомления в Telegram",
    "project": { "id": "p2", "name": "looper" },
    "stage": "structure",
    "state": "running",
    "stages": { "brief": "done", "slices": "done", "structure": "running", "research": "idle", "streams": "idle", "tasks": "idle" },
    "streams": [],
    "participants": ["sol", "fable"],
    "judge": "fable",
    "updatedAt": "2026-10-20T17:05:00Z",
    "activity": [{ "stage": "structure", "stream": null, "step": null, "state": "running", "text": "sol и fable раскладывают фрагменты по группам" }],
    "summary": "Группы — модели раскладывают фрагменты"
  }
}
```

Раскладка запустилась — у [раскладки](#structure--раскладка-совета-по-группам) новый ход работы: модели совета
работают, судья ждёт; групп пока нет.

После ответа фронтенд сразу ставит совет из ответа на место старого в списке советов у себя, заново запрашивает
список и открывает [«Группы»](#группы-совета) — `/c/<id>/structure`, как в макете: там «ИИ работает» и ход раскладки.
Ушёл с «Нарезки», пока раскладка запускалась, — «Группы» не открываются: человек остаётся там, куда ушёл.

Ошибки:

| code              | HTTP | Когда                                                          |
| ----------------- | ---- | -------------------------------------------------------------- |
| `slicing_running` | 409  | нарезка идёт (`stages.slices` — `running`): фрагментов ещё нет  |
| `not_found`       | 404  | совета нет                                                     |

Интерфейс показывает текст ошибки по коду под «Дальше» и «Повторить»; на `slicing_running` заново запрашивает список
советов — и показывает «ИИ работает».

### «Группы» совета

Этап «Группы» — `/c/<id>/structure` (`features/structure`), как в макете. Что на нём — по `stages.structure` совета из
[списка советов](#get-apicouncils--список-советов) и [раскладке](#get-apicouncilsidstructure--раскладка) совета.

Модели раскладывают фрагменты (`stages.structure` — `running`) — так же, как «Нарезка», пока модели режут текст:

- слева — метка «ИИ работает», «Совет раскладывает фрагменты по группам», пояснение и серые строки на месте групп;
- справа — «Ход работы» из `progress`: «Раскладка · sol, fable · работает…», «Судья раскладки · fable · ждёт»; строки и
  точки — как у [«Нарезки»](#нарезка-совета);
- пока раскладка идёт, фронтенд через 5 с после ответа на прошлый запрос раскладки заново запрашивает раскладку и
  [список советов](#get-apicouncils--список-советов): когда `stages.structure` перестал быть `running`, экран
  показывает группы.

В макете такого вида у «Групп» нет: там группы появляются сразу, будто модели уже поработали.

Раскладка не идёт (`stages.structure` — любое, кроме `running`, как в макете: и готовая, и остановившаяся, и не
начатая):

- раскладка остановилась (`failed`) — сверху красная плашка: «Раскладка остановилась», `error` и «Повтор не платит
  второй раз за готовые ответы.», кнопка «Запустить снова» —
  [запустить раскладку снова](#post-apicouncilsidstructureretry--запустить-раскладку-снова). Под плашкой — группы,
  как в макете;
- «ИИ предлагает 3 группы» — сколько групп, и пояснение;
- карточки групп сеткой: буква (`id`), название, «Идея» и откуда она (`ideaBy`), идея (пустая — подсказка «ИИ
  восстановит идею по фрагментам — или впишите свою»), фрагменты — `id`, `text` и тип (`label`), связи (`links`)
  через « · », внизу — «Объединить с…», «Разделить», «Переименовать»;
- «Переименовать» или щелчок по названию — поле названия. Enter, Esc и щелчок мимо закрывают его, название
  сохраняется — [правка группы](#patch-apicouncilsidgroupsgroupid--правка-группы). Название, которое отличается от
  того, что на экране, только пробелами по краям, не отправляется;
- идея правится прямо на плашке и сохраняется сама, когда человек перестал набирать (пауза 0,6 с); ушёл с экрана
  раньше — сразу. Пока правка идёт и после неё — «вы», как в макете;
- «Объединить с…» — «Объединить с», другие группы («B · Конфликты при синхронизации») и «Отмена»; щелчок по группе —
  [объединить](#post-apicouncilsidgroupsgroupidmerge--объединить-группы);
- «Разделить» — у фрагментов группы галочки, подсказка («Отметьте фрагменты для новой группы», «Выбрано 1 из 4 —
  вынести в новую группу»), «Отмена» и «В новую группу» —
  [разделить](#post-apicouncilsidgroupsgroupidsplit--разделить-группу). «В новую группу» доступна, когда отмечен хотя
  бы один фрагмент, но не все, — так в макете. Разделили — у новой группы сразу открыто поле названия;
- открыто что-то одно и на одной карточке: открыли другое — прежнее закрывается (поле названия — с сохранением);
- внизу — тёмная плашка «Подтвердить группы», пояснение и «Подтвердить →» —
  [подтвердить группы](#post-apicouncilsidstructureconfirm--подтвердить-группы). Группы уже подтверждены
  (`stages.structure` — `done`) — на кнопке «К исследованию →», и она просто открывает «Исследование», как в макете.

Правки групп — как в макете, без кнопки «Сохранить», и в любом из этих состояний: у готовой раскладки, остановившейся и
не начатой. Запросы групп идут по одному, в порядке действий человека: следующий — после ответа на предыдущий, правка
шлёт то, что человек ввёл последним. Название и идея на экране меняются сразу; объединение и разделение — когда пришёл
ответ, а пока его нет, правки и кнопки групп не действуют. Не вышло — текст ошибки по коду на карточке группы, без
«Повторить» (сделать снова), на карточке — снова то, что на сервере; ошибка держится, пока с группой не сделают
что-то снова. Модели начали или кончили раскладку — группы другие, хоть `id` у них те же: несохранённые правки, ошибки
и открытое на карточках забываются, а объединение или разделение прежних групп, которое ещё ждёт очереди, не уходит.
Потоки, которые уже есть (их создаёт [«К потокам →»](#post-apicouncilsidresearchapprove--утвердить-исследование)),
правки групп не меняют (решение q-002).

### GET /api/councils/{id}/structure — раскладка

Кто зовёт: [«Группы»](#группы-совета) (`features/structure`) — когда открываются, когда раскладка началась или
кончилась (`stages.structure` в списке советов стал или перестал быть `running`), после правок групп и, пока раскладка
идёт, через 5 с после ответа на прошлый запрос; [«Исследование»](#исследование-совета) — буквы и названия групп, под
которыми стоят находки. В коде — хук `useCouncilStructure()`. Пока раскладка грузится или не
загрузилась — на месте «Групп» «Загружаем…» или текст ошибки и «Повторить». Раскладка началась или кончилась — до
ответа на новый запрос тоже «Загружаем…»: раскладка, запрошенная раньше, — от другой раскладки.

Ответ `200` — [Structure](#structure--раскладка-совета-по-группам):

```json
{
  "structure": {
    "progress": [
      { "phase": "structure", "runs": [{ "model": "sol", "state": "done" }, { "model": "fable", "state": "failed" }] },
      { "phase": "structure_judge", "runs": [{ "model": "fable", "state": "waiting" }] }
    ],
    "groups": [
      {
        "id": "C",
        "title": "Индикатор сети",
        "idea": "Понятный индикатор: есть сеть или нет, сколько заявок ждёт отправки.",
        "ideaBy": "text",
        "fragments": [
          {
            "id": "F7",
            "text": "Понятный индикатор: есть сеть или нет, сколько заявок ждёт отправки.",
            "label": "idea",
            "councilLabel": "idea",
            "decidedBy": "agreed"
          }
        ],
        "links": [{ "kind": "related", "group": "A", "fragment": null }]
      }
    ],
    "error": "fable не справилась: прерван, сервер остановился."
  }
}
```

Модели закончили раскладку — `stages.structure` становится `waiting` (ИИ закончил, ход за человеком), в `groups` —
группы. Пока раскладка идёт, `groups` — пустой массив. Тип фрагмента, который человек сменил на «Нарезке», приходит и
в группах.

Ошибки: `not_found` — совета нет; остальные общие.

### PATCH /api/councils/{id}/groups/{groupId} — правка группы

Меняет название или идею группы. Кто зовёт: поле названия и идея на карточке группы ([«Группы»](#группы-совета)).
В коде — хук `useGroupEdits()`, `change()`.

Тело — [GroupFields](#groupfields--поля-группы): только поля, которые меняют.

```http
PATCH /api/councils/c1/groups/A
```

```json
{ "title": "Очередь заявок офлайн" }
```

У группы меняется поле; поменяли идею — `ideaBy` становится `user`. У совета меняется `updatedAt`. Состояния этапов
правка не меняет — так в макете.

Ответ `200` — группа после правки, [Group](#group--группа):

```json
{
  "group": {
    "id": "A",
    "title": "Очередь заявок офлайн",
    "idea": "Заявка копится на телефоне и уходит сама, когда сеть вернётся.",
    "ideaBy": "text",
    "fragments": [
      {
        "id": "F1",
        "text": "Мастера на объектах часто без связи — подвал, промзона.",
        "label": "constraint",
        "councilLabel": "constraint",
        "decidedBy": "agreed"
      }
    ],
    "links": [{ "kind": "required_by", "group": "B", "fragment": null }]
  }

```

После ответа фронтенд сразу ставит группу из ответа в раскладку у себя и заново запрашивает раскладку и список советов
(у совета новое время изменения).

Ошибки:

| code                | HTTP | Когда                                                                       |
| ------------------- | ---- | --------------------------------------------------------------------------- |
| `structure_running` | 409  | раскладка идёт (`stages.structure` — `running`): групп ещё нет              |
| `not_found`         | 404  | нет совета или у него нет такой группы                                      |

«Группы» правят группы, только когда раскладка не идёт, поэтому `structure_running` — на случай, когда раскладку
запустили снова в другой вкладке: интерфейс заново запрашивает список советов и показывает «ИИ работает». `not_found`
— группу успели объединить с другой: интерфейс заново запрашивает раскладку. Текст ошибки по коду — на карточке группы.

### POST /api/councils/{id}/groups/{groupId}/merge — объединить группы

Объединяет группу `groupId` с группой `into`. Кто зовёт: группа в «Объединить с» на карточке группы `groupId`. В коде —
хук `useGroupEdits()`, `merge()`.

Тело:

```json
{ "into": "C" }
```

Что меняется — как в макете:

- группа `groupId` пропадает, её фрагменты встают в конец группы `into`; фрагменты, которые уже есть в `into`, не
  повторяются (в макете повторяются);
- название — у `into`; идея — у `into`, а нет её — у `groupId`, вместе с `ideaBy`;
- у `into` — связь `merged` с `groupId`. Связи `groupId` переходят к `into`, ссылки других групп на `groupId` теперь
  ведут на `into`, связей группы с самой собой нет. В макете связи `into` просто заменяются строкой «объединена с
  группой …», а ссылки на пропавшую группу остаются;
- у совета — `updatedAt`; состояния этапов не меняются.

Ответ `200` — раскладка после объединения, [Structure](#structure--раскладка-совета-по-группам): меняются несколько
групп и их связи.

```json
{
  "structure": {
    "progress": [
      { "phase": "structure", "runs": [{ "model": "sol", "state": "done" }, { "model": "fable", "state": "done" }] },
      { "phase": "structure_judge", "runs": [{ "model": "fable", "state": "skipped" }] }
    ],
    "groups": [
      {
        "id": "C",
        "title": "Индикатор сети",
        "idea": "Понятный индикатор: есть сеть или нет, сколько заявок ждёт отправки.",
        "ideaBy": "text",
        "fragments": [],
        "links": [
          { "kind": "required_by", "group": "B", "fragment": null },
          { "kind": "merged", "group": "A", "fragment": null }
        ]
      }
    ],
    "error": null
  }
}
```

(Фрагменты групп в примере опущены.) После ответа фронтенд сразу ставит раскладку из ответа на место прежней у себя и
заново запрашивает раскладку и список советов.

Ошибки:

| code                | HTTP | Когда                                                              |
| ------------------- | ---- | ------------------------------------------------------------------ |
| `structure_running` | 409  | раскладка идёт: групп ещё нет                                      |
| `bad_merge`         | 422  | `into` — та же группа, что `groupId`                               |
| `not_found`         | 404  | нет совета или одной из групп                                      |

«Объединить с» предлагает только другие группы, поэтому `bad_merge` — на случай чужого клиента. Интерфейс показывает
текст ошибки по коду на карточке группы `groupId`; на `structure_running` заново запрашивает список советов, на
`bad_merge` и `not_found` — раскладку.

### POST /api/councils/{id}/groups/{groupId}/split — разделить группу

Выносит отмеченные фрагменты группы `groupId` в новую группу. Кто зовёт: «В новую группу» на карточке группы. В коде —
хук `useGroupEdits()`, `split()`.

Тело:

```json
{ "fragmentIds": ["F1"], "title": "Новая группа" }
```

| Поле          | Тип      | Что                                                                                     |
| ------------- | -------- | --------------------------------------------------------------------------------------- |
| `fragmentIds` | string[] | какие фрагменты группы вынести — хотя бы один, но не все                                  |
| `title`       | string   | название новой группы: интерфейс шлёт «Новая группа» на языке интерфейса, как в макете, и сразу открывает поле названия; пробелы по краям сервер убирает |

Что меняется — как в макете:

- новая группа встаёт сразу после `groupId`: `id` выбирает сервер (в макете — первая свободная буква), название —
  `title`, идеи нет (`idea` — `""`, `ideaBy` — `ai`: её восстановит ИИ), фрагменты — `fragmentIds` в порядке группы,
  связь — `split` с `groupId`;
- у `groupId` остаются другие фрагменты; связи `shared` про фрагменты, которых в ней больше нет, пропадают;
- у совета — `updatedAt`; состояния этапов не меняются.

Ответ `200` — раскладка после разделения, [Structure](#structure--раскладка-совета-по-группам), как у
[объединения](#post-apicouncilsidgroupsgroupidmerge--объединить-группы). Новая группа — та, которой не было до
запроса: у неё фронтенд открывает поле названия.

После ответа фронтенд сразу ставит раскладку из ответа на место прежней у себя и заново запрашивает раскладку и список
советов.

Ошибки:

| code                | HTTP | Когда                                                                         |
| ------------------- | ---- | ----------------------------------------------------------------------------- |
| `structure_running` | 409  | раскладка идёт: групп ещё нет                                                 |
| `bad_split`         | 422  | не отмечено ни одного фрагмента, отмечены все или фрагмента нет в группе      |
| `not_found`         | 404  | нет совета или группы                                                         |

«Разделить» даёт вынести только часть фрагментов группы, поэтому `bad_split` — на случай, когда группу успели поменять
в другой вкладке. Интерфейс показывает текст ошибки по коду на карточке, «Разделить» остаётся открытым; на
`structure_running` заново запрашивает список советов, на `bad_split` и `not_found` — раскладку.

### POST /api/councils/{id}/structure/confirm — подтвердить группы

Подтверждает группы: дальше совет исследует код и макет под все группы, каждая группа станет потоком. Кто зовёт:
«Подтвердить →» на [«Группах»](#группы-совета). В коде — хук `useConfirmStructure()`.

Перед запросом фронтенд отправляет то, что человек ввёл и что ещё не ушло (поле названия, идея), и дожидается ответа
на правки групп, которые ещё идут: подтверждаются группы, что на экране. Что-то не сохранилось — не подтверждает:
ошибка — на карточке группы. Пока группы подтверждаются, правки групп не действуют.

Тело — пустой объект:

```json
{}
```

Что меняется в совете — как в макете:

- `stages.structure` — `done`; «Исследование» ещё не начато (`stages.research` — `idle`) — оно ждёт человека
  (`waiting`): начать или пропустить исследование. Начато — не меняется;
- `stage` — первый этап после «Групп», который ещё не готов (все готовы — `tasks`), `state` — состояние этого этапа:
  обычно `research` и `waiting`;
- `activity` — без пунктов «Групп»; «Исследование» стало ждать — его пункт `waiting` (текст пишет сервер); уже начато
  и не утверждено — текст его пункта сервер пишет заново: группы подтверждены, исследование можно утвердить, когда оно
  готово; остальные — по [общим правилам](#activity--что-происходит-в-совете);
- `summary` — пишет сервер по новому состоянию;
- `updatedAt` — время запроса. Группы уже подтверждены (`stages.structure` — `done`) — ничего не меняется, сервер
  отвечает советом как есть.

Подтвердить можно и остановившуюся раскладку, и не начатую — так в макете; нельзя, только пока модели раскладывают
фрагменты.

Ответ `200` — совет после подтверждения, [CouncilSummary](#councilsummary--совет-в-списке):

```json

    "id": "c3",
    "name": "Импорт справочников из 1С",
    "project": { "id": "p1", "name": "Кромка" },
    "stage": "research",
    "state": "waiting",
    "stages": { "brief": "done", "slices": "done", "structure": "done", "research": "waiting", "streams": "idle", "tasks": "idle" },
    "streams": [],
    "participants": ["sol", "fable"],
    "judge": "fable",
    "updatedAt": "2026-10-20T17:20:00Z",
    "activity": [{ "stage": "research", "stream": null, "step": null, "state": "waiting", "text": "Начните или пропустите оба исследования — потом группы станут потоками." }],
    "summary": "Исследование ждёт запуска"
  }
}
```

После ответа фронтенд сразу ставит совет из ответа на место старого в списке советов у себя, заново запрашивает список
и открывает «Исследование» — `/c/<id>/research`, как в макете. Ушёл с «Групп», пока они подтверждались, —
«Исследование» не открывается.

Ошибки:

| code                | HTTP | Когда                                                     |
| ------------------- | ---- | --------------------------------------------------------- |
| `structure_running` | 409  | раскладка идёт: групп ещё нет                             |
| `not_found`         | 404  | совета нет                                                |

Интерфейс показывает текст ошибки по коду под плашкой «Подтвердить группы» и «Повторить»; на `structure_running`
заново запрашивает список советов — и показывает «ИИ работает».

### POST /api/councils/{id}/structure/retry — запустить раскладку снова

Запускает снова раскладку, которая остановилась. Кто зовёт: «Запустить снова» на красной плашке «Раскладка
остановилась» ([«Группы»](#группы-совета)). В коде — хук `useRetryStructure()`.

Перед запросом фронтенд отправляет то, что человек ввёл и что ещё не ушло (поле названия, идея), и дожидается ответа
на правки групп, которые ещё идут: запуск не обгоняет их, а они — его. Пока раскладка запускается, правки групп и
«Подтвердить →» не действуют; пока объединение или разделение ждёт ответа и пока группы подтверждаются, недоступна
«Запустить снова».

Тело — пустой объект:

```json
{}
```

Что меняется:

- модели, которые уже ответили, заново не работают: их ответы сохранены и второй раз не оплачиваются — «Повтор не
  платит второй раз за готовые ответы.», так в макете. В `progress` у них — `done`, остальные модели раскладки работают
  заново, судья ждёт своей очереди;
- `stages.structure` — `running`, `stage` — `structure`, `state` — `running`;
- `activity` — вместо пункта «Групп» с ошибкой — пункт `running` с тем, что делают модели («sol и fable раскладывают
  фрагменты по группам»), как после [«Предложить группы»](#post-apicouncilsidstructure--предложить-группы);
- `summary` — «Группы — модели раскладывают фрагменты»; `updatedAt` — время запуска;
- у раскладки — `error` `null`, `groups` пустые, пока модели работают.

Раскладка не остановилась (`stages.structure` — не `failed`) — сервер её не перезапускает и отвечает советом как есть.
В макете «Запустить снова» сразу делает «Группы» ждущими вас, будто модели уже поработали; у нас группы приходят, когда
модели закончат.

Ответ `200` — совет после запуска, [CouncilSummary](#councilsummary--совет-в-списке), как у
[«Предложить группы»](#post-apicouncilsidstructure--предложить-группы).

После ответа фронтенд сразу ставит совет из ответа на место старого в списке советов у себя и заново запрашивает список:
«Группы» показывают «ИИ работает» и ход новой раскладки.

Ошибки: `not_found` — совета нет; остальные общие. Интерфейс показывает текст ошибки по коду под плашкой и «Повторить».

### «Исследование» совета

Этап «Исследование» — `/c/<id>/research` (`features/research`), как в макете. Что на нём — по
[исследованию](#get-apicouncilsidresearch--исследование) совета; названия групп — из
[раскладки](#get-apicouncilsidstructure--раскладка).

Сверху — два блока рядом: «Исследование кода» и «Исследование макета». У каждого — «Код · необязательно» или «Макет ·
необязательно», метка состояния (`state`: «не начато», «идёт», «готово», «пропущено»), заголовок и пояснение; дальше —
по состоянию, как в макете:

- **не начато** (`setup`). У кода — «Репозитории проекта»: галочки на `repos`, отмечены те, у которых `selected`;
  справа — «репозиторий проекта» или, у не отмеченных сервером, «не нужен этой идее?»; под ними — «Сканируйте только
  свои, доверенные репозитории: модели читают код.» У макета — поле «Ссылка на Figma» с `link` и пояснение. Внизу —
  «Пропустить» ([пропустить](#post-apicouncilsidresearchkindskip--пропустить-исследование)) и «Начать исследование»
  ([начать](#post-apicouncilsidresearchcodestart--начать-исследование-кода)). Галочки и ссылку человек меняет на
  экране, на сервер они уходят с «Начать исследование»; ушёл с экрана раньше — при возврате снова то, что на сервере.
  «Начать исследование» у кода доступна, когда отмечен хотя бы один репозиторий, у макета — когда в ссылке есть
  `figma.com`, — так в макете;
- **идёт** (`running`). По строке на модель из `runs`: точка, модель, `text`, состояние модели («работает…»). Внизу —
  у кода «2 репоз. · ~2 мин» (сколько отмечено в `repos`, `minutes`), у макета «4 фрейма · ~1 мин» (`frames`,
  `minutes`), и «Остановить» ([остановить](#post-apicouncilsidresearchkindstop--остановить-исследование));
- **готово** (`done`). Строка: у кода — первый репозиторий из `scanned` («gen_sdk_tooling · коммит 7440e1a · файлов:
  304 · проходов: 1»), у макета — `link`; справа — сколько находок этого исследования («35 находок»). Внизу —
  «Результаты — ниже» и «Изменить и перезапустить»
  ([вернуть к настройке](#post-apicouncilsidresearchkindreset--вернуть-исследование-к-настройке));
- **пропущено** (`skipped`). Пунктирная плашка: у кода — «Пропущено — потоки пойдут без карты кода: вопросы и задачи
  не будут привязаны к файлам.», у макета — «Пропущено — потоки пойдут без макета.». Внизу — «Вернуть исследование»
  ([вернуть к настройке](#post-apicouncilsidresearchkindreset--вернуть-исследование-к-настройке)).

Пока действие с блоком ждёт ответа, кнопки, галочки и ссылка этого блока не действуют, а пока исследование
утверждается — обоих блоков и решения по находкам; не вышло — текст ошибки по коду под блоком и «Повторить» (запуск
повторяется с тем, что отмечено сейчас).

Есть находки (`findings` не пустой) — «Результаты · Что пойдёт в потоки» и пояснение, как в макете:

- чипы-фильтры: «Все», «Ждут вас», «Факты», «Выводы», «Противоречия», «Пробелы» — у каждого число находок; фильтр
  выбирает человек на экране, по умолчанию — «Все»;
- находки по группам: буква и название группы (`group`; группы нет в раскладке — только буква), сколько находок
  группы показано. Группы — в порядке раскладки;
- на находке: вид («факт», «вывод ИИ», «противоречие», «пробел»), откуда («код», «макет»), справа — что с ней будет
  по `decision` (см. [общие значения](#общие-значения)); `text`; у противоречия — две стороны: «Ваш текст» или
  «Документация» (`conflict.by`) и «Код» или «Макет» (`source`), выбранная сторона — в тёмной рамке; внизу — `ref` и
  кнопки решения. Выбранное решение — тёмная кнопка. Находка, которая ждёт решения, — на жёлтом фоне;
- щелчок по кнопке — [решение по находке](#patch-apicouncilsidresearchfindingsfindingid--решение-по-находке) сразу,
  без «Сохранить» (в макете её нет). Пока ответа нет, на экране выбранное; запросы одной находки идут по одному, с
  последним выбором. Не вышло — текст ошибки по коду на находке, без «Повторить» (выбрать снова), решение — снова
  с сервера.

Код исследован (`code.state` — `done`) и есть сценарии или покрытие — под находками два блока рядом:

- «Потоки в коде · 4» и пояснение: сценарии из `flows` — название, точка входа (`entry`), шаги с номерами и `id`
  находок через запятую. Первый сценарий открыт, остальные свёрнуты — «5 шагов»; щелчок по названию открывает или
  сворачивает («свернуть»). Исследование кода вернули к настройке и запустили снова — сценарии другие: снова открыт
  первый;
- «Покрытие · 9 проверено · 2 частично» и пояснение: `coverage` по порядку — метка («проверено», «частично», «вне
  задачи»), часть кода и `reason`.

Внизу — тёмная плашка «Утвердить исследование», пояснение и «К потокам →»
([утвердить исследование](#post-apicouncilsidresearchapprove--утвердить-исследование)). Пояснение — как в макете:

- оба исследования готовы или пропущены, находок, которые ждут решения, нет и группы подтверждены (`stages.structure` —
  `done`), — «Код: карта готова · макет: пропущен. Каждая группа станет потоком.» (готово — «карта готова», пропущено
  — «пропущен»);
- то же, но группы ещё не подтверждены, — «Подтвердите группы — потом они станут потоками.» (в макете такого пояснения
  нет: правило — из решения q-002);
- оба готовы или пропущены, но находки ждут решения, — «2 находки ждут вашего решения — выводы и противоречия.»;
- хоть одно идёт — «Дождитесь окончания исследования.»;
- иначе — «Начните или пропустите оба исследования — потом группы станут потоками.»

«К потокам →» доступна только в первом случае и недоступна, пока исследование утверждается. В макете кнопка от групп
не зависит; у нас она недоступна, пока группы не подтверждены (решение q-002). Исследование уже утверждено
(`stages.research` — `done`) — кнопка просто открывает «Потоки» (туда же, куда совет на «Потоках» из меню), как
«К исследованию →» на «Группах».

Пока хоть одно исследование идёт или в списке советов `stages.research` — `running`, фронтенд через 5 с после ответа
на прошлый запрос исследования заново запрашивает исследование и [список советов](#get-apicouncils--список-советов)
(список, который ещё не ответил, — не перезапрашивает): экран видит, как работают модели, и, когда они кончили, —
находки; меню, Сводка и вкладки этапов догоняют исследование, даже если список запросили за миг до того, как модели
кончили.

В макете исследование «как будто» идёт 2,4 с и само становится готовым; у нас — пока модели не закончат.

**Как исследование меняет совет.** Состояние этапа `stages.research` сервер ведёт по исследованиям:

- хотя бы одно исследование идёт — `running`; пункт «Исследования» в `activity` — `running`, с тем, что делают модели
  («sol и fable исследуют код»);
- иначе, пока исследование не утверждено, — `waiting`: человек начинает, пропускает, решает находки, утверждает;
  пункт «Исследования» — `waiting` (текст пишет сервер: что нужно от человека);
- утверждено («К потокам →») — `done`; пункта «Исследования» в `activity` нет.

Действие с исследованием — начать, пропустить, остановить, вернуть к настройке — снимает утверждение: `stages.research`
снова `running` или `waiting`, пока человек не утвердит исследование заново. Потоки, которые уже есть, оно не трогает.
Решения по находкам состояния этапов не меняют — как правки групп. После каждого действия у совета: `stage` — первый
этап, который ещё не готов (все готовы — `tasks`), `state` — состояние этого этапа, `summary` — пишет сервер,
`updatedAt` — время действия. Начать исследование можно и до того, как группы подтверждены, — в макете ограничений нет;
утвердить — только после (решение q-002).

### GET /api/councils/{id}/research — исследование

Кто зовёт: [«Исследование»](#исследование-совета) (`features/research`) — когда открывается, после действий с
исследованием и решений по находкам и, пока исследование идёт, через 5 с после ответа на прошлый запрос. В коде — хук
`useCouncilResearch()`. Пока исследование грузится или не загрузилось — на месте «Исследования» «Загружаем…» или текст
ошибки и «Повторить».

Ответ `200` — [Research](#research--исследование-совета):

```json
{
  "research": {
    "code": {
      "state": "running",
      "repos": [
        { "name": "kromka-api", "selected": true },
        { "name": "kromka-frontend", "selected": true },
        { "name": "kromka-android", "selected": false }
      ],
      "runs": [
        { "model": "sol", "state": "running", "text": "проход 1 · читает kromka-api" },
        { "model": "fable", "state": "running", "text": "проход 1 · читает kromka-frontend" }
      ],
      "minutes": 2,
      "scanned": [],
      "rounds": 0
    },
    "design": { "state": "setup", "link": "", "runs": [], "minutes": 0, "frames": 0 },
    "findings": [],
    "flows": [],
    "coverage": []
  }
}
```

Исследования ещё не было — оба `setup`; у кода `repos` — репозитории проекта, `selected` — у тех, что совет считает
нужными идее. Модели закончили — исследование `done`, его находки — в `findings`: у выводов ИИ и противоречий
`decision` — `null` (ждут вас), у пробелов — `question`.

Ошибки: `not_found` — совета нет; остальные общие.

### POST /api/councils/{id}/research/code/start — начать исследование кода

Кто зовёт: «Начать исследование» в блоке «Исследование кода». В коде — хук `useResearchAction()`.

Тело — какие репозитории исследовать: отмеченные на экране, в порядке `repos`.

```json
{ "repos": ["kromka-api", "kromka-frontend"] }
```

Исследование кода — `running`: модели совета читают репозитории; у `repos` `selected` — у этих. Совет — см. [«Как
исследование меняет совет»](#исследование-совета).

Исследование не в настройке (`code.state` — не `setup`) — сервер его не запускает и отвечает исследованием как есть.

Ответ `200` — исследование после запуска, [Research](#research--исследование-совета) целиком (`{ "research": … }`).
После ответа фронтенд сразу ставит его на место прежнего у себя и заново запрашивает исследование и список советов.

Ошибки:

| code           | HTTP | Когда                                                                      |
| -------------- | ---- | -------------------------------------------------------------------------- |
| `no_repos`     | 422  | `repos` пустой                                                             |
| `unknown_repo` | 422  | репозитория нет в `repos` проекта совета                                   |
| `not_found`    | 404  | совета нет                                                                 |

«Начать исследование» недоступна, пока не отмечен ни один репозиторий, поэтому `no_repos` — на случай чужого клиента.
`unknown_repo` — репозиторий убрали из проекта, пока «Исследование» было открыто: интерфейс показывает текст ошибки по
коду под блоком и заново запрашивает исследование — с новым списком репозиториев.

### POST /api/councils/{id}/research/design/start — начать исследование макета

Кто зовёт: «Начать исследование» в блоке «Исследование макета». В коде — хук `useResearchAction()`.

Тело — ссылка на Figma, как её вставил человек; пробелы по краям сервер убирает.

```json
{ "link": "https://www.figma.com/design/kromka-app?node-id=12-480" }
```

Исследование макета — `running`, `link` — эта ссылка, `frames` — сколько фреймов по ней. Не в настройке — сервер
отвечает исследованием как есть. Ответ и что делает фронтенд — как у
[исследования кода](#post-apicouncilsidresearchcodestart--начать-исследование-кода).

Ошибки:

| code        | HTTP | Когда                                      |
| ----------- | ---- | ------------------------------------------ |
| `bad_link`  | 422  | в ссылке нет `figma.com`                    |
| `not_found` | 404  | совета нет                                 |

«Начать исследование» недоступна, пока в ссылке нет `figma.com`, поэтому `bad_link` — на случай чужого клиента.

### POST /api/councils/{id}/research/{kind}/skip — пропустить исследование

`kind` — `code` или `design`. Кто зовёт: «Пропустить» в блоке. В коде — хук `useResearchAction()`. Тело — `{}`.

Ошибки: `not_found` — совета нет или `kind` не `code` и не `design`; остальные общие.

### POST /api/councils/{id}/research/{kind}/stop — остановить исследование

Кто зовёт: «Остановить» в блоке, пока исследование идёт. В коде — хук `useResearchAction()`. Тело — `{}`.

Модели останавливаются, сделанное ими не сохраняется; исследование — снова `setup`, с теми же репозиториями или ссылкой,
что при запуске. Не идёт — сервер его не трогает и отвечает исследованием как есть (оно успело кончиться — находки
остаются). Ответ и что делает фронтенд — как у [начала](#post-apicouncilsidresearchcodestart--начать-исследование-кода).

Ошибки: `not_found` — совета нет или `kind` не `code` и не `design`; остальные общие.

### POST /api/councils/{id}/research/{kind}/reset — вернуть исследование к настройке

Кто зовёт: «Изменить и перезапустить» у готового исследования и «Вернуть исследование» у пропущенного. В коде — хук
`useResearchAction()`. Тело — `{}`.

Исследование — снова `setup`, как в макете: у кода — с репозиториями, которые брали в прошлый раз, у макета — с прошлой
ссылкой; их можно поменять и начать заново. Находки этого исследования пропадают, у кода — и `flows`, и `coverage`.
Готово или пропущено — только тогда; иначе сервер отвечает исследованием как есть. Ответ и что делает фронтенд — как у
[начала](#post-apicouncilsidresearchcodestart--начать-исследование-кода).

Ошибки: `not_found` — совета нет или `kind` не `code` и не `design`; остальные общие.

### PATCH /api/councils/{id}/research/findings/{findingId} — решение по находке

Кто зовёт: кнопки решения на находке ([«Исследование»](#исследование-совета)). В коде — хук `useFindingDecisions()`.

```http
PATCH /api/councils/c6/research/findings/R6
```

```json
{ "decision": "question" }
```

`decision` — [решение](#общие-значения), которое подходит виду находки. У совета меняется `updatedAt`; состояния этапов
не меняются.

Ответ `200` — находка после решения, [Finding](#finding--находка):

```json
{
  "finding": {
```

После ответа фронтенд сразу ставит находку из ответа в исследование у себя и заново запрашивает исследование и список

Ошибки:

| code           | HTTP | Когда                                                                   |
| -------------- | ---- | ----------------------------------------------------------------------- |
| `bad_decision` | 422  | решение не подходит виду находки: у факта, `accept` у противоречия и так далее |
| `not_found`    | 404  | нет совета или у него нет такой находки                                 |

Находка даёт выбрать только свои решения, поэтому `bad_decision` — на случай чужого клиента. `not_found` — находки уже
нет: исследование вернули к настройке в другой вкладке. Интерфейс показывает текст ошибки по коду на находке; на
`not_found` заново запрашивает исследование.

### POST /api/councils/{id}/research/approve — утвердить исследование

Кто зовёт: «К потокам →» на тёмной плашке «Утвердить исследование». В коде — хук `useApproveResearch()`.

Перед запросом фронтенд дожидается ответа на решения по находкам, которые ещё идут: утверждается то, что на экране.
Что-то не сохранилось — не утверждает: ошибка — на находке.

Тело — пустой объект:

```json
{}
```

Утвердить можно, когда оба исследования готовы или пропущены и находок, которые ждут решения, нет, — как в макете, — и
группы подтверждены (`stages.structure` — `done`, решение q-002). Что меняется в совете:

- `stages.research` — `done`;
- потоки — как в макете: «Потоки» ещё не начаты (`stages.streams` — `idle`) — каждая группа
  [раскладки](#structure--раскладка-совета-по-группам) становится потоком, в порядке групп: `id` потока — `id` группы,
  `step` — `project`; `stages.streams` — `waiting`. Потоки уже есть — не меняются; правки групп после этого их тоже
  не меняют (решение q-002);
- `stage` — первый этап, который ещё не готов (обычно `streams`), `state` — состояние этого этапа;
- `activity` — без пункта «Исследования»; у новых потоков — пункты по
  [общим правилам](#activity--что-происходит-в-совете);
- `summary` — пишет сервер; `updatedAt` — время запроса. Уже утверждено — ничего не меняется, сервер отвечает советом
  как есть.

Ответ `200` — совет после утверждения, [CouncilSummary](#councilsummary--совет-в-списке):

```json
{
  "council": {
    "id": "c6",
    "name": "Экспорт отчётов в PDF",
    "project": { "id": "p2", "name": "looper" },
    "stage": "streams",
    "state": "waiting",
    "stages": { "brief": "done", "slices": "done", "structure": "done", "research": "done", "streams": "waiting", "tasks": "idle" },
    "streams": [{ "id": "A", "step": "project" }, { "id": "B", "step": "project" }, { "id": "C", "step": "project" }],
    "participants": ["sol", "fable"],
    "judge": "fable",
    "updatedAt": "2026-10-21T10:05:00Z",
    "activity": [
      { "stage": "streams", "stream": "A", "step": "project", "state": "waiting", "text": "Отметьте прошлые решения проекта" },
      { "stage": "streams", "stream": "B", "step": "project", "state": "waiting", "text": "Отметьте прошлые решения проекта" },
      { "stage": "streams", "stream": "C", "step": "project", "state": "waiting", "text": "Отметьте прошлые решения проекта" }

    "summary": "Потоки ждут вас"

```

После ответа фронтенд сразу ставит совет из ответа на место старого в списке советов у себя, заново запрашивает список
и открывает «Потоки» — первый поток на его шаге (`/c/<id>/streams/<поток>/<шаг>`), как в макете. Ушёл с «Исследования»,
пока оно утверждалось, — «Потоки» не открываются.

Ошибки:

| code                 | HTTP | Когда                                                                        |
| -------------------- | ---- | ---------------------------------------------------------------------------- |
| `research_not_ready` | 409  | исследование не начато, идёт, находки ждут решения или группы не подтверждены |
| `not_found`          | 404  | совета нет                                                                   |

«К потокам →» доступна, только когда исследование готово и группы подтверждены, поэтому `research_not_ready` — на
случай, когда исследование поменяли в другой вкладке: интерфейс показывает текст ошибки по коду под плашкой и заново
запрашивает исследование и список советов. Остальные — текст ошибки по коду под плашкой и «Повторить».

### «Потоки» совета

Шаг потока — `/c/<id>/streams/<поток>/<шаг>` (`features/stream`), как в макете. Общее для всех шагов — по
[потокам совета](#get-apicouncilsidstreams--потоки-совета):

- **вкладки потоков**: буква (`id`) в кружке, название (`title`), под ним точка и текущий шаг потока (первый
  неготовый) с его состоянием — «Варианты · ждёт вас», «Вопросы · ошибка»; все шаги готовы — «готово». Цвет точки —
  как у состояния: готово и ИИ работает — зелёная, ждёт вас — жёлтая, ошибка — красная. Открытая вкладка — тёмная,
  буква на ней — белая. Вкладка ведёт на текущий шаг потока, как в макете;
- слева — **«Цепочка · поток A»**: шесть шагов по порядку — кружок, название шага и строка шага (`note`). Кружок:
  готов — «✓» на тёмном; ждёт вас — номер на жёлтом; ошибка — на красном; ИИ работает — на зелёном; не начат — номер
  на светлом в серой рамке. Строка шага, который ждёт вас, — жёлтым, с ошибкой — красным; у не начатого — «не начато»,
  и весь шаг бледный. Открытый шаг — на серой подложке. Щелчок по шагу открывает его; не начатый не открывается — как в
  макете;
- под цепочкой — **плашка состояния открытого шага**: ждёт вас — жёлтая «Ход за вами» и «ИИ закончил шаг
  «Варианты» — решение за вами.»; ошибка — красная «Сбой · Вопросы», `text` и «Запустить снова»
  ([запустить шаг снова](#post-apicouncilsidstreamsstreamidretry--запустить-шаг-снова)); ИИ работает — зелёная «ИИ
  работает» и `text`. Шаг готов или не начат — плашки нет;
- под ней — **«Ход работы · последний запуск»** из `progress` открытого шага, вид «grouped» макета: по части шага —
  подпись части, справа её состояние, под ней модели «таблетками». Состояние части: хоть одна модель не справилась —
  «сбой» (красным); хоть одна работает — «думает»; хоть одна ждёт — «ждёт»; все не понадобились — «не понадобился»;
  иначе — «готово» (зелёным). Модель: готово — на зелёном, не справилась — на красном, работает — на белом в зелёной
  рамке, точка пульсирует, «sol · думает 0:12» — сколько она работает, от `startedAt`, каждую секунду; ждёт и не
  понадобился — в пунктирной рамке. «Ход работы» показывается у шага с ошибкой и у шага, где работают модели: в макете —
  у шага с ошибкой, в том числе пока он запускается снова; у «Вариантов» — всегда, когда модели на них уже работали,
  как в макете. В макете «ждёт» выглядит как «не понадобился» — у нас это разные состояния;
- справа — **карточка шага**: подпись капсом — название шага и чей ход (ждёт вас — «Варианты · вы», ошибка и ИИ
  работает — «Вопросы · ИИ»), название шага, пояснение шага (тексты — из макета); дальше — содержимое шага и внизу его
  переходы: у каждого шага свои, см. шаг. Шаг не начат — вместо содержимого пунктирная плашка «Шаг откроется, когда
  пройдены предыдущие.», как в макете.

Потока из адреса у совета нет — экран открывает первый поток на его текущем шаге (так макет поступает с незнакомым
потоком); потоков нет совсем — «Исследование». Пока потоки грузятся или не загрузились — под вкладками этапов
«Загружаем…» или текст ошибки и «Повторить».

Пока хоть на одном шаге потоков совета работают модели (`running`) или в списке советов `stages.streams` — `running`,
фронтенд через 5 с после ответа на прошлый запрос потоков заново запрашивает потоки и
[список советов](#get-apicouncils--список-советов) (список, который ещё не ответил, — не перезапрашивает): экран видит,
как работают модели, а когда они кончили — что шаг ждёт вас или остановился.

**Как шаги потоков меняют совет.** После каждого действия с потоком у совета:

- `streams` — у потока его текущий шаг (`step`);
- `activity` — по пункту на шаг потока с ошибкой, ждущий вас и где работает ИИ, по
  [общим правилам](#activity--что-происходит-в-совете): «Отметьте прошлые решения проекта», «sol и fable собирают
  вопросы», «Сбор вопросов остановился»;
- `stages.streams` — по шагам потоков: все шаги всех потоков готовы — `done`; иначе есть шаг, который ждёт человека, —
  `waiting` (так у совета c1 в макете: поток C с ошибкой, A и B ждут вас — «Потоки» ждут вас); иначе работают модели —
  `running`; иначе — `failed`;
- `stage` — первый этап, который ещё не готов (все готовы — `tasks`), `state` — состояние этого этапа; `summary` — пишет
  сервер; `updatedAt` — время действия.

### POST /api/councils/{id}/streams/{streamId}/retry — запустить шаг снова

Запускает снова шаг потока, который остановился (`failed`). Кто зовёт: «Запустить снова» на красной плашке «Сбой ·
Вопросы» под цепочкой ([шаг потока](#потоки-совета)). В коде — хук `useRetryStream()`. Пока запуск ждёт ответа, кнопка
недоступна, а переход и правки шага не действуют: [«Утвердить вопросы»](#post-apicouncilsidstreamsstreamidquestionsapprove--утвердить-вопросы),
«Убрать» / «Вернуть» и «Добавить» не уходят вместе с запуском; на «Вариантах» — выбор, свой вариант, правка и
[«Утвердить выбор»](#post-apicouncilsidstreamsstreamidoptionsapprove--утвердить-выбор). И наоборот: пока вопросы
утверждаются, свой вопрос добавляется или «Убрать» / «Вернуть» ждут ответа (на «Вариантах» — выбор, свой вариант,
правка или «Утвердить выбор»), «Запустить снова» недоступна.

Тело — пустой объект:

```json
{}
```

Что меняется — как в макете («ответ fable сохранён и не оплачивается второй раз»):

- модели, которые уже ответили, заново не работают: их ответы сохранены и второй раз не оплачиваются; в `progress` у
  них — `done`. Шаг идёт снова с первой части, где ответили не все: её модели работают заново (`running`, `startedAt` —
  время запуска), модели следующих частей ждут своей очереди (`waiting`). Остановились модели совета — они работают
  заново, судья ждёт; модели совета ответили, остановился судья — заново работает судья;
- шаг — `running`, `text` — что делают модели («sol собирает вопросы заново, ответ fable сохранён и не оплачивается
  второй раз.»), `note` — пишет сервер;
- запускают снова «Варианты» — `run` в [вариантах потока](#get-apicouncilsidstreamsstreamidoptions--варианты-потока)
  на 1 больше;
- совет — см. [«Как шаги потоков меняют совет»](#потоки-совета): вместо пункта шага с ошибкой — пункт `running`.

Шага с ошибкой в потоке нет — сервер ничего не запускает и отвечает потоком как есть. В макете шаг после «Запустить
снова» так и остаётся «ИИ работает»; у нас он кончится, когда модели закончат: ждёт вас или снова остановится.

### «Решения проекта» потока

Шаг «Решения проекта» — `/c/<id>/streams/<поток>/project` (`features/projectDecisions`), как в макете. В карточке шага
— по [прошлым решениям потока](#get-apicouncilsidstreamsstreamidproject-decisions--прошлые-решения-потока):

- жёлтая плашка «Идея потока · утверждена в группах» и `idea` потока;
- шаг готов (`done`) — серая плашка: «Учитываются: ADR-0003, ADR-0005» — решения с `selected`, по порядку; ни одного —
  «Прошлые решения не учитываются.»; справа — «Изменить отбор»: открывает отбор, как в макете;
- шаг ждёт вас или нажали «Изменить отбор» — отбор:
  - другие потоки совета, которые ещё не выгружены в заметки (их «Документация» не готова), — «Потоки B, C не
    выгружены в заметки — их решения здесь не учтены.» жёлтым; таких нет — строки нет. В макете — все другие потоки
    совета: у макета ни один другой поток не выгружен;
  - строка каталога: есть прошлые решения — «В каталоге решений: 14, со следом в коде: 9 · kromka-api/docs/reasoning»
    (`total`, `traced`, `path`); нет — «Каталог /repos/claude_notes · прошлых решений, относящихся к идее, нет», как у
    g1 в макете; каталога нет (`catalog` — `null`) — строки нет;
  - прошлые решения карточками с галочкой: `id`, метка `relation`, метка `status` (у `active` её нет), `decision`,
    «вопрос: …», `reason`, след в коде. Галочка стоит у решений с `selected`; отмеченная карточка — в тёмной рамке.
    Галочки человек меняет на экране, на сервер они уходят с переходом к вопросам; ушёл с шага раньше — при возврате
    снова как на сервере (как отметки репозиториев на «Исследовании»);
  - внизу — «Без прошлых решений → к вопросам» и справа «Отмечено 2 из 5» и «Учитывать отмеченные → к вопросам» —
    [отбор прошлых решений](#post-apicouncilsidstreamsstreamidproject-decisionsapprove--отбор-прошлых-решений): без
    решений или с отмеченными. Обе доступны всегда, как в макете; пока отбор уходит, кнопки и галочки не действуют.
    Отбор принят — открываются «Вопросы» потока (`/c/<id>/streams/<поток>/questions`); ушёл с шага, пока отбор уходил, —
    не открываются. Не вышло — текст ошибки по коду под кнопками и «Повторить» (с тем, что отмечено сейчас).

Пока прошлые решения грузятся или не загрузились — под идеей потока «Загружаем…» или текст ошибки и «Повторить».

отбора. В коде — хук `useProjectDecisions()`.

Ответ `200` — [ProjectDecisions](#projectdecisions--прошлые-решения-потока):

```json
{
  "projectDecisions": {
    "catalog": { "path": "/repos/claude_notes", "total": 0, "traced": 0 },
    "decisions": []
  }
}
```

Ошибки: `not_found` — нет совета или у него нет такого потока; остальные общие.

### POST /api/councils/{id}/streams/{streamId}/project-decisions/approve — отбор прошлых решений

Кто зовёт: «Учитывать отмеченные → к вопросам» (тело — отмеченные решения) и «Без прошлых решений → к вопросам» (тело —
пустой список) на [«Решениях проекта»](#решения-проекта-потока). В коде — хук `useApproveProjectDecisions()`.

Тело — `id` решений, которые учитывать, в порядке списка:

```json
{ "selected": ["ADR-0003", "ADR-0005"] }
```

Что меняется:

- у прошлых решений потока `selected` — у этих, у остальных — `false`. Их учтут вопросы, варианты и решения потока:
  решённое не переспросят, а противоречие покажут (пояснение шага в макете);
- «Решения проекта» ждали вас — шаг готов (`done`, `note` — что учтено: «учтены ADR-0003, ADR-0005», «без прошлых
  решений»), и модели начинают собирать вопросы: «Вопросы» — `running`, `text` — что делают модели, в `progress` —
  модели совета работают, судья ждёт. В макете «Вопросы» сразу ждут вас, будто модели уже поработали; у нас — когда
  модели закончат;
- «Решения проекта» уже были готовы («Изменить отбор») — меняется только отбор и `note` шага; остальные шаги не
  меняются, как в макете;
- совет — см. [«Как шаги потоков меняют совет»](#потоки-совета).

Ответ `200` — поток после отбора, [Stream](#stream--поток), как у
[«Запустить снова»](#post-apicouncilsidstreamsstreamidretry--запустить-шаг-снова).

После ответа фронтенд сразу ставит поток из ответа на место прежнего у себя, заново запрашивает потоки, прошлые решения
и список советов и открывает «Вопросы» потока.

Ошибки:

| code               | HTTP | Когда                                                                     |
| ------------------ | ---- | ------------------------------------------------------------------------- |
| `unknown_decision` | 422  | в `selected` есть решение, которого нет у потока в прошлых решениях         |
| `not_found`        | 404  | нет совета или у него нет такого потока                                     |

Отбор даёт отметить только решения из списка, поэтому `unknown_decision` — на случай, когда список устарел (каталог
поменялся, пока шаг был открыт): интерфейс показывает текст ошибки по коду под кнопками и заново запрашивает прошлые
решения. Пока они не пришли, галочки и кнопки не действуют; не пришли — под кнопками ошибка запроса, и «Повторить»
запрашивает их снова. Остальные — текст ошибки по коду под кнопками и «Повторить».

### «Вопросы» потока

Шаг «Вопросы» — `/c/<id>/streams/<поток>/questions` (`features/questions`), как в макете. В карточке шага — по
[вопросам потока](#get-apicouncilsidstreamsstreamidquestions--вопросы-потока):

- вопросы по порядку, строками: `id`, текст, под ним метка источника («из текста», «ИИ», «вы») и «почему: …»
  (`reason`; нет — только метка). Справа — «Убрать»
  ([убрать или вернуть](#patch-apicouncilsidstreamsstreamidquestionsquestionid--убрать-или-вернуть-вопрос)); убранный
  вопрос остаётся в списке бледным и зачёркнутым, кнопка у него — «Вернуть», как в макете;
- вопрос пересматривает решение проекта (`revisits`) — красная плашка: «Пересматривает решение проекта» и id решения,
  текст решения зачёркнут, под ним пояснение из макета: «Пока вопрос открыт, ADR-0005 — under_review: другие потоки на
  него не опираются. Когда вопрос решат, новый ADR заменит его — ADR-0005 станет superseded.» Статус решения в каталоге
  этот шаг не меняет: пояснение говорит, что с решением будет дальше;
- в тексте уже есть ответ (`proposals`) — зелёная плашка: «В тексте уже есть ответ · предложение» (их несколько — «В
  тексте уже есть ответы · предложения: 2»), фрагменты — id и «текст», внизу — «Станет вариантом «из группы» на
  следующем шаге — вопрос можно оставить, чтобы сравнить с другими.»;
- под вопросами — поле «Свой вопрос…» и «Добавить» ([свой вопрос](#post-apicouncilsidstreamsstreamidquestions--свой-вопрос)):
  пустой (или из одних пробелов) вопрос не добавляется, как в макете; добавленный встаёт в конец списка, поле
  очищается. Не вышло — текст ошибки по коду под полем, набранное остаётся;
- шаг ждёт вас или остановился — внизу «Утвердить вопросы → к вариантам»
  ([утвердить вопросы](#post-apicouncilsidstreamsstreamidquestionsapprove--утвердить-вопросы)); шаг готов — низа нет,
  как в макете.

Убирать, возвращать и добавлять вопросы можно, пока шаг ждёт вас, остановился или уже готов — как в макете; пока шаг
с ошибкой запускают снова, правки не действуют. Щелчок по «Убрать» / «Вернуть» сразу уходит на сервер; у каждого
вопроса своя очередь запросов, на сервере остаётся последний выбор; ошибка — на строке вопроса. Пока на шаге работают модели (ИИ работает), на месте вопросов — серые строки, а поля
«Свой вопрос…» и «Утвердить» нет: вопросы появятся, когда модели закончат. Шаг сменил состояние (модели закончили или
остановились, шаг запустили снова) — вопросы запрашиваются заново.

Пока вопросы грузятся или не загрузились — в карточке шага «Загружаем…» или текст ошибки и «Повторить».

### GET /api/councils/{id}/streams/{streamId}/questions — вопросы потока

Кто зовёт: [«Вопросы»](#вопросы-потока) (`features/questions`) — когда открываются, когда шаг сменил состояние и после
правок вопросов. В коде — хук `useStreamQuestions()`.

Ответ `200` — вопросы потока по порядку, [Question](#question--вопрос-потока): сначала те, что собрали модели (в порядке
судьи), потом свои — в порядке добавления. Убранные — на своих местах.

```json
{
  "questions": [
    {
      "id": "Q1",
      "text": "Какие сервисы входят в список Generation?",
      "source": "text",
      "reason": "F2 отвечает именно на этот вопрос: предлагает правило отбора, но сам вопрос в материале не записан.",
      "proposals": [
        {
          "id": "F2",
          "text": "В список входят сервисы read-in-full = 100%, partial или scanned, у которых в активном снимке есть хотя бы один эндпоинт.",
          "label": "proposal",
          "councilLabel": "proposal",
          "decidedBy": "judge"
        }
      ],
      "revisits": null,
      "removed": false
    },
    {
      "id": "Q10",
      "text": "Что показывает страница /generation, если получить список сервисов от backend не удалось?",
      "source": "user",
      "reason": null,
      "proposals": [],
      "revisits": null,
      "removed": false
    }
  ]
}
```

Шаг не начат — пустой массив. Шаг остановился — вопросы моделей, которые успели ответить: в макете «fable успела
собрать 5 вопросов — их можно взять без перезапуска». Пока модели собирают вопросы, интерфейс вопросы не показывает.

Ошибки: `not_found` — нет совета или у него нет такого потока; остальные общие.

### PATCH /api/councils/{id}/streams/{streamId}/questions/{questionId} — убрать или вернуть вопрос

Кто зовёт: «Убрать» и «Вернуть» на строке вопроса ([«Вопросы»](#вопросы-потока)). В коде — хук `useQuestionRemovals()`.

```http
PATCH /api/councils/c1/streams/C/questions/Q4
```

```json
{ "removed": true }
```

Что меняется: у вопроса — `removed`; у совета — `updatedAt`. Шаги потока не меняются, в том числе у готового шага — как
в макете. Убранный вопрос не идёт на следующие шаги: в макете «Варианты» его не показывают.

Ответ `200` — вопрос после правки, [Question](#question--вопрос-потока):

```json
{
  "question": {
    "id": "Q4",
    "text": "Нужна ли отправка очереди в фоне при закрытом приложении?",
    "source": "ai",
    "reason": "Android 8+ ограничивает фоновые задачи",
    "proposals": [],
    "revisits": null,
    "removed": true
  }
}
```

После ответа фронтенд сразу ставит вопрос из ответа на место прежнего у себя и заново запрашивает вопросы и список
советов (у совета новое время изменения).

Ошибки:

| code                  | HTTP | Когда                                                                    |
| --------------------- | ---- | ------------------------------------------------------------------------ |
| `questions_not_ready` | 409  | шаг «Вопросы» не начат или на нём работают модели                         |
| `not_found`           | 404  | нет совета, у него нет такого потока или у потока нет такого вопроса       |

Пока модели работают, вопросы не показываются, поэтому `questions_not_ready` — на случай, когда шаг запустили снова в
другой вкладке: интерфейс показывает текст ошибки по коду на строке вопроса и заново запрашивает потоки и вопросы. На
`not_found` — текст ошибки на строке и заново запрашивает вопросы.

### POST /api/councils/{id}/streams/{streamId}/questions — свой вопрос

Кто зовёт: «Добавить» под вопросами ([«Вопросы»](#вопросы-потока)). В коде — хук `useAddQuestion()`.

Тело — текст вопроса:

```json
{ "text": "Что показывает страница /generation, если получить список сервисов от backend не удалось?" }
```

Заголовок `Idempotency-Key` — ключ нового вопроса, как у [нового совета](#post-apicouncils--новый-совет): пока вопрос
не создан, все попытки с тем же текстом — с одним ключом (пробелы по краям не в счёт: сервер их убирает); текст
поправили после неудачной попытки — это другой вопрос, и он идёт с новым ключом; вопрос создан — следующий вопрос идёт
с новым ключом. Сервер, получив ключ, по
которому уже создал вопрос, второй не создаёт и отвечает этим вопросом (`201`), даже если текст в теле другой. Ключ
сервер помнит не меньше суток.

```http
POST /api/councils/g1/streams/A/questions
Idempotency-Key: 9d2b7c1e4f0a46b8a3c5e7d9f1b2a4c6
```

Новый вопрос — как в макете: текст без пробелов по краям, `id` — «Q» и номер на один больше самого большого номера
вопросов потока, `source` — `user`, `reason` — `null`, `proposals` — пустой, `revisits` — `null`, `removed` — `false`;
встаёт в конец списка. У совета — `updatedAt`. Шаги потока не меняются, как и у правки вопроса; свой вопрос идёт на
следующие шаги вместе с остальными.

Ответ `201` — созданный вопрос, [Question](#question--вопрос-потока):

```json
{
  "question": {
    "id": "Q13",
    "text": "Что показывает страница /generation, если получить список сервисов от backend не удалось?",
    "source": "user",
    "reason": null,
    "proposals": [],
    "revisits": null,
    "removed": false
  }
}
```

После ответа фронтенд ставит вопрос из ответа в конец списка у себя, очищает поле и заново запрашивает вопросы и список
советов.

Ошибки:

| code                  | HTTP | Когда                                                     |
| --------------------- | ---- | --------------------------------------------------------- |
| `text_required`       | 422  | текст пустой (или из одних пробелов)                       |
| `questions_not_ready` | 409  | шаг «Вопросы» не начат или на нём работают модели          |
| `not_found`           | 404  | нет совета или у него нет такого потока                    |

Пустой вопрос интерфейс не отправляет, поэтому `text_required` — на случай чужого клиента. Интерфейс показывает текст
ошибки по коду под полем; повторить — снова «Добавить». На `questions_not_ready` заново запрашивает потоки и вопросы.

### POST /api/councils/{id}/streams/{streamId}/questions/approve — утвердить вопросы

Кто зовёт: «Утвердить вопросы → к вариантам» внизу [«Вопросов»](#вопросы-потока). В коде — хук `useApproveQuestions()`.
Сначала интерфейс дожидается ответов на «Убрать» и «Вернуть», которые ещё идут, — утверждается то, что на экране; одно
из них не сохранилось — не утверждает. Пока свой вопрос добавляется, «Добавить» и «Утвердить» не действуют; пока
вопросы утверждаются — не действуют ещё «Убрать» / «Вернуть» и «Запустить снова» на плашке шага с ошибкой. Пока шаг
запускают снова, «Утвердить», «Убрать» / «Вернуть» и «Добавить» не действуют: запросы не уходят вместе.

Тело — пустой объект:

```json
{}
```

Что меняется:

- шаг ждёт вас или остановился — «Вопросы» готовы (`done`, `text` — `null`, `note` — сколько вопросов не убрано:
  «отобрано 4 вопроса»); на следующие шаги идут неубранные вопросы. Шаг остановился — идут вопросы моделей, которые
  успели ответить: в макете «их можно взять без перезапуска»; ход последнего запуска остаётся как был. Модели начинают
  искать варианты: «Варианты» — `running`, `text` — что делают модели, в `progress` — модели совета работают, судья
  ждёт; `run` в [вариантах потока](#get-apicouncilsidstreamsstreamidoptions--варианты-потока) — `1`. В макете
  «Варианты» сразу ждут вас, будто модели уже поработали; у нас — когда модели закончат;
- шаг уже готов — сервер ничего не меняет и отвечает потоком как есть;
- совет — см. [«Как шаги потоков меняют совет»](#потоки-совета).

Ответ `200` — поток после утверждения, [Stream](#stream--поток), как у
[«Запустить снова»](#post-apicouncilsidstreamsstreamidretry--запустить-шаг-снова).

После ответа фронтенд сразу ставит поток из ответа на место прежнего у себя, заново запрашивает потоки, вопросы и
список советов и открывает «Варианты» потока (`/c/<id>/streams/<поток>/options`); ушёл с шага, пока вопросы
утверждались, — не открывает.

Ошибки:

| code                  | HTTP | Когда                                                     |
| --------------------- | ---- | --------------------------------------------------------- |
| `questions_not_ready` | 409  | шаг «Вопросы» не начат или на нём работают модели          |
| `not_found`           | 404  | нет совета или у него нет такого потока                    |

«Утвердить» есть, только когда шаг ждёт вас или остановился, поэтому `questions_not_ready` — на случай, когда шаг
запустили снова в другой вкладке: интерфейс показывает текст ошибки по коду под кнопкой и заново запрашивает потоки и
вопросы. Остальные — текст ошибки по коду под кнопкой и «Повторить».

### «Варианты» потока

Шаг «Варианты» — `/c/<id>/streams/<поток>/options` (`features/options`), как в макете. В карточке шага — по
[вариантам потока](#get-apicouncilsidstreamsstreamidoptions--варианты-потока), вопросы по одному:

- сверху — чипы вопросов (`id`): точка зелёная — по вопросу есть выбор, жёлтая — нет; открытый вопрос — в тёмной
  рамке, щелчок по чипу открывает вопрос. Справа — «готово 2 из 4» (сколько вопросов с выбором из всех) и «←» / «→» —
  предыдущий и следующий вопрос. Открывается первый вопрос без выбора; выбор есть у всех — первый (в макете у потока B
  открыт Q3 — первый без выбора);
- открытый вопрос: `id`, метка источника («из текста», «ИИ», «вы») и текст;
- серая плашка «Выбор за вами · судья fable»: `summary` (пустой — строки нет) и «Отброшено вариантов: 2 — почему» —
  открывает отброшенные: текст зачёркнут, под ним — почему; открыты — «Скрыть отброшенные»; отброшенных нет — «Ничего не
  отброшено». Открыты отброшенные или нет — одно на весь шаг, как в макете. Судья — судья совета (`judge` в
  [списке советов](#get-apicouncils--список-советов)): в макете «судья fable» написан у всех советов;
- варианты карточками с кружком выбора: `id`, метка источника, «рекомендация судьи» (`recommended`), текст; под ним
  «почему» и «цена» (`cost` нет — строки нет); зависимости — «зависит от Q2 · решён»: «решён» — у вопроса выбран
  вариант (зелёным), «не решён» — выбора нет, «unresolved» — передан как unresolved, «убран» — вопроса нет на
  «Вариантах» (его убрали на «Вопросах»); кроме «решён» — жёлтым. Щелчок по зависимости открывает тот вопрос, убранный —
  нет. Выбранная карточка — белая, в тёмной рамке. Справа внизу — «Поправить»;
- «Поправить» — вместо текста поле с ним, «Правка станет вашим вариантом — совет пересмотрит «почему» и «цену» под
  новую формулировку.», «Сохранить» и «Отмена». «Сохранить» у варианта совета — [свой вариант](#post-apicouncilsidstreamsstreamidoptionsquestionid--свой-вариант)
  на его основе (`basedOn`), у своего варианта — [правка своего варианта](#patch-apicouncilsidstreamsstreamidoptionsquestionidoptionid--правка-своего-варианта);
  сохранённую правку интерфейс сразу выбирает
  ([выбор](#put-apicouncilsidstreamsstreamidoptionsquestionidchoice--выбор-по-вопросу)), как у g1 в макете: там свой
  вариант всегда выбран. Текст не меняли — поле закрывается без запроса; пустой — не сохраняется, как
  пустой вопрос на «Вопросах». Не вышло — текст ошибки по коду под кнопками, поле остаётся открытым. «Отмена»
  закрывает поле без запроса;
- «вы · Свой вариант» — щелчок открывает поле «Опишите, как должно работать. Совет допишет «почему», «цену» и
  зависимости.»; набранное сохраняется само, после паузы в наборе (сначала
  [свой вариант](#post-apicouncilsidstreamsstreamidoptionsquestionid--свой-вариант), дальше —
  [правка](#patch-apicouncilsidstreamsstreamidoptionsquestionidoptionid--правка-своего-варианта) этого же варианта),
  и интерфейс выбирает его. Пустое поле выбор не меняет: пока в поле ничего не набрано, его кружок не выбран, выбран
  прежний выбор вопроса (выбора нет — ничего), и «Утвердить» утверждает его. Вариант из поля сохранился, а выбрать его
  не вышло, — так же: кружок не выбран, выбран прежний выбор, как на сервере, под вариантами — текст ошибки по коду;
  щелчок по кружку выбирает вариант из поля снова. Стёрли поле, из которого вариант уже
  создан, — на сервере он с прежним текстом, а пустым его не сохранить: под полем текст ошибки `text_required`, и
  «Утвердить» не утверждает (`not_saved`), пока в поле не впишут текст или у вопроса не выберут другое. Пока поле
  открыто, свой вариант — в нём; выбрали другой вариант
  или ушли к другому вопросу — поле закрывается, а сохранённый вариант стоит среди вариантов карточкой «вы», как у g1
  в макете. Ушли к другому вопросу, а набранное не сохранилось, — поле не закрывается: вернулись к вопросу — оно открыто
  с набранным и текстом ошибки по коду под ним;
- «Пока не решаю — передать как unresolved» — пунктирная карточка с кружком выбора.

Щелчок по варианту или по «Пока не решаю» сразу уходит на сервер
([выбор](#put-apicouncilsidstreamsstreamidoptionsquestionidchoice--выбор-по-вопросу)): у каждого вопроса своя
очередь запросов, на сервере остаётся последний выбор — и когда с «Вариантов» ушли, пока выбор уходил, вернулись и
выбрали другое: новый выбор уходит после ответа на прежний; не вышло — текст ошибки по коду под вариантами вопроса.
Выбрали у вопроса другое (вариант, «Пока не решаю», «Свой вариант» или сохранили правку другого варианта), пока свой
вариант или правка ещё сохранялись, — они сохраняются, но выбором не становятся: выбор за последним щелчком; так же,
когда с «Вариантов» ушли, пока они сохранялись, вернулись и выбрали другое. Пока правка уходит, её поле не правится и к
другому вопросу не уйти (чипы, «←» / «→» и зависимости не действуют): не сохранилась — текст ошибки виден под ней, и
«Утвердить» без неё не утверждает. Шаг ждёт вас или остановился — внизу «Выбрано 2 из 4»
и «Утвердить выбор → к решениям»
([утвердить выбор](#post-apicouncilsidstreamsstreamidoptionsapprove--утвердить-выбор)); шаг готов — низа нет, как в
макете.

Выбирать, писать свой вариант и править можно, пока шаг ждёт вас, остановился или уже готов — как в макете; пока шаг
с ошибкой запускают снова — нельзя. Пока на шаге работают модели (ИИ работает), вместо вопросов — серые строки, а низа
нет: варианты появятся, когда модели закончат. Шаг сменил состояние — варианты запрашиваются заново, а выбор, поле
«Свой вариант» и правка прежних вариантов забываются: набранное в поле и правке не уходит, а то, что уже уходит,
выбором не становится, в варианты у себя не встаёт и дальше не правится — ответ про прежние варианты. Так же — когда
пришли варианты с другим `run`, а состояние шага на экране то же: шаг запустили снова в другой вкладке, и он успел
кончиться, пока экран не видел, что он шёл; id у вариантов могут быть те же, но это другие варианты. Вопроса больше
нет в вариантах (его убрали на «Вопросах», а шаг тот же) — его поле «Свой вариант» и правка забываются так же: их не
видно, и «Утвердить» их не ждёт. Пока варианты
грузятся или не загрузились — в карточке шага «Загружаем…» или текст ошибки и «Повторить».

### GET /api/councils/{id}/streams/{streamId}/options — варианты потока

Кто зовёт: [«Варианты»](#варианты-потока) (`features/options`) — когда открываются, когда шаг сменил состояние и
после правок выбора. В коде — хук `useStreamOptions()`.

Ответ `200` — номер запуска шага и варианты по вопросам, [OptionSet](#optionset--варианты-на-вопрос), в порядке
вопросов потока. Только неубранные вопросы: убранный на «Вопросах» на «Варианты» не идёт, как в макете; вернули — он
снова здесь, со своим выбором.

| Поле         | Тип         | Что                                                                                          |
| ------------ | ----------- | -------------------------------------------------------------------------------------------- |
| `run`        | number      | номер запуска шага «Варианты»: растёт на 1 с каждым запуском моделей на шаге — первым (после «Утвердить вопросы») и каждым «Запустить снова»; шаг не начат — `0` |
| `optionSets` | OptionSet[] | варианты по вопросам                                                                         |

По `run` интерфейс узнаёт, что варианты — от другой работы моделей, когда состояние шага у него то же: шаг запустили
снова в другой вкладке, и он успел кончиться между опросами потоков. Тогда выбор, поле «Свой вариант» и правка
прежних вариантов забываются, как при смене состояния шага (см. [«Варианты»](#варианты-потока)).

```json
{
  "run": 1,
  "optionSets": [
    {
      "question": {
        "id": "Q3",
        "text": "Сжимать фото на устройстве или отправлять оригинал позже?",
        "source": "ai",
        "reason": "F5 и F6 тянут в разные стороны",
        "proposals": [
          { "id": "F6", "text": "Может, сжимать фото на устройстве?", "label": "proposal", "councilLabel": "proposal", "decidedBy": "agreed" }
        ],
        "revisits": null,
        "removed": false
      },
      "summary": "Оба варианта решают F5 — фото не грузятся минутами.",
      "dropped": [{ "text": "Отправлять оригинал как есть", "reason": "Отброшено: не решает F5." }],
      "options": [
        {
          "id": "P21",
          "text": "Сжимать фото до 1600 px на устройстве до постановки в очередь.",
          "source": "group",
          "recommended": true,
          "reason": "F6 — прямо в тексте.",
          "cost": "Оригинал теряется навсегда.",
          "dependsOn": [],
          "basedOn": null
        },
        {
          "id": "P26",
          "text": "Сжимать фото до 2400 px, оригинал хранить на устройстве неделю.",
          "source": "user",
          "recommended": false,
          "reason": null,
          "cost": null,
          "dependsOn": [],
          "basedOn": "P21"
        }
      ],
      "choice": { "kind": "option", "option": "P26" }
    }
  ]
}
```

Шаг не начат — `run` — `0`, `optionSets` — пустой массив. Шаг остановился — варианты моделей, которые успели ответить. Пока модели ищут
варианты, интерфейс их не показывает. Вопрос, добавленный на «Вопросах» уже после «Утвердить вопросы», приходит без
вариантов совета (`options` пустой, `summary` — пустая строка): по нему можно написать свой вариант или передать его как
unresolved.

Ошибки: `not_found` — нет совета или у него нет такого потока; остальные общие.

### PUT /api/councils/{id}/streams/{streamId}/options/{questionId}/choice — выбор по вопросу

Кто зовёт: щелчок по варианту и по «Пока не решаю — передать как unresolved» на [«Вариантах»](#варианты-потока).
В коде — хук `useOptionChoices()`.

```http
PUT /api/councils/c1/streams/B/options/Q3/choice
```

Тело — [Choice](#optionset--варианты-на-вопрос):

```json
{ "kind": "option", "option": "P21" }
```

Что меняется: у вопроса — `choice`; у шага «Варианты» — `note`: сколько вопросов с выбором из всех («выбрано 2 из 3»,
пишет сервер); у совета — `updatedAt`, а если шаг ждёт вас — текст его пункта в `activity` («Выберите вариант на
1 вопрос из 3», пишет сервер). Состояния шагов не меняются, в том числе у готового шага — как в макете.

Ответ `200` — варианты вопроса после выбора, [OptionSet](#optionset--варианты-на-вопрос):

```json
{
  "optionSet": {
    "question": { "id": "Q3", "text": "Сжимать фото на устройстве или отправлять оригинал позже?", "source": "ai", "reason": "F5 и F6 тянут в разные стороны", "proposals": [], "revisits": null, "removed": false },
    "summary": "Оба варианта решают F5 — фото не грузятся минутами.",
    "dropped": [],
    "options": [],
    "choice": { "kind": "option", "option": "P21" }
  }
}
```

После ответа фронтенд сразу ставит варианты вопроса из ответа на место прежних у себя и заново запрашивает варианты,
потоки (строка шага в цепочке) и список советов.

Ошибки:

| code                | HTTP | Когда                                                                          |
| ------------------- | ---- | ------------------------------------------------------------------------------ |
| `unknown_option`    | 422  | в `option` — вариант, которого у вопроса нет                                    |
| `options_not_ready` | 409  | шаг «Варианты» не начат или на нём работают модели                              |
| `not_found`         | 404  | нет совета, у него нет такого потока или вопроса нет на «Вариантах» (нет или убран) |

Интерфейс выбирает только из вариантов вопроса, поэтому `unknown_option` — на случай, когда варианты устарели: текст
ошибки по коду под вариантами вопроса, и варианты запрашиваются заново, как на `not_found`. `options_not_ready` — шаг
запустили снова в другой вкладке: так же, и ещё заново запрашиваются потоки.

### POST /api/councils/{id}/streams/{streamId}/options/{questionId} — свой вариант

Кто зовёт: поле «Свой вариант» — набранное, после паузы в наборе — и «Сохранить» правки варианта совета («Поправить»)
на [«Вариантах»](#варианты-потока). В коде — хук `useAddOption()`.

```http
POST /api/councils/c1/streams/B/options/Q3
Idempotency-Key: 4c7e2a9d1b0f46e8a5c3d7f9b1e2a4c6
```

```json
{ "text": "Сжимать фото до 2400 px, оригинал хранить на устройстве неделю.", "basedOn": "P21" }
```

| Поле      | Тип            | Что                                                                     |
| --------- | -------------- | ----------------------------------------------------------------------- |
| `text`    | string         | вариант; не пустой. Пробелы по краям сервер убирает                     |
| `basedOn` | string \| null | правка — `id` варианта, который правили; свой вариант с нуля — `null`   |

Заголовок `Idempotency-Key` — ключ поля, в котором пишут вариант, как у [нового совета](#post-apicouncils--новый-совет):
пока вариант не создан, все попытки из одного поля идут с одним ключом, даже если текст между ними поправили — это тот
же вариант; вариант создан — следующий идёт с новым ключом. Сервер, получив ключ, по которому уже создал вариант,
второй не создаёт и отвечает им (`201`) — с тем текстом, с которым его создал; интерфейс видит, что текст другой, и
[правит](#patch-apicouncilsidstreamsstreamidoptionsquestionidoptionid--правка-своего-варианта) его. Ключ сервер помнит
не меньше суток.

Новый вариант: `id` — «P» и номер на один больше самого большого номера вариантов потока, `source` — `user`,
`recommended` — `false`, `reason` и `cost` — `null`, `dependsOn` — пустой, `basedOn` — из тела; встаёт в конец
вариантов вопроса. Выбор (`choice`) он не меняет: выбрать — отдельное действие,
[выбор](#put-apicouncilsidstreamsstreamidoptionsquestionidchoice--выбор-по-вопросу). У совета — `updatedAt`; шаги
потока не меняются.

Ответ `201` — созданный вариант, [Option](#option--вариант):

```json
{
  "option": {
    "id": "P26",
    "text": "Сжимать фото до 2400 px, оригинал хранить на устройстве неделю.",
    "source": "user",
    "recommended": false,
    "reason": null,
    "cost": null,
    "dependsOn": [],
    "basedOn": "P21"
  }
}
```

После ответа фронтенд ставит вариант в конец вариантов вопроса у себя и сразу выбирает его — сохранённый свой вариант
и сохранённая правка становятся выбором, как у g1 в макете (свой вариант там всегда выбран). Ушли к другому вопросу,
пока вариант из поля «Свой вариант» сохранялся, — он всё равно становится выбором: его набрали последним. Выбрали у
вопроса другое, пока он сохранялся (другой вариант, «Пока не решаю», сохранили правку), — не становится: выбор — за
последним действием человека. Дальше поле правит вариант по его `id`. Варианты и список советов запрашиваются заново.

Ошибки:

| code                | HTTP | Когда                                                           |
| ------------------- | ---- | --------------------------------------------------------------- |
| `text_required`     | 422  | текст пустой (или из одних пробелов)                            |
| `unknown_option`    | 422  | `basedOn` — вариант, которого у вопроса нет                     |
| `options_not_ready` | 409  | шаг «Варианты» не начат или на нём работают модели              |
| `not_found`         | 404  | нет совета, у него нет такого потока или вопроса нет на «Вариантах» |

Пустой текст интерфейс не отправляет, поэтому `text_required` — на случай чужого клиента. Текст ошибки по коду —
под полем; поле «Свой вариант» пробует снова со следующей правкой, «Сохранить» — по щелчку. На `unknown_option`,
`not_found` и `options_not_ready` — как у выбора.

### PATCH /api/councils/{id}/streams/{streamId}/options/{questionId}/{optionId} — правка своего варианта

Кто зовёт: поле «Свой вариант», когда вариант из него уже создан, и «Сохранить» правки своего варианта («Поправить» у
карточки «вы») на [«Вариантах»](#варианты-потока). В коде — хук `useUpdateOption()`.

```http
PATCH /api/councils/c1/streams/B/options/Q3/P26
```

```json
{ "text": "Сжимать фото до 2400 px, оригинал хранить на устройстве две недели." }
```

Что меняется: у варианта — `text` (без пробелов по краям); «почему», «цену» и зависимости совет пересмотрит под новый
текст, как обещает макет, — до тех пор `reason` и `cost` — `null`, `dependsOn` — пустой. Выбор не меняется; у совета —
`updatedAt`.

Ответ `200` — вариант после правки, [Option](#option--вариант), как у
[своего варианта](#post-apicouncilsidstreamsstreamidoptionsquestionid--свой-вариант).

После ответа фронтенд ставит вариант на место прежнего у себя и, как после своего варианта, выбирает его (у вопроса,
пока вариант сохранялся, выбрали другое — не выбирает); варианты и список советов запрашиваются заново.

Ошибки:

| code                | HTTP | Когда                                                                     |
| ------------------- | ---- | ------------------------------------------------------------------------- |
| `text_required`     | 422  | текст пустой (или из одних пробелов)                                      |
| `not_own_option`    | 422  | вариант — не свой (`source` — не `user`): варианты совета не правят, правка создаёт свой вариант |
| `options_not_ready` | 409  | шаг «Варианты» не начат или на нём работают модели                        |
| `not_found`         | 404  | нет совета, потока, вопроса на «Вариантах» или у вопроса нет такого варианта |

Интерфейс правит только свои варианты и не шлёт пустой текст, поэтому `text_required` и `not_own_option` — на случай
чужого клиента. Поле «Свой вариант», из которого вариант уже создан, стёрли — запроса нет, а текст ошибки
`text_required` интерфейс ставит под полем сам. Остальное — как у [своего варианта](#post-apicouncilsidstreamsstreamidoptionsquestionid--свой-вариант).

### POST /api/councils/{id}/streams/{streamId}/options/approve — утвердить выбор

Кто зовёт: «Утвердить выбор → к решениям» внизу [«Вариантов»](#варианты-потока). В коде — хук `useApproveOptions()`.
Сначала интерфейс дожидается ответов на выбор, свой вариант и правку, которые ещё идут (набранное в поле «Свой
вариант» уходит сразу, и из полей, где сохранить не вышло, — снова), — утверждается то, что на экране; что-то из них не
сохранилось — не утверждает, а под кнопкой — текст ошибки `not_saved` и «Повторить»: ошибка может быть у вопроса,
которого сейчас нет на экране. Выбор, который не сохранился раньше, утверждению не мешает: экран после ошибки уже
показывает выбор с сервера. Пока выбор
утверждается, выбор, свой вариант, правка и «Запустить снова» на плашке шага с ошибкой не действуют; пока шаг
запускают снова, не действуют «Утвердить», выбор, свой вариант и правка: запросы не уходят вместе.

Тело — пустой объект:

```json
{}
```

Что меняется:

- шаг ждёт вас или остановился — «Варианты» готовы (`done`, `text` — `null`, `note` — «выбрано 4 из 4»). Вопрос без
  выбора идёт на «Решения» с первым вариантом — так в макете: «Решения» берут выбор, а нет его — первый вариант;
  вариантов у вопроса нет — он передаётся как unresolved («Передан как unresolved» в макете). Этот выбор сервер
  записывает в `choice` вопроса. Шаг остановился — идут варианты моделей, которые успели ответить; ход последнего
  запуска остаётся как был. Модели начинают проверять решения: «Решения» — `running`, `text` — что делают модели,
  в `progress` — модели совета работают, судья ждёт. В макете «Решения» сразу ждут вас, будто модели уже поработали;
  у нас — когда модели закончат;
- шаг уже готов — сервер ничего не меняет и отвечает потоком как есть;
- совет — см. [«Как шаги потоков меняют совет»](#потоки-совета).

Ответ `200` — поток после утверждения, [Stream](#stream--поток), как у
[«Запустить снова»](#post-apicouncilsidstreamsstreamidretry--запустить-шаг-снова).

После ответа фронтенд сразу ставит поток из ответа на место прежнего у себя, заново запрашивает потоки, варианты и
список советов и открывает «Решения» потока (`/c/<id>/streams/<поток>/decisions`); ушёл с шага, пока выбор
утверждался, — не открывает.

Ошибки:

| code                | HTTP | Когда                                              |
| ------------------- | ---- | -------------------------------------------------- |
| `options_not_ready` | 409  | шаг «Варианты» не начат или на нём работают модели |
| `not_found`         | 404  | нет совета или у него нет такого потока            |

«Утвердить» есть, только когда шаг ждёт вас или остановился, поэтому `options_not_ready` — на случай, когда шаг
запустили снова в другой вкладке: интерфейс показывает текст ошибки по коду под кнопкой и заново запрашивает потоки и
варианты. Остальные — текст ошибки по коду под кнопкой и «Повторить».

### GET /api/models — модели совета

Модели, которые работают в советах, — все, в том числе не подключённые. Порядок задаёт сервер, фронтенд его
сохраняет.

Кто зовёт: меню слева, блок «Модели совета» (`features/frame`); «Ввод» — блок «Совет» (`features/brief`). В коде —
хук `useModels()`; после ошибок `unknown_model` и `model_offline` у [правки совета](#patch-apicouncilsid--правка-совета)
список запрашивается заново.

Ответ `200`:

```json
{
  "models": [
    { "id": "sol", "provider": "codex", "model": "gpt-5.6-sol", "online": true },
    { "id": "fable", "provider": "claude", "model": "claude-fable-5-1", "online": true },
    { "id": "opus", "provider": "claude", "model": "claude-opus-5-5", "online": false }
  ]
}
```

`models` — массив [Model](#model--модель-совета); моделей нет — пустой массив.

Меню показывает у модели имя (`id`), провайдера (`provider`) и метку — как в макете:

- не подключена (`online: false`) — «офлайн»;
- подключена и судит открытый совет (`judge` открытого совета в [списке советов](#get-apicouncils--список-советов)) —
  «судья»;
- остальные подключённые — «в совете».

Метка «судья» — только на экранах совета; на Сводке и в Проектах её нет (решение q-001). Отдельной ручки для судьи нет:
он приходит в списке советов.

Ошибки: только общие.

### GET /api/projects — проекты

Все проекты. Порядок задаёт сервер, фронтенд его сохраняет; в макете — в порядке создания.

Кто зовёт: Проекты (`features/projects`); «Ввод» — чипы проектов (`features/brief`). В коде — хук `useProjects()`;
после [нового проекта](#post-apiprojects--новый-проект), [правки](#patch-apiprojectsid--сохранить-проект),
[удаления проекта](#delete-apiprojectsid--удалить-проект), [«Нового совета»](#post-apicouncils--новый-совет),
[смены проекта у совета](#patch-apicouncilsid--правка-совета) и ошибки `unknown_project` список запрашивается заново.

Проекты показывают этот список, как в макете: пояснение и карточки сеткой, в порядке списка. На карточке:

- название (`name`) и в скольких советах выбран проект (`councilCount`): «в 3 советах», `0` — «не используется»;
- «Репозитории» — `repos` плашками;
- «Папка документации» — `docs`; пустая строка — красным «Без папки: потоки не выгрузить в заметки»;
- «Править» — окно проекта, см. [правку](#patch-apiprojectsid--сохранить-проект); «Удалить» — см.
  [удаление](#delete-apiprojectsid--удалить-проект).

Ответ `200`:

```json
{
  "projects": [
    {
      "id": "p1",
      "name": "Кромка",
      "repos": ["kromka-api", "kromka-frontend", "kromka-android"],
      "docs": "kromka-api/docs/reasoning",
      "councilCount": 3
    },
    {
      "id": "p2",
      "name": "looper",
      "repos": ["looper"],
      "docs": "",
      "councilCount": 2
    }
  ]
}
```

`projects` — массив [Project](#project--проект); проектов нет — пустой массив.

Ошибки: только общие.

### Окно проекта

Одно окно на новый проект и правку — как в макете. Открывают его «+ Новый проект» в шапке «Проектов» и «Править» на
карточке проекта (`components/ProjectDialog`); в макете «+ Новый проект» есть только на «Проектах».

- Заголовок — «Новый проект» или «Проект»; кнопка сохранения — «Создать проект» или «Сохранить».
- «Название» — поле; у правки в нём название проекта.
- «Репозитории» — галочки на каждую рабочую копию из [GET /api/repos](#get-apirepos--рабочие-копии-git), в порядке
  списка; у правки отмечены репозитории проекта. Репозитории проекта, которых в списке уже нет, стоят после списка,
  отмеченными, — их можно снять и, пока окно открыто, отметить снова. Отмеченный репозиторий встаёт в конец `repos`, порядок остальных не меняется — как в
  макете. Отмечено 10 — остальные галочки недоступны («Не больше 10»).
- «Папка документации» — поле; у правки в нём `docs`.
- Сохранить нельзя без названия — кнопка недоступна, как и пока идёт запрос. Сохранилось — окно закрывается; не
  вышло — текст ошибки по коду над кнопками, окно остаётся открытым.
- «Отмена», «×», клик мимо окна и Esc закрывают окно; несохранённые правки пропадают.

Окно запоминает поля проекта, когда открывается: новый список проектов, пришедший, пока окно открыто, их не меняет.

### POST /api/projects — новый проект

Создаёт проект. Кто зовёт: «Создать проект» в окне «Новый проект». В коде — хук `useCreateProject()`. После ответа
фронтенд закрывает окно, ставит проект из ответа в конец списка проектов у себя — как в макете — и заново запрашивает
список проектов.

Тело — [ProjectFields](#projectfields--поля-проекта):

```json
{ "name": "Агенты", "repos": ["agent-workers"], "docs": "" }
```

Заголовок `Idempotency-Key` — ключ нового проекта, как у [нового совета](#post-apicouncils--новый-совет): пока проект
не создан, все попытки из одного окна — с одним ключом; новое окно «Новый проект» — новый ключ. Сервер, получив ключ,
по которому уже создал проект, второй не создаёт и отвечает этим проектом (`201`), даже если поля в теле другие. Ключ
сервер помнит не меньше суток.

```http
POST /api/projects
Idempotency-Key: 0c4e8f2a9b7d41e6a3f5c2d1e0b9a8f7
```

Новый проект встаёт в конец [списка проектов](#get-apiprojects--проекты); он не выбран ни в одном совете
(`councilCount` — `0`).

Ответ `201` — созданный проект, [Project](#project--проект):

```json
{
  "project": { "id": "p5", "name": "Агенты", "repos": ["agent-workers"], "docs": "", "councilCount": 0 }
}
```

Ошибки — [ошибки полей](#projectfields--поля-проекта) и общие. Интерфейс показывает текст ошибки по коду над кнопками
окна; повторить — снова «Создать проект».

### PATCH /api/projects/{id} — сохранить проект

Меняет поля проекта. Кто зовёт: «Сохранить» в окне «Проект» — его открывает «Править» на карточке проекта. В коде —
хук `useUpdateProject()`.

Тело — [ProjectFields](#projectfields--поля-проекта). Поля, которых нет в теле, не меняются; окно проекта шлёт все три.

```http
PATCH /api/projects/p1
```

```json
{ "name": "Кромка", "repos": ["kromka-api", "kromka-frontend"], "docs": "kromka-api/docs/reasoning" }
```

Название проекта меняется везде, где он есть: в `project` советов в [списке советов](#get-apicouncils--список-советов)
приходит новое название. Проект в советах править можно — так в макете.

Ответ `200` — проект после правки, [Project](#project--проект):

```json
{
  "project": {
    "id": "p1",
    "name": "Кромка",
    "repos": ["kromka-api", "kromka-frontend"],
    "docs": "kromka-api/docs/reasoning",
    "councilCount": 3
  }
}
```

После ответа фронтенд закрывает окно, сразу ставит проект из ответа на место старого в списке проектов и новое
название — в советы этого проекта у себя (меню слева, шапка совета), и заново запрашивает список проектов и список
советов.

Ошибки — [ошибки полей](#projectfields--поля-проекта) и общие:

- `not_found` — проекта уже нет, например его удалили в другой вкладке. Интерфейс показывает текст ошибки по коду над
  кнопками окна, убирает проект из списка у себя и заново запрашивает список проектов;
- остальные — текст ошибки по коду над кнопками окна; повторить — снова «Сохранить».

### DELETE /api/projects/{id} — удалить проект

Удаляет проект. Удалить можно только проект, который не выбран ни в одном совете (`councilCount` — `0`), — так в
макете.

Кто зовёт: «Удалить» на карточке проекта (`features/projects`). В коде — хук `useDeleteProject()`. Как в макете:

- проект в советах — «Удалить» недоступна;
- первое нажатие «Удалить» ничего не удаляет, а превращает кнопку в красное «Да, удалить»; «Удалить» у другого
  проекта переносит вопрос туда; ушли с экрана — вопрос снят;
- «Да, удалить» шлёт запрос. Пока он идёт, «Удалить» у всех проектов недоступна. После ответа фронтенд сразу убирает
  проект из списка у себя и заново запрашивает список проектов.

Тела нет.

```http
DELETE /api/projects/p5
```

Ответ `204` — без тела.

Ошибки:

| code             | HTTP | Когда                                                     |
| ---------------- | ---- | --------------------------------------------------------- |
| `project_in_use` | 409  | проект выбран хотя бы в одном совете — его не удалить      |
| `not_found`      | 404  | проекта нет                                                |

- `project_in_use` — проект успели выбрать в совете, пока список был на экране. Интерфейс показывает текст ошибки по
  коду на карточке без «Повторить», сразу делает «Удалить» у проекта недоступной и заново запрашивает список
  проектов — с новым числом советов. «Удалить» остаётся недоступной, пока этот список не придёт, — даже если человек
  тем временем нажал «Удалить» у другого проекта или список не загрузился.
- `not_found` — проекта уже нет, например его удалили в другой вкладке. Для интерфейса это тоже «удалён»: он убирает
  проект из списка, ошибку не показывает.
- Остальные — общие: интерфейс показывает текст ошибки по коду на карточке и «Повторить».

### GET /api/repos — рабочие копии git

Рабочие копии git, которые лежат в папке COUNCIL_REPOS на сервере, — их отмечают в окне проекта. Порядок задаёт
сервер, фронтенд его сохраняет.

Кто зовёт: окно проекта, «Репозитории» (`components/ProjectDialog`) — каждый раз, когда окно открывается. В коде — хук
`useRepos()`; после ошибки `unknown_repo` у [нового проекта](#post-apiprojects--новый-проект) или
[правки](#patch-apiprojectsid--сохранить-проект) список запрашивается заново. Пока список грузится или не загрузился,
на месте галочек — «Загружаем…» или текст ошибки и «Повторить».

Ответ `200`:

```json
{
  "repos": [
    "gen_sdk_tooling",
    "python-t-cloud",
    "kromka-api",
    "kromka-frontend",
    "kromka-android",
    "looper",
    "site",
    "agent-workers"
  ]
}
```

`repos` — имена рабочих копий: так их пишет `repos` у [Project](#project--проект). Рабочих копий нет — пустой массив.

Ошибки: только общие.
